## 02-howto

> как в python прочитать jsonl построчно и пропустить битые строки, но залогировать номер строки

### real (1693 chars)

Используй `enumerate(f, start=1)` и лови `json.JSONDecodeError` на каждой строке:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid line.
    """
    with open(path, encoding="utf-8", errors="replace") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                logger.warning("%s:%d: invalid JSON (%s)", path, lineno, e.msg)
```

Использование:

```python
logging.basicConfig(level=logging.INFO)
for record in read_jsonl("data.jsonl"):
    ...
```

Что здесь важно:

- Нумерация с 1 совпадает с номерами строк в редакторе и в `sed -n '42p'`.
- Пустые строки пропускаются молча, обычно это хвостовой `\n` в конце файла. Если их тоже надо считать ошибкой, убери `continue` и логируй.
- `errors="replace"` нужен, чтобы битая кодировка в одной строке не роняла весь цикл с `UnicodeDecodeError`. Такая строка почти наверняка не распарсится и попадёт в лог. Если битый UTF-8 должен быть фатальным, убери этот параметр.
- Генератор не грузит файл в память целиком, так что подходит и для больших файлов.

Если нужно ещё вернуть список номеров битых строк, например для итогового отчёта, собирай их в `list[int]` в `except` и возвращай кортежем вместо генератора.

## 03-concept

> Объясни, что такое идемпотентность в HTTP API и зачем нужен Idempotency-Key.

### real (3082 chars)

Идемпотентная операция при повторном выполнении с теми же параметрами даёт тот же результат на сервере, что и при однократном. Idempotency-Key нужен, чтобы сделать такими операции, которые по природе не идемпотентны, в первую очередь POST.

## Идемпотентность методов

По RFC 9110:

| Метод | Идемпотентен | Почему |
|---|---|---|
| GET, HEAD, OPTIONS | да | ничего не меняют |
| PUT | да | «установи ресурс в такое состояние»: второй раз состояние то же |
| DELETE | да | после первого вызова ресурса нет, после второго тоже нет (код ответа может отличаться, 200 и 404, это допустимо) |
| POST | нет | «создай ещё один»: два вызова дают два заказа |
| PATCH | не гарантируется | `{"balance": 100}` идемпотентен, `{"op": "increment"}` нет |

Речь именно о состоянии сервера, а не об одинаковости ответа. Логи, метрики и счётчики просмотров не считаются.

## Зачем это нужно

Сеть ненадёжна. Клиент отправил запрос на оплату, соединение оборвалось по таймауту. Он не знает, дошёл ли запрос до сервера, обработался ли он и потерялся только ответ. Безопасный повтор возможен только для идемпотентной операции. Для PUT и DELETE клиент, прокси и балансировщик могут повторять запрос автоматически. Повтор POST на создание платежа означает риск двойного списания.

## Как работает Idempotency-Key

Клиент генерирует уникальный ключ (обычно UUID) на каждую логическую операцию и передаёт его в заголовке:

```http
POST /payments
Idempotency-Key: 7f3c9a2e-4b1d-4e8a-9c3f-2a1b5d6e8f90
Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

При повторе клиент отправляет тот же ключ. Сервер:

1. Ищет ключ в хранилище (БД, Redis), с привязкой к пользователю или API-ключу.
2. Если ключа нет, атомарно резервирует его, выполняет операцию, сохраняет ответ (статус и тело) вместе с ключом.
3. Если ключ есть и операция завершена, возвращает сохранённый ответ, ничего не выполняя повторно.
4. Если ключ есть, но операция ещё идёт (параллельный повтор), возвращает 409 Conflict или ждёт.
5. Если ключ тот же, а тело запроса другое, возвращает ошибку (обычно 422). Для этого вместе с ключом хранят хэш тела.

Ключи хранят ограниченное время, например 24 часа у Stripe.

## Детали, на которых чаще всего ошибаются

- Проверку и резервирование ключа надо делать атомарно (unique constraint, `INSERT ... ON CONFLICT`, `SET NX` в Redis). Иначе два параллельных запроса оба увидят «ключа нет» и оба выполнятся.
- Запись ключа и бизнес-действие лучше фиксировать в одной транзакции. Если платёж прошёл, а ключ не сохранился, повтор снова спишет деньги.
- Ключ генерирует клиент один раз на намерение пользователя, а не на каждую попытку. Новый UUID на ретрай ломает всю схему.
- Ошибки 5xx обычно не кэшируют, чтобы повтор мог выполниться заново. Ошибки валидации 4xx кэшировать можно.
- Внешние вызовы внутри операции (платёжный шлюз) тоже должны быть идемпотентными. Ключ обычно передают дальше по цепочке.

Заголовок используют Stripe, PayPal, Adyen и другие платёжные API. В IETF есть черновик стандарта `draft-ietf-httpapi-idempotency-key-header`, который формализует эту практику.

## 04-choice

> что взять для фоновых задач в небольшом fastapi проекте: celery, rq или arq? сервер один, задач ~1000 в день, редис уже есть

### real (1178 chars)

**arq, если код задач асинхронный, rq, если синхронный.** Celery для одного сервера и ~1000 задач в день избыточен: отдельный конфиг, свои воркеры с prefork, beat для расписаний, больше движущихся частей и неочевидных настроек (acks, prefetch, visibility timeout). Его плюсы, то есть несколько брокеров, сложные цепочки и канвасы, роутинг по очередям на разных машинах, тебе сейчас не нужны.

arq хорошо ложится на FastAPI: задачи это `async def`, можно переиспользовать тот же async-клиент к БД и httpx, есть ретраи, отложенный запуск и cron из коробки, воркер один процесс на asyncio. Минус: проект развивается медленно, перед выбором стоит глянуть активность репозитория.

rq проще всего в понимании и отладке, есть rq-dashboard, но задачи синхронные и каждая выполняется в форкнутом процессе. Если в проекте всё на async, придётся либо дублировать синхронные клиенты, либо оборачивать в `asyncio.run`, это неудобно.

Есть ещё вариант без новых зависимостей: встроенный `BackgroundTasks` в FastAPI. Он подойдёт, если задачи короткие и потерять их при рестарте не страшно, потому что очереди и ретраев там нет. Если нужны гарантии выполнения, повторы или расписание, бери arq.

## 05-debug

> чё за хрень, вчера работало
> 
> Traceback (most recent call last):
>   File "/app/worker.py", line 51, in <module>
>     asyncio.run(main())
>   File "/usr/lib/python3.12/asyncio/runners.py", line 194, in run
>     return runner.run(main)
>   File "/app/worker.py", line 44, in main
>     await asyncio.gather(*(process(job) for job in jobs))
>   File "/app/worker.py", line 30, in process
>     async with pool.acquire() as conn:
>   File "/app/.venv/lib/python3.12/site-packages/asyncpg/pool.py", line 1024, in __aenter__
>     self.connection = await self.pool._acquire(self.timeout)
> RuntimeError: Task <Task pending name='Task-3' coro=<process() running at /app/worker.py:30>> got Future <Future pending> attached to a different loop
> 
> пул создаётся на уровне модуля: pool = asyncio.get_event_loop().run_until_complete(asyncpg.create_pool(DSN))

### real (1712 chars)

Пул создан в одном event loop, а `asyncio.run()` запускает `main()` в другом. Пул и его соединения привязаны к первому loop, поэтому при `acquire()` получается Future «из чужого цикла».

`asyncio.get_event_loop().run_until_complete(...)` на уровне модуля создаёт loop №1 и открывает в нём пул. Потом `asyncio.run(main())` создаёт новый loop №2. Внутренняя очередь пула и транспорты соединений остаются на loop №1.

Почему вчера работало, точно не скажу. Скорее всего, сегодня одновременных `process()` стало больше, чем `max_size` пула (по умолчанию 10). Пока в очереди пула есть свободное соединение, `acquire()` отдаёт его сразу. Когда свободных нет, задача начинает ждать, создаётся Future, и проверка loop падает. Второй вариант: обновился `asyncpg` или образ. Сравни `pip freeze` со вчерашним, если есть с чем.

Исправление: создавать пул внутри `main()`, в том же loop.

```python
import asyncio
import asyncpg

pool: asyncpg.Pool | None = None


async def process(job) -> None:
    assert pool is not None
    async with pool.acquire() as conn:
        ...


async def main() -> None:
    global pool
    pool = await asyncpg.create_pool(DSN)
    try:
        jobs = ...
        await asyncio.gather(*(process(job) for job in jobs))
    finally:
        await pool.close()


if __name__ == "__main__":
    asyncio.run(main())
```

Глобальную переменную лучше заменить на передачу пула аргументом, `process(pool, job)`. Тогда модуль не держит состояние и его проще тестировать.

`get_event_loop()` без запущенного loop в 3.12 выдаёт `DeprecationWarning`, а в 3.14 будет ошибкой. Так что этот вызов на уровне модуля в любом случае стоит убрать.

Если пришлёшь `worker.py` целиком, внесу правку прямо в файл.

## 07-deep

> Разбери подробно, как в PostgreSQL работает MVCC: снапшоты, xmin/xmax, видимость строк, зачем нужен VACUUM и что такое wraparound. Мне нужно глубоко, со всеми нюансами.

### real (22455 chars)

MVCC в PostgreSQL устроен так: каждая версия строки хранит в заголовке xid создавшей её транзакции (`xmin`) и удалившей (`xmax`), а каждый запрос получает снапшот, по которому решает, какие версии ему видны. Старые версии физически остаются в таблице, пока VACUUM не убедится, что их уже никто не увидит. Ниже по порядку, от устройства кортежа до wraparound.

## 1. Базовая модель и её цена

UPDATE не перезаписывает строку на месте. Он помечает старую версию как удалённую и вставляет новую. DELETE только помечает. ROLLBACK физически ничего не откатывает: транзакция отмечается как прерванная в `pg_xact`, и все её версии становятся мусором. Undo-журнала нет. В Oracle и InnoDB в таблице лежит последняя версия, а старые живут в undo-сегментах; в PostgreSQL все версии лежат в самой таблице.

Плюсы такого подхода: читатели не блокируют писателей и наоборот, откат и коммит выполняются за O(1) независимо от объёма изменений. Минусы: таблицы и индексы распухают от мёртвых версий, их надо чистить, а 32-битные xid в заголовках надо «замораживать».

## 2. Идентификаторы транзакций

- `xid` 32-битный. Зарезервированы 0 (`InvalidTransactionId`), 1 (`BootstrapTransactionId`), 2 (`FrozenTransactionId`), обычные начинаются с 3.
- Выдаётся лениво, при первой записи: INSERT/UPDATE/DELETE, `SELECT FOR UPDATE`, многие DDL. До этого у транзакции есть только virtual xid, который на диск не попадает. Читающие транзакции xid не расходуют. Проверить можно через `pg_current_xact_id_if_assigned()`.
- Внутри сервер ведёт 64-битный `FullTransactionId` (эпоха плюс xid), `pg_current_xact_id()` возвращает `xid8`. Но в заголовке кортежа лежат 32 бита, отсюда и wraparound.
- Статус транзакции хранится в `pg_xact` (бывший clog): 2 бита на xid, состояния `IN_PROGRESS`, `COMMITTED`, `ABORTED`, `SUB_COMMITTED`. Страницы кэшируются в SLRU-буферах в shared memory. Коммит после сброса WAL-записи сводится к смене двух бит.
- Подтранзакции (`SAVEPOINT`, блоки `EXCEPTION` в PL/pgSQL) получают собственные xid, связь с родителем хранится в `pg_subtrans`.

## 3. Заголовок кортежа

`HeapTupleHeaderData` занимает 23 байта плюс выравнивание:

| Поле | Смысл |
|---|---|
| `t_xmin` | xid, вставивший версию |
| `t_xmax` | xid, удаливший, обновивший или заблокировавший версию; 0, если такого нет |
| `t_cid` | номер команды внутри транзакции (cmin, cmax или combo CID, если нужны оба) |
| `t_ctid` | адрес (страница, line pointer) самой версии или следующей, более новой |
| `t_infomask` | hint bits и флаги про xmin/xmax |
| `t_infomask2` | число атрибутов и HOT-флаги |

Флаги, важные для видимости:

- `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID`: hint bits о судьбе xmin. Оба сразу означают `HEAP_XMIN_FROZEN`.
- `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID`: то же для xmax.
- `HEAP_XMAX_LOCK_ONLY`: xmax означает только блокировку строки, удаления не было.
- `HEAP_XMAX_IS_MULTI`: в xmax лежит MultiXactId.

Посмотреть можно через системные колонки:

```sql
CREATE TABLE t (id int, v text);
INSERT INTO t VALUES (1, 'a');
SELECT ctid, xmin, xmax, * FROM t;
--  ctid | xmin | xmax | id | v
-- (0,1) | 1001 |    0 |  1 | a

UPDATE t SET v = 'b';
SELECT ctid, xmin, xmax, * FROM t;
-- (0,2) | 1002 |    0 |  1 | b
```

Версия `(0,1)` по-прежнему лежит на странице с `xmax = 1002`. Увидеть её можно через `pageinspect`:

```sql
CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid, t_infomask::bit(16)
FROM heap_page_items(get_raw_page('t', 0));
```

Ненулевой `xmax` у видимой строки не означает, что она удалена. Если другая сессия начала DELETE и ещё не закоммитила, вы увидите строку с её xid в `xmax`. То же бывает после откатившегося UPDATE и после `SELECT FOR UPDATE`.

## 4. Снапшот

Снапшот (`SnapshotData`) состоит из:

- `xmin`: наименьший xid, активный в момент снимка. Все xid меньше него завершены, их судьбу знает `pg_xact`.
- `xmax`: первый ещё не выданный xid (`latestCompletedXid + 1`). Всё, что `>= xmax`, для снапшота находится в будущем.
- `xip[]`: xid из диапазона `[xmin, xmax)`, активные в момент снимка. Плюс `subxip[]` для подтранзакций.
- `curcid`: номер текущей команды, нужен для видимости собственных изменений.

```sql
SELECT pg_current_snapshot();
-- 1005:1009:1005,1007
```

Здесь 1006 и 1008 завершены, 1005 и 1007 активны, 1009 и дальше ещё не существуют. Транзакция считается закоммиченной для снапшота, если она закоммичена в `pg_xact`, её xid меньше `snapshot.xmax` и её нет в `xip`.

Снапшот строит `GetSnapshotData`, обходя ProcArray (массив всех бэкендов) под `ProcArrayLock` в shared-режиме. На сотнях соединений это было заметной точкой contention; в PG14 структуру переделали (плотные массивы xid, кэширование снапшота), и стоимость сильно упала.

**Переполнение подтранзакций.** Каждый бэкенд кэширует в PGPROC до 64 xid своих подтранзакций. Если их больше, снапшот получает флаг `suboverflowed`, и проверка любого xid из диапазона снапшота требует похода в `pg_subtrans` за родителем. Это известный обрыв производительности, особенно на репликах. Типичные источники: SAVEPOINT в цикле, EXCEPTION-блок внутри цикла в PL/pgSQL, ORM, оборачивающие каждый запрос в savepoint.

## 5. Когда берётся снапшот: уровни изоляции

| Уровень | Снапшот | Конфликт записи с параллельной транзакцией |
|---|---|---|
| Read Uncommitted | ведёт себя как Read Committed | |
| Read Committed (по умолчанию) | новый на каждый оператор | ждёт, затем перепроверяет новейшую версию (EvalPlanQual) |
| Repeatable Read | один на транзакцию, берётся на первом операторе | ошибка 40001 `could not serialize access due to concurrent update` |
| Serializable | как в RR, плюс SSI: предикатные блокировки и отслеживание rw-зависимостей | ошибка 40001 при опасной структуре зависимостей |

Нюансы:

- В Repeatable Read снапшот берётся на первом запросе после `BEGIN`, сам `BEGIN` его не фиксирует.
- В Read Committed функция с `VOLATILE` берёт новый снапшот на каждый свой запрос, `STABLE` и `IMMUTABLE` используют снапшот вызывающего оператора.
- **UPDATE в Read Committed.** T1 обновила строку и не закоммитила. T2 выполняет `UPDATE ... WHERE ...`, находит строку по своему снапшоту и видит в `xmax` живую транзакцию. T2 ждёт её, беря ShareLock на xid T1 (каждая транзакция держит ExclusiveLock на собственный xid). Если T1 откатилась, T2 обновляет исходную версию. Если закоммитилась, T2 идёт по цепочке `t_ctid` к новейшей версии, заново вычисляет WHERE только для неё и обновляет, если условие всё ещё выполняется. В итоге один оператор видит остальные строки по старому снапшоту, а эту по свежей версии. Отсюда аномалии вроде `UPDATE t SET x = x + 1 WHERE x = 5`, который при параллельных изменениях пропускает строки.
- `pg_export_snapshot()` плюс `SET TRANSACTION SNAPSHOT` позволяют нескольким соединениям работать с одной картиной данных. Так `pg_dump --jobs` получает согласованный дамп.

## 6. Правила видимости

Упрощённая логика `HeapTupleSatisfiesMVCC`.

**Проверка xmin:**

1. Если стоит `XMIN_INVALID`, версия невидима.
2. Если xmin принадлежит текущей транзакции или её подтранзакции, версия видна только при `cmin < curcid`, то есть если её вставила предыдущая команда. Поэтому `INSERT INTO t SELECT * FROM t` не зацикливается (проблема Хэллоуина).
3. Если xmin активен с точки зрения снапшота (есть в `xip` или `>= snapshot.xmax`), версия невидима, даже если в `pg_xact` она уже закоммичена.
4. Иначе смотрим `pg_xact`: закоммичена, ставим `XMIN_COMMITTED` и идём дальше; иначе ставим `XMIN_INVALID`, версия невидима. Транзакции, оборвавшиеся при крэше, в `pg_xact` остаются `IN_PROGRESS`, но после рестарта они не активны и не закоммичены, поэтому считаются прерванными.

**Проверка xmax** (если xmin прошла):

1. `xmax = 0` или стоит `XMAX_INVALID`: видна.
2. `XMAX_LOCK_ONLY`: видна, это только блокировка.
3. `XMAX_IS_MULTI`: из MultiXact извлекается xid обновляющего участника, дальше как для обычного xid.
4. xmax принадлежит текущей транзакции: видна при `cmax >= curcid` (удалена командой, начавшейся после текущей).
5. xmax активен для снапшота: видна, удаление для нас ещё не произошло.
6. xmax закоммичен: невидима. Откатился: ставим `XMAX_INVALID`, видна.

Порядок проверок принципиален. При коммите сервер сначала пишет `COMMITTED` в `pg_xact` и только потом убирает транзакцию из ProcArray. Для MVCC источником истины служит снапшот, а `pg_xact` используется только для xid, которые снапшот считает завершёнными. В проверках без снапшота (`HeapTupleSatisfiesUpdate` и подобных) по той же причине `TransactionIdIsInProgress` вызывается раньше `TransactionIdDidCommit`.

## 7. Hint bits

Ходить в `pg_xact` за каждой строкой дорого, поэтому первый бэкенд, узнавший судьбу xmin или xmax, ставит hint bit в заголовок кортежа. Дальнейшие проверки обходятся без `pg_xact`.

- Бит ставится, только когда транзакция завершена и её коммит-запись в WAL уже на диске. При `synchronous_commit = off` есть окно, в котором ставить бит нельзя.
- Установка hint bit пачкает страницу. Поэтому первый `SELECT` по свежезагруженной таблице вызывает запись на диск.
- Сами hint bits в WAL не пишутся. Но при включённых checksums или `wal_log_hints` первое изменение страницы после чекпоинта порождает full page image. Значит, `SELECT` может генерировать WAL. С PG18 `initdb` включает checksums по умолчанию.

## 8. Блокировки строк и MultiXact

`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` не создают записей в lock manager на каждую строку. Они пишут свой xid в `xmax` с флагом `LOCK_ONLY` и битами режима. Поэтому можно заблокировать миллион строк без исчерпания shared memory, но каждая блокировка пачкает страницу и пишет WAL.

Если строку одновременно держат несколько транзакций, в `xmax` пишется MultiXactId: ссылка на набор пар (xid, режим) в `pg_multixact/offsets` и `pg_multixact/members`. Частая ситуация: каждый INSERT в дочернюю таблицу берёт `FOR KEY SHARE` на родительскую строку из-за внешнего ключа, а параллельно кто-то её обновляет. MultiXactId тоже 32-битные и подвержены собственному wraparound. Кроме того, пространство members ограничено примерно 4 млрд записей, и его исчерпание тоже останавливает запись.

## 9. Цепочки версий, HOT и pruning

Индексная запись указывает на (страница, line pointer). При обычном UPDATE новая версия получает новые записи во всех индексах, даже если индексированные колонки не менялись.

**HOT (heap-only tuple).** Если ни одна индексированная колонка не изменилась и новая версия помещается на ту же страницу, индексы не трогаются. Старая версия получает флаг `HEAP_HOT_UPDATED`, новая `HEAP_ONLY_TUPLE`, связь идёт через `t_ctid`. Индекс указывает на корень цепочки, и сервер проходит по ней до видимой версии. С PG16 изменение колонок, покрытых только BRIN (summarizing) индексами, HOT не ломает.

**Pruning.** Когда бэкенд читает страницу, на которой мало свободного места, он при возможности взять cleanup lock чистит её сам, без VACUUM. Мёртвые HOT-версии удаляются, корневой line pointer превращается в `LP_REDIRECT` на живую версию. Мёртвые не-HOT версии превращаются в 4-байтовые заглушки `LP_DEAD`: место под данные освобождается, но сам line pointer освободить нельзя, пока на него ссылаются индексы. Это делает только VACUUM.

Практика: для часто обновляемых таблиц `fillfactor` 70–90 оставляет место для HOT. Долю HOT видно по `n_tup_hot_upd` против `n_tup_upd` в `pg_stat_user_tables`.

Индексы не хранят xmin/xmax, поэтому индексный поиск всегда проверяет видимость в heap. Исключение: Index Only Scan по страницам, помеченным all-visible в visibility map. Если индексный скан обнаружил, что версия мертва для всех, он помечает индексную запись `LP_DEAD` (kill_prior_tuple), и при следующем переполнении страницы индекса её удаляют без VACUUM. С PG14 в btree есть ещё bottom-up deletion для дубликатов, порождённых не-HOT обновлениями.

## 10. Горизонт удаления

Версию можно удалить, когда её `xmax` закоммичен и старше горизонта, то есть минимального xmin среди всех, кто ещё может её увидеть:

- снапшоты активных транзакций (для обычных таблиц учитываются бэкенды той же базы, для общих каталогов все);
- `xmin` физических слотов репликации, а при `hot_standby_feedback = on` и горизонт запросов на реплике;
- `catalog_xmin` логических слотов (держит только системные каталоги);
- prepared transactions (`PREPARE TRANSACTION`), они переживают рестарт.

С PG14 горизонты считаются раздельно для общих каталогов, обычных каталогов, данных и временных таблиц (`GlobalVisState`).

Горизонт держит любой открытый снапшот: долгий запрос, сессия `idle in transaction` на Repeatable Read, работающий `pg_dump`. Пока горизонт стоит, VACUUM работает впустую: в `VACUUM VERBOSE` это видно как «N are dead but not yet removable, oldest xmin: X».

Диагностика:

```sql
SELECT pid, datname, state, backend_xid, backend_xmin,
       age(backend_xmin) AS xmin_age, xact_start, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

SELECT slot_name, slot_type, active, xmin, catalog_xmin,
       age(xmin), age(catalog_xmin)
FROM pg_replication_slots;

SELECT gid, prepared, transaction, age(transaction)
FROM pg_prepared_xacts;
```

Защиты: `idle_in_transaction_session_timeout`, `transaction_timeout` (PG17), `idle_replication_slot_timeout` (PG18) для брошенных слотов. `old_snapshot_threshold` удалён в PG17.

Реплики: если VACUUM на мастере удалил версии, нужные запросу на реплике, запрос отменяется с `canceling statement due to conflict with recovery` после `max_standby_streaming_delay`. `hot_standby_feedback` убирает эти отмены ценой bloat на мастере.

## 11. VACUUM

Обычный VACUUM (без FULL) для одной таблицы:

1. **Сканирование heap.** Страницы all-visible пропускаются по visibility map (в неагрессивном режиме). На каждой странице выполняется pruning, собираются TID мёртвых кортежей, замораживаются подходящие кортежи, обновляется VM.
2. **Очистка индексов.** Когда память под TID (`maintenance_work_mem` или `autovacuum_work_mem`) заполнилась или скан закончен, VACUUM проходит по каждому индексу (`ambulkdelete`) и удаляет записи, указывающие на собранные TID. Btree читается целиком, поэтому нехватка памяти означает несколько полных проходов по всем индексам. До PG17 TID хранились плоским массивом с потолком 1 ГБ (около 178 млн TID); в PG17 его заменили на TidStore (радикс-дерево), он в разы компактнее и потолка 1 ГБ не имеет.
3. **Второй проход по heap.** `LP_DEAD` становится `LP_UNUSED`, обновляется free space map.
4. **Cleanup индексов** и обновление статистики.
5. **Усечение хвоста файла**, если в конце пустые страницы. Нужна кратковременная ACCESS EXCLUSIVE; отключается через `vacuum_truncate`.
6. **Обновление `pg_class`**: `relpages`, `reltuples`, `relallvisible`, `relfrozenxid`, `relminmxid`; затем при возможности `datfrozenxid` в `pg_database` и усечение старых сегментов `pg_xact` и `pg_multixact`.

VACUUM берёт `SHARE UPDATE EXCLUSIVE`: DML работает параллельно, конфликтуют DDL и второй VACUUM.

Место операционной системе не возвращается, кроме пустого хвоста. Освобождённое пространство переиспользуется для новых версий той же таблицы через FSM. Сжать таблицу физически можно через `VACUUM FULL` или `CLUSTER` (полная перезапись под ACCESS EXCLUSIVE, нужно место на вторую копию) или сторонними `pg_repack` / `pg_squeeze`, которые делают это онлайн.

**Visibility map** хранит 2 бита на страницу: all-visible (все кортежи видны всем, мёртвых нет) и all-frozen. Используется для пропуска страниц вакуумом и для Index Only Scan. Любое изменение страницы сбрасывает биты, ставят их VACUUM и `COPY ... FREEZE`.

## 12. Autovacuum

Launcher раз в `autovacuum_naptime` (1 мин) запускает воркеров (`autovacuum_max_workers`, по умолчанию 3). Таблица вакуумится, когда:

```
n_dead_tup > autovacuum_vacuum_threshold (50)
           + autovacuum_vacuum_scale_factor (0.2) × reltuples
```

- С PG13 есть аналогичный триггер по вставкам (`autovacuum_vacuum_insert_threshold`, `..._insert_scale_factor`). До этого insert-only таблицы не вакуумились до anti-wraparound: VM не заполнялась, Index Only Scan ходил в heap, а потом приходил тяжёлый агрессивный вакуум по всей таблице.
- С PG18 `autovacuum_vacuum_max_threshold` (по умолчанию 100 млн) ограничивает порог сверху, чтобы на таблице в 10 млрд строк 20% не означали 2 млрд мёртвых версий.
- ANALYZE запускается по своему порогу.

**Троттлинг.** Чтение страницы из кэша стоит `vacuum_cost_page_hit` (1), с диска `vacuum_cost_page_miss` (2 с PG14), загрязнение `vacuum_cost_page_dirty` (20). Набрав `autovacuum_vacuum_cost_limit` (по умолчанию берётся `vacuum_cost_limit` = 200), воркер спит `autovacuum_vacuum_cost_delay` (2 мс с PG12, раньше 20 мс). Лимит делится между всеми активными воркерами, поэтому увеличение `autovacuum_max_workers` без увеличения cost limit автовакуум не ускоряет, только размазывает тот же бюджет.

Пороги настраиваются на уровне таблицы:

```sql
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_cost_limit = 2000
);
```

Обычный автовакуум уступает: если кто-то ждёт конфликтующую блокировку, он отменяется. Автовакуум против wraparound не уступает, и `ALTER TABLE` будет ждать его до конца.

Мониторинг: `pg_stat_user_tables` (`n_dead_tup`, `last_autovacuum`, `autovacuum_count`), `pg_stat_progress_vacuum`.

## 13. Wraparound

32 бита дают около 4,29 млрд значений. Сравнение xid идёт по модулю 2³²: `TransactionIdPrecedes(a, b)` вычисляет `(int32)(a - b) < 0`. Для любого xid примерно 2,1 млрд значений лежат в прошлом и столько же в будущем. Если у строки `xmin = 100`, а счётчик ушёл вперёд больше чем на 2³¹, xid 100 оказывается «в будущем», и строка, закоммиченная годы назад, перестаёт быть видимой. Данные на диске есть, но из выборок они исчезают. Это и называют wraparound data loss.

**Заморозка.** Закоммиченный кортеж, xmin которого старше горизонта, помечается как frozen и дальше считается видимым всем, без сравнения xid. До 9.4 xmin заменялся на 2; с 9.4 ставятся оба бита `XMIN_COMMITTED | XMIN_INVALID`, а исходный xmin сохраняется для отладки. Заодно обрабатывается xmax: старый lock-only или откатившийся xmax обнуляется, старые MultiXact заменяются.

`pg_class.relfrozenxid` гарантирует, что в таблице нет незамороженных xid старше этого значения. `pg_database.datfrozenxid` равен минимуму по таблицам базы. Минимум по всем базам определяет, сколько ещё можно выдать xid и какие сегменты `pg_xact` удалить. У каждой TOAST-таблицы свой `relfrozenxid`.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | кортежи старше этого возраста замораживаются, когда VACUUM посещает страницу |
| `vacuum_freeze_table_age` | 150 млн | при `age(relfrozenxid)` выше VACUUM становится агрессивным и читает все страницы, кроме all-frozen |
| `autovacuum_freeze_max_age` | 200 млн | при превышении автовакуум запускается принудительно, даже при `autovacuum = off`, и не уступает блокировкам |
| `vacuum_failsafe_age` | 1,6 млрд | PG14+: аварийный режим, снимается cost delay, пропускается очистка индексов, цель одна: продвинуть `relfrozenxid` |
| `vacuum_multixact_*` / `autovacuum_multixact_freeze_max_age` | 5 млн / 150 млн / 400 млн / 1,6 млрд | то же для MultiXactId |

Агрессивный режим нужен потому, что обычный VACUUM пропускает all-visible страницы, а на них могут лежать незамороженные кортежи. С PG15 VACUUM устанавливает `relfrozenxid` по самому старому реально увиденному xid, а не по порогу, но продвинуть его может, только если не пропустил ни одной страницы all-visible без all-frozen. PG16 добавил оппортунистическую заморозку: если pruning всё равно порождает full page image, страница замораживается целиком. PG18 добавил eager scanning: обычный VACUUM заранее сканирует часть all-visible страниц, чтобы заморозить их и разгрузить будущий агрессивный проход (`vacuum_max_eager_freeze_failure_rate`).

**Что происходит при приближении к краю:**

- За 40 млн xid до остановки каждая транзакция, получающая xid, выдаёт `WARNING: database "x" must be vacuumed within N transactions`.
- За 3 млн (в старых версиях за 1 млн) сервер отказывает в выдаче новых xid: `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение работает, любая запись падает.
- Лечение: сначала найти и убрать то, что держит горизонт (раздел 10), иначе VACUUM ничего не заморозит. Затем обычный `VACUUM` на таблицах с наибольшим `age(relfrozenxid)`. `VACUUM FULL` здесь вреден: он медленнее и требует места. Раньше документация предписывала single-user mode, сейчас рекомендует обычный режим.

Заморозка упирается в тот же горизонт, что и удаление. Если забытый слот репликации, prepared transaction или `idle in transaction` держат xmin, `age(datfrozenxid)` растёт, сколько бы VACUUM ни запускался. Большинство реальных инцидентов с wraparound происходят именно так, а не из-за медленного автовакуума.

Ещё одна ловушка: автовакуум не обрабатывает временные таблицы. Долгоживущая сессия с временной таблицей может довести базу до wraparound, и вакуумить такую таблицу может только сама сессия.

Мониторинг:

```sql
SELECT datname, age(datfrozenxid), mxid_age(datminmxid)
FROM pg_database
ORDER BY 2 DESC;

SELECT c.oid::regclass AS rel, c.relkind,
       age(c.relfrozenxid) AS xid_age,
       mxid_age(c.relminmxid) AS mxid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
WHERE c.relkind IN ('r', 't', 'm')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;
```

Алерт имеет смысл ставить на `age(datfrozenxid)` заметно выше `autovacuum_freeze_max_age`, например 500–700 млн: это значит, что принудительный автовакуум не справляется или что-то держит горизонт. Скорость расхода xid определяется числом пишущих транзакций и подтранзакций: вставка по одной строке в autocommit сжигает xid на каждую строку, батч тратит один.

## 14. Что из этого следует на практике

- Следить за горизонтом важнее, чем за настройками автовакуума: долгие транзакции, `idle in transaction`, слоты, prepared transactions.
- На больших таблицах опускать `autovacuum_vacuum_scale_factor` до 0,01–0,05 и поднимать `autovacuum_vacuum_cost_limit`; встроенные значения рассчитаны на скромное железо.
- Давать `maintenance_work_mem` / `autovacuum_work_mem` достаточно, чтобы индексы проходились один раз (до PG17 это особенно важно).
- Для горячих по UPDATE таблиц: понижать `fillfactor`, не индексировать часто меняющиеся колонки без необходимости, смотреть долю HOT.
- Мониторить `age(datfrozenxid)`, `mxid_age(datminmxid)` и `n_dead_tup`, а не ждать WARNING в логах.

## 08-english

> What's the practical difference between git rebase and git merge, and when should I pick each?

### real (1950 chars)

Merge сохраняет историю как была и добавляет merge-коммит. Rebase переписывает твои коммиты поверх новой базы, и история получается линейной.

**Что происходит на практике**

`git merge main` в feature-ветке создаёт коммит с двумя родителями. Твои коммиты остаются с прежними хешами, видно, когда и откуда ветка вливалась. Конфликты решаются один раз, в merge-коммите.

`git rebase main` берёт твои коммиты и применяет их заново поверх `main`. У каждого коммита появляется новый хеш. История выглядит так, будто ты начал работу с текущего `main`. Конфликты могут всплывать на каждом переигрываемом коммите отдельно.

**Последствия**

- После rebase уже запушенной ветки нужен `git push --force-with-lease`, и у всех, кто её стянул, история разъедется.
- С линейной историей проще работать с `git log`, `git bisect` и `git revert`: нет развилок и merge-коммитов.
- Merge честнее показывает, как шла работа, но при частом подтягивании `main` в ветку лог засоряется коммитами «Merge branch 'main' into feature».
- Rebase может тихо сломать промежуточные коммиты: каждый из них теперь стоит на базе, на которой его никто не запускал.

**Когда что брать**

Rebase:
- чтобы подтянуть свежий `main` в свою локальную или личную ветку перед PR;
- для чистки своих коммитов через `git rebase -i` (squash, fixup, переименование) до того, как их кто-то увидел;
- `git pull --rebase`, чтобы не плодить merge-коммиты при синхронизации с удалённой веткой.

Merge:
- для вливания готовой ветки в общую (`main`, `develop`), особенно если важно видеть границы фич;
- когда над веткой работают несколько человек;
- когда ветка уже опубликована и переписывать её нельзя.

Простое правило: rebase то, что есть только у тебя, merge то, что общее. Многие команды совмещают оба подхода: ветка ребейзится на `main` перед вливанием, а потом вливается через merge (`--no-ff`) или squash-merge, в зависимости от того, нужна ли в `main` вся история ветки или один коммит на фичу.

## 09-multistep

> надо на свежей ubuntu 24.04 поднять nginx с https через letsencrypt для домена example.com и проксировать на приложение на 127.0.0.1:8000. распиши по шагам

### real (3387 chars)

Понадобятся DNS-запись на сервер, nginx как reverse proxy и certbot с плагином nginx, который сам выпустит сертификат и пропишет HTTPS в конфиг.

### 0. DNS

A-запись `example.com` (и `www.example.com`, если нужен) должна указывать на IP сервера. Если есть IPv6, добавь AAAA, иначе удали её: Let's Encrypt проверяет по IPv6, если запись есть. Проверить:

```bash
dig +short example.com
dig +short www.example.com
```

### 1. Пакеты

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx certbot python3-certbot-nginx
```

### 2. Файрвол

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'   # 80 и 443
sudo ufw enable
sudo ufw status
```

`OpenSSH` разрешить до `enable`, иначе можно потерять доступ. Порт 8000 наружу не открывай.

### 3. Конфиг nginx (пока только HTTP)

```bash
sudo nano /etc/nginx/sites-available/example.com
```

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    client_max_body_size 20m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket, если приложению нужен
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        proxy_read_timeout 60s;
    }
}
```

Для `$connection_upgrade` нужен map в контексте `http`:

```bash
sudo tee /etc/nginx/conf.d/websocket-map.conf >/dev/null <<'EOF'
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
EOF
```

Если WebSocket не нужен, убери обе строки с `Upgrade`/`Connection` и этот файл не создавай.

### 4. Включить сайт

```bash
sudo ln -s /etc/nginx/sites-available/example.com /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
```

Проверка: `curl -I http://example.com` должен вернуть ответ приложения (или 502, если оно ещё не запущено; это значит, что nginx работает).

### 5. Сертификат

```bash
sudo certbot --nginx -d example.com -d www.example.com \
  --redirect -m you@example.com --agree-tos --no-eff-email
```

Certbot пройдёт HTTP-01 проверку, допишет в конфиг `listen 443 ssl`, пути к сертификатам и редирект с 80 на 443.

### 6. Автопродление

Пакет ставит systemd-таймер:

```bash
systemctl list-timers | grep certbot
sudo certbot renew --dry-run
```

Reload nginx после продления certbot с плагином `--nginx` делает сам.

### 7. Проверка

```bash
curl -I http://example.com     # 301 на https
curl -I https://example.com    # ответ приложения
sudo nginx -t
```

### 8. Со стороны приложения

- Слушать только `127.0.0.1:8000`, не `0.0.0.0`.
- Доверять заголовкам `X-Forwarded-*` от 127.0.0.1, чтобы приложение видело реальный IP клиента и схему `https` (в Django это `SECURE_PROXY_SSL_HEADER`, в uvicorn `--proxy-headers --forwarded-allow-ips=127.0.0.1`, в gunicorn `--forwarded-allow-ips`).
- Запускать его через systemd-юнит, чтобы поднималось после перезагрузки.

Если после шага 5 нужен HSTS, добавь в 443-блок `add_header Strict-Transport-Security "max-age=31536000" always;`, но только когда уверен, что HTTPS работает стабильно на всех поддоменах, которые попадут под заголовок.

## 10-followup

> а если это симлинк, который указывает на удалённый файл? что вернёт твоя проверка

### real (573 chars)

`-f` вернёт ложь. Она идёт по ссылке до цели, а цели нет, поэтому битый симлинк для неё выглядит как отсутствующий файл. `-e` ведёт себя так же.

Сам симлинк видит только `-L` (или синоним `-h`), он ссылку не разыменовывает. Битую ссылку можно отличить так:

```bash
if [ -L "$f" ] && [ ! -e "$f" ]; then
    echo "битый симлинк"
fi
```

Если нужно «есть хоть что-то по этому пути, включая битую ссылку», используйте `[ -e "$f" ] || [ -L "$f" ]`. Это важно, например, перед `ln -s` или созданием файла: `-e` скажет «нет», а запись упадёт или пойдёт по ссылке в чужое место.
