## 02-howto

> как в python прочитать jsonl построчно и пропустить битые строки, но залогировать номер строки

### baseline (2410 chars)

Генератор, который отдаёт валидные записи, а битые строки пропускает и пишет в лог с номером:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[dict[str, Any]]:
    """Yield JSON objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON object for each valid line.
    """
    # Binary mode so a single line with bad UTF-8 doesn't abort the whole read.
    with open(path, "rb") as f:
        for lineno, raw in enumerate(f, start=1):
            if not raw.strip():
                continue
            try:
                obj = json.loads(raw)
            except (json.JSONDecodeError, UnicodeDecodeError) as e:
                logger.warning("%s:%d: skipping malformed line: %s", path, lineno, e)
                continue
            if not isinstance(obj, dict):
                logger.warning(
                    "%s:%d: expected object, got %s", path, lineno, type(obj).__name__
                )
                continue
            yield obj
```

Использование:

```python
logging.basicConfig(level=logging.INFO)

for record in read_jsonl("data.jsonl"):
    ...
```

Что здесь важно:

- **`enumerate(f, start=1)`** даёт номер строки как в редакторе, начиная с 1.
- **Файл открывается в режиме `"rb"`.** `json.loads` принимает `bytes` и сам декодирует UTF-8. Если открыть файл в текстовом режиме, то одна строка с битой кодировкой выбросит `UnicodeDecodeError` прямо из цикла `for`, и чтение оборвётся целиком, а не пропустит одну строку.
- **Пустые строки пропускаются молча.** Обычно это хвостовой `\n` в конце файла, а не ошибка. Если пустые строки тоже нужно считать битыми, уберите эту проверку.
- **Проверка `isinstance(obj, dict)`** нужна, потому что строки `42` или `"abc"` являются валидным JSON, но, скорее всего, не тем, что вы ждёте. Если в файле допустимы любые JSON-значения, проверку можно убрать и поменять тип на `Iterator[Any]`.
- В лог попадает текст исключения. У `JSONDecodeError` там есть позиция внутри строки (`line 1 column 15 (char 14)`), что помогает найти место поломки.

Если нужно ещё и узнать количество пропущенных строк в конце, проще всего завести счётчик и вывести итог после цикла через `logger.info`. Могу показать вариант с ним.

### current (1632 chars)

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def iter_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid line.
    """
    with open(path, encoding="utf-8", errors="replace") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                logger.warning("%s:%d: invalid JSON (%s)", path, lineno, e.msg)
```

Использование:

```python
logging.basicConfig(level=logging.INFO)
for rec in iter_jsonl("data.jsonl"):
    ...
```

Пара нюансов:

- `errors="replace"` нужен, чтобы битая кодировка не роняла весь цикл с `UnicodeDecodeError`. Такая строка превратится в мусор с `\ufffd` и, скорее всего, отвалится на `json.loads`, то есть тоже залогируется. Если нужно ловить кодировку отдельно, читай файл в бинарном режиме (`"rb"`) и делай `line.decode("utf-8")` внутри того же `try`, добавив `UnicodeDecodeError` в `except`.
- Пустые строки молча пропускаются. Хочешь видеть их в логе, убери `continue` и логируй.
- `json.loads` спокойно примет `42` или `"foo"` как валидную строку. Если ждёшь только объекты, добавь проверку `isinstance(obj, dict)` и логируй остальное как битое.
- Если нужна статистика в конце, заведи счётчик пропущенных и выведи после цикла.

### baseline (5123 chars)

# Идемпотентность в HTTP API

## Что это

Операция **идемпотентна**, если повторное выполнение с теми же параметрами оставляет систему в том же состоянии, что и однократное. Ответ при этом может отличаться: первый `DELETE` вернёт `204`, второй `404`. Важно другое: состояние сервера после N вызовов такое же, как после одного.

Идемпотентность не равна «безопасности». **Safe**-методы вообще не меняют состояние (`GET`, `HEAD`, `OPTIONS`). Идемпотентные могут менять состояние, но повтор ничего не добавляет.

## Методы по RFC 9110

| Метод | Safe | Идемпотентен | Почему |
|---|---|---|---|
| `GET`, `HEAD`, `OPTIONS` | да | да | ничего не меняют |
| `PUT` | нет | да | «положи ресурс в такое состояние», и повтор даёт то же состояние |
| `DELETE` | нет | да | удалённое остаётся удалённым |
| `POST` | нет | **нет** | «создай ещё один», и каждый вызов создаёт новый |
| `PATCH` | нет | **не гарантируется** | `{"balance": 100}` идемпотентен, `{"op": "increment"}` нет |

Это контракт, а не магия. Если ваш `PUT` инкрементирует счётчик, он нарушает спецификацию, и клиенты, прокси и ретраи будут вести себя неправильно.

## Зачем это нужно: проблема ретраев

Сеть ненадёжна. Типичный сценарий:

```
Клиент ── POST /payments {amount: 100} ──▶ Сервер
                                          списал деньги
Клиент ◀──── ✗ таймаут / обрыв ────────── ответ потерялся
```

Клиент не знает, что произошло:
- запрос не дошёл до сервера;
- дошёл, но упал при обработке;
- обработался, но потерялся ответ.

Если ретраить, можно списать деньги дважды. Если не ретраить, платёж может так и не пройти. Для идемпотентных методов ответ простой: ретраим смело. Для `POST` нужен дополнительный механизм.

## Idempotency-Key

Клиент генерирует уникальный ключ (обычно UUID v4) **на одну логическую операцию** и шлёт его в заголовке:

```http
POST /payments HTTP/1.1
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 100, "currency": "RUB"}
```

При ретрае клиент отправляет **тот же ключ**. Сервер видит, что запрос уже был, и не выполняет операцию заново, а возвращает сохранённый результат.

Так `POST` становится идемпотентным, хотя по своей семантике он таким не является. Подход популяризировал Stripe, сейчас он есть в API PayPal, Adyen, многих банков и описан в IETF-драфте `draft-ietf-httpapi-idempotency-key-header`.

## Как это реализуется на сервере

```
1. Пришёл запрос с ключом K
2. Ищем K в хранилище (scope: ключ + клиент/аккаунт)
   ├─ не найден → атомарно записываем K со статусом "processing" и хешем тела,
   │              выполняем операцию, сохраняем ответ (статус + тело), "completed"
   ├─ найден, "completed", хеш тела совпадает → возвращаем сохранённый ответ
   ├─ найден, хеш тела НЕ совпадает → 422 (ключ переиспользован с другими данными)
   └─ найден, "processing" → 409 Conflict (параллельный дубль, пусть клиент повторит позже)
3. Через TTL (обычно 24 ч) ключ удаляется
```

На чём обычно ошибаются:

- **Гонка при проверке.** Последовательность «проверил, что ключа нет, потом вставил» без атомарности пропустит два параллельных дубля. Нужен `INSERT ... ON CONFLICT`, уникальный индекс или `SET NX` в Redis.
- **Атомарность с бизнес-операцией.** Если ключ лежит в Redis, а платёж в Postgres, между ними может случиться падение. Надёжнее хранить ключ в той же БД и в той же транзакции, что и сам эффект.
- **Проверка тела.** Без сравнения хеша ошибка клиента (тот же ключ для другого платежа) молча вернёт чужой результат.
- **Scope ключа.** Ключ уникален в рамках клиента или аккаунта, а не глобально. Иначе один клиент может получить ответ другого.
- **Что кешировать.** Успешные ответы и детерминированные ошибки (`4xx` валидации) сохраняют. Ответы `5xx` обычно не сохраняют, чтобы ретрай мог пройти.
- **Внешние побочные эффекты.** Если внутри вызывается сторонний платёжный шлюз, ему тоже нужно передавать idempotency key, иначе дубль возникнет уровнем ниже.

## Обязанности клиента

- Генерировать ключ **один раз на намерение пользователя**, а не на каждую HTTP-попытку. Самая частая ошибка: новый UUID внутри цикла ретраев сводит всю защиту на нет.
- Ретраить с экспоненциальной задержкой и jitter.
- Не переиспользовать ключ для другой операции.

## Альтернативы и смежные приёмы

- **Естественные ключи.** Если у операции есть бизнес-идентификатор (номер заказа клиента), достаточно уникального индекса по нему.
- **`PUT` с клиентским ID.** `PUT /orders/{client-generated-uuid}` идемпотентен по определению, и отдельный заголовок не нужен.
- **Условные запросы.** `If-Match` с `ETag` защищает от потерянных обновлений, но это другая задача: конкурентность, а не дубли.
- **Дедупликация в очередях.** В брокерах та же идея называется «exactly-once processing» и строится на at-least-once доставке плюс идемпотентный консьюмер.

## Коротко

Идемпотентность позволяет безопасно повторять запросы при сбоях сети. `GET`, `PUT` и `DELETE` идемпотентны по спецификации, `POST` нет. `Idempotency-Key` делает `POST` идемпотентным: клиент помечает операцию уникальным ключом, а сервер запоминает результат и при повторе отдаёт его, не выполняя операцию снова.

### current (3156 chars)

**Идемпотентность** означает, что повторный запрос оставляет сервер в том же состоянии, что и первый. Один раз отправил или пять, итог одинаковый.

По спеке HTTP (RFC 9110) идемпотентны `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`. Не идемпотентны `POST` и `PATCH`.

Идемпотентность касается состояния, а не ответа. Первый `DELETE /orders/42` вернёт 204, второй вернёт 404, но заказ в обоих случаях удалён. Это нормально.

Ещё её путают с безопасностью (safe). Safe методы вообще ничего не меняют (`GET`). `DELETE` меняет состояние, значит он не safe, но идемпотентен.

## Зачем нужен Idempotency-Key

Сеть ненадёжна. Клиент шлёт `POST /payments` и ловит таймаут. Возможны три исхода:

- запрос не дошёл;
- дошёл, но упал на сервере;
- дошёл и выполнился, а потерялся только ответ.

Клиент не знает, какой из них случился. Если не ретраить, платёж может потеряться. Если ретраить, деньги могут списаться дважды. С `PUT` и `DELETE` ретрай безопасен, с `POST` нет.

`Idempotency-Key` делает `POST` идемпотентным вручную. Клиент генерирует уникальный ключ (обычно UUID v4) на одну логическую операцию и шлёт его в заголовке:

```http
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

Сервер смотрит, видел ли он этот ключ раньше:

- ключ новый: выполняет операцию и сохраняет ключ вместе с ответом;
- ключ уже есть, операция завершена: отдаёт сохранённый ответ и ничего не выполняет заново;
- ключ есть, но первый запрос ещё обрабатывается: обычно 409 Conflict.

Подход популяризовал Stripe. В IETF есть черновик `draft-ietf-httpapi-idempotency-key-header`. Насколько я знаю, RFC он так и не стал, поэтому детали поведения у разных API отличаются.

## Где обычно косячат

**Ключ генерируется заново на каждый ретрай.** Тогда он бесполезен. Ключ создаётся один раз на операцию («оплатить заказ 42») и переиспользуется во всех попытках. Новая операция получает новый ключ.

**Нет атомарности.** Если сначала списать деньги, а потом записать ключ, то падение между этими шагами снова даёт дубль. Ключ и побочный эффект должны фиксироваться в одной транзакции. Если эффект во внешней системе, ключ нужно прокидывать туда же.

**Гонки.** Два одинаковых запроса пришли одновременно, оба проверили ключ, оба не нашли. Нужна блокировка или уникальный индекс, чтобы второй запрос упал на вставке.

**Тот же ключ, другое тело.** Это баг клиента. Надо хранить хэш тела рядом с ключом и при несовпадении отвечать ошибкой (обычно 422), а не молча отдавать старый ответ.

**Скоуп и TTL.** Ключ должен быть уникален в рамках клиента или аккаунта, иначе чужие ключи могут случайно совпасть. Хранить вечно не нужно: у Stripe, например, 24 часа. Ретраи за пределами этого окна уже будут считаться новыми запросами.

**Что сохранять.** Успешные ответы сохранять нужно. С 5xx решения разные. Если сохранить 5xx, клиент навсегда застрянет на ошибке. Если не сохранять, придётся гарантировать, что при ошибке побочный эффект откатился.

Короче, `Idempotency-Key` позволяет клиенту спокойно ретраить неидемпотентные операции, а сервер отвечает за то, чтобы операция выполнилась ровно один раз.

## 04-choice

> что взять для фоновых задач в небольшом fastapi проекте: celery, rq или arq? сервер один, задач ~1000 в день, редис уже есть

### baseline (2302 chars)

**Рекомендация: arq**, если код задач асинхронный (httpx, asyncpg, async SQLAlchemy и т.п.). Если задачи в основном синхронные, бери **RQ**. Celery для такого масштаба избыточен.

## Почему arq

- **Нативный asyncio.** Задачи — обычные `async def`, можно переиспользовать тот же async-код и клиенты, что в FastAPI. В Celery и RQ async-задачи придётся оборачивать в `asyncio.run()`, а это неудобно и мешает переиспользовать пулы соединений.
- **Лёгкий.** Одна зависимость поверх Redis, конфиг — класс `WorkerSettings` на десяток строк.
- **Всё нужное есть:** отложенный запуск (`_defer_by`, `_defer_until`), retry через `raise Retry(defer=...)`, cron-задачи, хранение результатов в Redis, дедупликация по `_job_id`.
- **1000 задач в день** — это меньше одной в минуту. Один воркер arq с `max_jobs=10` справится с большим запасом.

## Подводные камни arq

- **CPU-bound код блокирует event loop** и вместе с ним все остальные задачи воркера. Тяжёлое нужно выносить в `run_in_executor`.
- **Нет готового дашборда** уровня Flower или rq-dashboard. Мониторить придётся через логи или самописный эндпоинт.
- **Темп разработки.** Проект поддерживается небольшой командой и развивается медленно, в какой-то момент он фактически был в режиме поддержки. Какой у него статус на конец 2026, я точно не знаю. Перед выбором стоит посмотреть на активность репозитория и issues.

## Когда что-то другое

- **RQ** подходит, если задачи синхронные: pandas, синхронные SDK, CPU-нагрузка. Он очень простой и зрелый, есть rq-dashboard. По умолчанию запускает каждую задачу в отдельном форке процесса, что надёжно, но не бесплатно. Под Windows не работает.
- **Celery** нужен, если понадобятся сложные цепочки (chain, chord, group), rate limits, несколько очередей с приоритетами, другой брокер вроде RabbitMQ или Flower из коробки. Цена — громоздкая конфигурация и неудобная работа с async.
- **taskiq** стоит упомянуть как альтернативу arq. Он тоже async-first, имеет интеграцию с FastAPI-зависимостями и развивается активнее. Менее обкатан, чем RQ или Celery.
- **Встроенный `BackgroundTasks` FastAPI** подойдёт, если задачи короткие и их потеря при рестарте не страшна. Тогда отдельная очередь не нужна вовсе.

Если покажешь, что именно делают задачи (I/O или CPU, нужны ли retry, cron, результаты), могу сказать точнее.

### current (1535 chars)

При ~1000 задач в день (меньше одной в минуту) нагрузку вытянет любой из трёх. Выбирать стоит по тому, какой код у тебя в задачах.

**arq**, если задачи async: ходят в httpx, async ORM, другие сервисы. Это самый естественный вариант для FastAPI. Те же async-функции, никаких `asyncio.run` внутри sync-воркера. Ретраи, отложенный запуск и cron есть из коробки, зависит только от редиса, кода мало. Минус: проект живёт силами одного мейнтейнера, и, насколько я помню, в README висела пометка про maintenance mode. Свежий статус я не проверял, глянь репо перед тем, как тащить. Для твоего масштаба это не критично, API там маленький и стабильный.

**RQ**, если задачи синхронные или тяжёлые по CPU: pandas, генерация PDF, sync SQLAlchemy. Простой, зрелый, есть нормальный дашборд (rq-dashboard). Каждая задача по умолчанию форкается, это даёт изоляцию, но на коротких задачах добавляет оверхед. Для async-кода неудобен.

**Celery** тут оверкилл. Много конфигурации, много движущихся частей, своя магия с сериализацией и acks. Нужен, когда есть сложные цепочки задач (chord/group), несколько брокеров, много воркеров на разных машинах. У тебя ничего из этого нет.

Если код в основном async, бери arq. Если sync, бери RQ. Вне этих трёх есть ещё taskiq: тот же async, живее поддерживается, но его надо отдельно оценить.

И проверь, нужна ли очередь вообще. Если задачи короткие и потерять их при рестарте не страшно, встроенных `BackgroundTasks` из FastAPI может хватить без всякого воркера.

## Причина

Пул и `main()` работают в **разных event loop'ах**:

1. При импорте модуля `asyncio.get_event_loop()` создаёт loop A, и в нём через `run_until_complete` создаётся пул. Внутренние futures пула и сокеты соединений привязываются к loop A.

# MVCC в PostgreSQL: подробный разбор

Разбор идёт от устройства строки на диске к снапшотам, правилам видимости, VACUUM и wraparound. Где поведение зависит от версии PostgreSQL, я это указываю.

---

## 1. Основная идея

PostgreSQL **не перезаписывает строку на месте**. Любое изменение создаёт новую **версию строки** (tuple):

- `INSERT` создаёт версию.
- `DELETE` помечает существующую версию как удалённую. Физически она остаётся на странице.
- `UPDATE` делает то же, что `DELETE` + `INSERT`: старая версия помечается удалённой, рядом создаётся новая.

Каждая транзакция смотрит на данные через **снапшот**, то есть через правило «какие транзакции для меня уже завершились». По этому правилу она сама решает, какую из версий видеть. Отсюда главное свойство: **читатели не блокируют писателей, писатели не блокируют читателей**.

Цена такого подхода в том, что старые версии копятся в таблице. Убирать их кто-то должен, и этим занимается VACUUM.

Undo-лога, как в Oracle или InnoDB, в PostgreSQL нет. Старые версии лежат прямо в heap, вперемешку с живыми. Почти все особенности PostgreSQL (bloat, VACUUM, HOT, wraparound) следуют из этого решения.

---

## 2. Идентификаторы транзакций (XID)

### 2.1. Что такое XID

- 32-битное беззнаковое число, растёт монотонно.
- **Выдаётся лениво**, только при первой записи: INSERT/UPDATE/DELETE, `SELECT FOR UPDATE`, DDL. Читающая транзакция получает лишь **virtual xid** (`backendID/localXID`) и счётчик XID не расходует. Это важно для wraparound: скорость «старения» базы определяется числом **пишущих** транзакций, а не всех подряд.
- Особые значения:
  - `0` — `InvalidTransactionId`;
  - `1` — `BootstrapTransactionId`;
  - `2` — `FrozenTransactionId`;
  - обычные XID начинаются с `3`.
- Внутри сервера есть 64-битный `FullTransactionId`: эпоха плюс 32-битный XID. Наружу он доступен как тип `xid8` через `pg_current_xact_id()`. **На диске в заголовке строки XID по-прежнему 32-битный**, и проблема wraparound возникает именно поэтому.

### 2.2. Статус транзакции: pg_xact (бывший pg_clog)

На каждую транзакцию отводится 2 бита: `IN_PROGRESS`, `COMMITTED`, `ABORTED`, `SUB_COMMITTED`. Данные лежат в SLRU-кэше и в файлах `pg_xact/`.

Подтранзакции (`SAVEPOINT`, блоки `EXCEPTION` в PL/pgSQL) получают собственные XID. Связь «подтранзакция → родитель» хранится в `pg_subtrans`.

### 2.3. Сравнение XID: модульная арифметика

XID сравниваются по кругу:

```c
/* упрощённо, TransactionIdPrecedes */
return (int32)(id1 - id2) < 0;
```

Для любого XID примерно 2³¹ (≈2,1 млрд) значений считаются «прошлым», а другие 2³¹ — «будущим». Подробнее об этом в разделе про wraparound.

## 3. Заголовок версии строки (HeapTupleHeader)

Каждая версия строки несёт примерно 23 байта служебных данных:

| Поле | Смысл |
|---|---|
| `t_xmin` | XID транзакции, создавшей версию |
| `t_xmax` | XID транзакции, удалившей или заблокировавшей версию (0, если таких не было) |
| `t_cid` | command id внутри транзакции: cmin, cmax или combo cid |
| `t_ctid` | ссылка на **следующую** версию той же строки (или на себя, если версия последняя) |
| `t_infomask` | флаги: hint bits, тип блокировки, multixact и т. п. |
| `t_infomask2` | число атрибутов, `HEAP_HOT_UPDATED`, `HEAP_ONLY_TUPLE`, `HEAP_KEYS_UPDATED` |

Посмотреть на это можно своими глазами:

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
CREATE TABLE t(id int, v text);
INSERT INTO t VALUES (1, 'a');
UPDATE t SET v = 'b' WHERE id = 1;

SELECT xmin, xmax, ctid, * FROM t;   -- видна только актуальная версия

SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid,
       t_infomask::bit(16), t_infomask2::bit(16)
FROM heap_page_items(get_raw_page('t', 0));
```

На странице окажутся обе версии. У первой `t_xmax` равен XID апдейта, а `t_ctid = (0,2)`. У второй `t_xmin` равен тому же XID, `t_xmax = 0`, `t_ctid = (0,2)`.

**Нюанс:** ненулевой `xmax` **не означает**, что строка удалена. Он бывает ненулевым у вполне видимой строки в трёх случаях:
- транзакция, удалявшая строку, откатилась;
- на строку брали блокировку (`SELECT FOR UPDATE/SHARE`), см. раздел 7;
- `xmax` содержит MultiXactId.

## 4. Снапшот

### 4.1. Из чего он состоит

Снапшот строится функцией `GetSnapshotData()` по данным ProcArray, общей таблицы активных бэкендов.

| Поле | Значение |
|---|---|
| `xmin` | наименьший XID, активный в момент снятия снапшота. Всё, что `< xmin`, уже завершено (коммитом или откатом) |
| `xmax` | `latestCompletedXid + 1`, первый ещё «не случившийся» XID. Всё, что `>= xmax`, для снапшота относится к будущему |
| `xip[]` | список XID из диапазона `[xmin, xmax)`, которые были активны на момент снапшота |
| `subxip[]` | активные подтранзакции (`suboverflowed`, если кэш переполнился) |
| `curcid` | текущий command id, нужен для видимости собственных изменений |

Текущий снапшот можно увидеть так: `SELECT pg_current_snapshot();`. Пример вывода: `100:105:100,102`.

### 4.2. Как XID проверяется против снапшота (`XidInMVCCSnapshot`)

```
if xid <  snap.xmin  → транзакция завершена до снапшота; дальше статус берётся из pg_xact
if xid >= snap.xmax  → транзакция «в будущем», её изменения не видны
if xid in snap.xip   → транзакция была активна, её изменения не видны
иначе                → транзакция завершена; статус берётся из pg_xact
```

Ключевая мысль: **снапшот не хранит список закоммиченных транзакций.** Он хранит только границы и список активных. Всё прочее вычисляется через pg_xact.

### 4.3. Когда снимается снапшот (уровни изоляции)

- **Read Committed** (по умолчанию): новый снапшот на **каждый оператор**. Поэтому два одинаковых SELECT внутри одной транзакции могут вернуть разные данные.
- **Repeatable Read**: один снапшот на всю транзакцию. Он снимается **при первом запросе, а не при `BEGIN`**. Это частая ловушка: `BEGIN ISOLATION LEVEL REPEATABLE READ; ... pause ...; SELECT` зафиксирует данные на момент SELECT.
- **Serializable**: тот же снапшот, что в RR, плюс SSI (Serializable Snapshot Isolation). SSI ставит предикатные блокировки `SIREAD`, отслеживает rw-зависимости между транзакциями и откатывает одну из них при обнаружении «опасной структуры», то есть двух подряд rw-рёбер в цикле. Возможны ложноположительные откаты.
- **Read Uncommitted** в PostgreSQL ведёт себя как Read Committed. Грязного чтения нет вообще.

Снапшотом можно поделиться: `pg_export_snapshot()` в одной транзакции и `SET TRANSACTION SNAPSHOT '...'` в другой. Так работает параллельный `pg_dump -j`.

### 4.4. Стоимость снапшота

`GetSnapshotData()` проходит по ProcArray. При тысячах соединений это заметно. В PG14 эту функцию серьёзно переработали: данные о XID лежат плотными массивами, а снапшот переиспользуется, если с прошлого раза не было коммитов (`xactCompletionCount`). Тем не менее огромное число соединений без пулера остаётся плохой идеей, в том числе из-за этого.

## 5. Правила видимости

Упрощённая логика `HeapTupleSatisfiesMVCC()`.

### 5.1. Проверка xmin: видна ли версия как созданная

```
if xmin — моя транзакция (или моя подтранзакция):
    if cmin >= curcid → не видна (вставлена этой же или более поздней командой)
    иначе переходим к проверке xmax
elif XidInMVCCSnapshot(xmin) → не видна (создатель ещё был активен)
elif xmin committed (pg_xact) → видна как созданная
else (aborted / crashed)      → не видна
```

### 5.2. Проверка xmax: не удалена ли версия

```
if xmax invalid / только блокировка (LOCK_ONLY) → видна
if xmax — моя транзакция:
    cmax >= curcid → видна (удалена командой, которая ещё «не случилась»)
    иначе          → не видна
if XidInMVCCSnapshot(xmax) → видна (удаляющий ещё не завершился для меня)
if xmax committed          → не видна
else (aborted)             → видна
```

### 5.3. Почему порядок проверок важен

Сначала проверяется снапшот, и только потом pg_xact. Причина в порядке действий при коммите: транзакция сначала пишет статус в pg_xact, а затем убирает себя из ProcArray. Если смотреть в pg_xact первым, можно увидеть `COMMITTED` у транзакции, которая для твоего снапшота ещё активна. Это нарушило бы изоляцию.

Для оператора, который не является снапшотным чтением (например, проверка уникальности), используется отдельная проверка `TransactionIdIsInProgress()`, тоже перед pg_xact.

### 5.4. Command ID: cmin, cmax, combo cid

Внутри одной транзакции видимость определяется номером команды. Именно поэтому `UPDATE t SET x = x + 1` не зацикливается на только что вставленных версиях (так называемая Halloween problem): новая версия имеет `cmin = текущей команде` и для этой же команды невидима.

Под `cmin` и `cmax` в заголовке есть только одно поле. Если одна транзакция и вставила, и удалила строку, туда пишется **combo cid**: индекс в локальной (backend-local) хэш-таблице пар `(cmin, cmax)`. Другим транзакциям эти значения не нужны: для них чужая незакоммиченная транзакция целиком невидима.

## 6. Hint bits: почему SELECT пишет на диск

Ходить в pg_xact за каждой строкой дорого. Поэтому, как только статус `xmin` или `xmax` выяснен окончательно, бэкенд кэширует его прямо в заголовке строки флагами из `t_infomask`:

- `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID`
- `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID`

Нюансы:

1. **Хинты выставляет первый, кто прочитал строку**, причём даже обычный `SELECT`. Страница становится dirty. Отсюда эффект «после массовой загрузки первый SELECT медленный и генерирует запись». Чтобы избежать этого, после загрузки стоит сделать `VACUUM` (или `VACUUM FREEZE`), а при загрузке использовать `COPY ... FREEZE`.
2. Сами по себе хинты в WAL не пишутся. Но при включённых `data_checksums` или `wal_log_hints = on` первая модификация страницы после чекпоинта порождает **full page image** в WAL. Чтение тогда начинает генерировать WAL.
3. При `synchronous_commit = off` хинт нельзя ставить, пока WAL не сброшен на диск дальше LSN коммит-записи. Иначе после краха на странице окажется «committed» у транзакции, которой фактически нет. Это проверяется в `SetHintBits()`.
4. Хинт «in progress» не кэшируется: этот статус временный.

## 7. Блокировки строк тоже живут в xmax

В PostgreSQL нет таблицы блокировок строк в памяти, иначе она переполнялась бы на миллионах строк. Блокировка записывается прямо в строку:

- `SELECT ... FOR UPDATE` пишет свой XID в `xmax` и ставит `HEAP_XMAX_LOCK_ONLY` и `HEAP_XMAX_EXCL_LOCK`. Это физическая модификация страницы, и транзакция получает настоящий XID.
- Уровни блокировок: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`. Обычный `UPDATE`, не трогающий ключевые колонки, берёт `NO KEY UPDATE`. Он совместим с `KEY SHARE`, которую берут проверки внешних ключей. Это сильно снижает конфликты FK.
- **MultiXact.** Если строку держат сразу несколько транзакций (например, несколько `FOR SHARE`, или `KEY SHARE` плюс апдейтер), в `xmax` пишется MultiXactId (`HEAP_XMAX_IS_MULTI`). Это ссылка в `pg_multixact/offsets` и `pg_multixact/members`. MultiXact имеет собственное 32-битное пространство и **собственный wraparound** (см. раздел 13).
- Ожидание блокировки устроено так: тот, кто наткнулся на чужой `xmax` от активной транзакции, ждёт на **блокировке XID этой транзакции** (каждая транзакция держит эксклюзивный lock на собственный XID). В `pg_locks` это видно как `locktype = transactionid`.

## 8. Конкурирующие UPDATE

Пусть T1 и T2 одновременно обновляют одну строку, и T1 успела первой.

**Read Committed.** T2 ждёт завершения T1.
- Если T1 откатилась, T2 обновляет исходную версию.
- Если T1 закоммитилась, T2 идёт по цепочке `t_ctid` к новейшей версии и **заново проверяет WHERE** на ней. Этот механизм называется EvalPlanQual. Если условие всё ещё выполняется, T2 обновляет новую версию.
- Отсюда известные аномалии RC: часть оператора работает по старому снапшоту, часть по новой версии строки. Например, `UPDATE ... SET balance = balance - 100 WHERE balance >= 100` проверит условие на новой версии, а вот подзапросы в том же операторе видят старый снапшот.

**Repeatable Read и Serializable.** Если T1 закоммитилась, T2 получает `ERROR: could not serialize access due to concurrent update`. Приложение обязано уметь повторять транзакцию.

## 9. HOT: Heap-Only Tuples

Без оптимизаций каждый UPDATE создаёт новую версию, а значит, новую запись **в каждом индексе**: индекс указывает на конкретный TID `(page, offset)`. Это дорого.

**HOT-обновление** применяется при двух условиях:
1. не изменилась ни одна колонка, входящая в индексы (с PG16 колонки только BRIN-индексов не мешают HOT);
2. новая версия помещается на **ту же страницу**.

Тогда новая версия получает флаг `HEAP_ONLY_TUPLE`, старая получает `HEAP_HOT_UPDATED`, и **в индексы ничего не пишется**. Индекс по-прежнему указывает на корень HOT-цепочки, а сканирование идёт по `t_ctid` внутри страницы.

**Page pruning** (`heap_page_prune`) работает «мимоходом», без VACUUM. Когда бэкенд читает страницу, на которой мало места (заполнена больше чем примерно на `max(fillfactor, 90%)`), он может вычистить мёртвые версии HOT-цепочек внутри страницы. Корневой line pointer превращается в `LP_REDIRECT` на живую версию, место от мёртвых освобождается. Line pointers, на которые ссылаются индексы, при этом остаются: их может освободить только VACUUM вместе с чисткой индексов.

Практические выводы:
- `fillfactor = 70–90` на часто обновляемых таблицах оставляет место для HOT.
- Не индексируйте лишнего: каждый индекс по обновляемой колонке убивает HOT.
- Доля HOT видна так: `pg_stat_user_tables.n_tup_hot_upd / n_tup_upd`.

## 10. Индексы и видимость

**В индексах нет информации о видимости**, то есть нет xmin и xmax. Поэтому:

- Index Scan всегда ходит в heap, чтобы проверить видимость.
- **Index Only Scan** может не ходить в heap, если страница помечена в **visibility map** как all-visible: все строки на ней видимы всем транзакциям. VM поддерживается VACUUM'ом. Без регулярного VACUUM index-only scan деградирует до обычного (в `EXPLAIN ANALYZE` смотрите `Heap Fetches`).
- B-tree помечает записи, указывающие на заведомо мёртвые строки, как `LP_DEAD` (killed tuples) прямо при сканировании и потом может их вычистить. Начиная с PG14 есть **bottom-up deletion**: перед сплитом страницы индекса B-tree пытается удалить дубликаты-версии, порождённые не-HOT апдейтами.

## 11. Горизонт удаления (xmin horizon)

Мёртвую версию можно физически удалить, только если её **не может увидеть ни один существующий или будущий снапшот**. Формально это значит, что `xmax` закоммичен и старше **горизонта**. Горизонт вычисляется как минимум из:

- `xmin` всех активных снапшотов во всех бэкендах (`pg_stat_activity.backend_xmin`) и XID активных транзакций (`backend_xid`);
- `xmin` и `catalog_xmin` **слотов репликации** (`pg_replication_slots`);
- `xmin`, присылаемого репликами при `hot_standby_feedback = on`;
- **подготовленных транзакций** (`pg_prepared_xacts`, 2PC).

Начиная с PG14 горизонты считаются раздельно: для каталога, для обычных таблиц, для временных таблиц, с учётом базы данных. Но долгоживущая транзакция в **любой** базе кластера всё равно влияет на shared-каталоги, а слоты влияют на всё.

### Кто держит горизонт

1. **Долгие транзакции**, особенно `idle in transaction`. Приложение открыло транзакцию и ушло думать. Лечится `idle_in_transaction_session_timeout`.
2. **Долгие запросы**: аналитика, `pg_dump` на RR-снапшоте.
3. **Брошенный слот репликации.** Это ещё и неограниченный рост WAL; частично защищает `max_slot_wal_keep_size`.
4. **Забытые prepared transactions.** Они переживают рестарт!
5. **`hot_standby_feedback = on`** с долгими запросами на реплике.

Диагностика:

```sql
-- бэкенды, держащие горизонт
SELECT pid, datname, usename, state, backend_xid, backend_xmin,
       age(backend_xmin) AS xmin_age, xact_start, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL OR backend_xid IS NOT NULL
ORDER BY greatest(age(backend_xmin), age(backend_xid)) DESC;

-- слоты
SELECT slot_name, active, xmin, catalog_xmin,
       age(xmin) AS xmin_age, age(catalog_xmin) AS catalog_xmin_age
FROM pg_replication_slots;

-- 2PC
SELECT gid, prepared, owner, database, age(transaction)
FROM pg_prepared_xacts;
```

Пока горизонт стоит, VACUUM отрабатывает, но ничего не удаляет. В `VACUUM VERBOSE` это видно по строке `dead row versions cannot be removed yet`, в логах autovacuum — по растущему `removable cutoff` / `oldest xmin` age.

## 12. VACUUM

### 12.1. Что он делает

1. **Удаляет мёртвые версии**, которые старше горизонта, и освобождает место для повторного использования внутри таблицы.
2. **Чистит индексы** от ссылок на удалённые строки.
3. **Обновляет visibility map**: биты all-visible и all-frozen.
4. **Обновляет free space map (FSM)**, чтобы INSERT и UPDATE знали, куда писать.
5. **Замораживает** старые версии. Это защита от wraparound, подробнее в разделе 13.
6. **Сдвигает `relfrozenxid` и `relminmxid`** таблицы, а затем `datfrozenxid` базы. Это позволяет обрезать pg_xact и pg_multixact.
7. Обновляет `reltuples` и `relpages`. Статистику распределений собирает не он, а `ANALYZE`.

### 12.2. Фазы обычного VACUUM

```
1. Сканирование heap.
   Страницы, помеченные all-visible в VM, пропускаются (кроме aggressive-режима).
   На каждой странице выполняется pruning; TID мёртвых строк копятся в памяти,
   при необходимости строки замораживаются.
2. Vacuum indexes.
   Каждый индекс полностью сканируется (для B-tree), ссылки на собранные TID удаляются.
3. Vacuum heap.
   Line pointers удалённых строк становятся LP_UNUSED.
   Если память под TID кончилась, шаги 2–3 повторяются циклом.
4. Cleanup индексов, обновление FSM/VM/pg_class.
5. Truncate.
   Если в хвосте файла пустые страницы, файл обрезается.
   Это единственный случай, когда обычный VACUUM возвращает место ОС.
   Нужен кратковременный ACCESS EXCLUSIVE lock, который может мешать репликам.
```

Нюансы:
- Память под TID задаётся `maintenance_work_mem` (для autovacuum — `autovacuum_work_mem`). До PG17 был жёсткий потолок 1 ГБ и плоский массив, так что на больших таблицах индексы сканировались несколько раз. В PG17 появился TidStore на radix tree: он намного компактнее, и лимита в 1 ГБ больше нет.
- Обычный VACUUM берёт `SHARE UPDATE EXCLUSIVE` и не мешает DML.
- `VACUUM FULL` **переписывает таблицу** целиком под `ACCESS EXCLUSIVE` и требует до двух объёмов таблицы на диске. Для боевых систем обычно лучше `pg_repack` или `pg_squeeze`.
- Опции: `INDEX_CLEANUP off` (быстро, но индексы не чистятся), `PARALLEL n` (параллельная чистка индексов, только ручной VACUUM), `SKIP_LOCKED`, `PROCESS_TOAST`, `BUFFER_USAGE_LIMIT` (PG16).
- Таблица `TOAST` вакуумится отдельно, у неё свои `relfrozenxid` и мёртвые строки.

### 12.3. Autovacuum

Таблица попадает в очередь, когда:

```
n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples
             (50)                         (0.2)
```

Дополнительные триггеры:
- С PG13 есть порог по вставкам: `autovacuum_vacuum_insert_threshold` / `_scale_factor`. Он нужен, чтобы insert-only таблицы получали VM и заморозку.
- В PG18 добавили `autovacuum_vacuum_max_threshold`, верхнюю границу порога. Иначе `0.2 * 1 млрд строк` означало бы, что VACUUM придёт только после 200 млн мёртвых строк.
- Принудительный запуск по возрасту `relfrozenxid` (см. раздел 13).

Типичные проблемы и настройки:
- `scale_factor = 0.2` слишком велик для больших таблиц. Его настраивают пер-табличным `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01)`.
- Throttling: `autovacuum_vacuum_cost_limit` / `_cost_delay`. Дефолты консервативны. С PG12 `cost_delay` равен 2 мс, но на быстрых дисках лимит часто поднимают.
- `autovacuum_max_workers` (по умолчанию 3) — это число воркеров на весь кластер, а cost limit делится между ними. Если добавить воркеров без увеличения лимита, каждый станет медленнее.
- Обычный autovacuum **уступает** блокировку: если кому-то нужен конфликтующий lock (например, DDL), воркер отменяется. Анти-wraparound autovacuum так не делает (см. раздел 13).

Мониторинг: `pg_stat_user_tables` (`n_dead_tup`, `last_autovacuum`, `autovacuum_count`), `pg_stat_progress_vacuum`, `log_autovacuum_min_duration = 0` (или небольшой порог) в логах. Реальный bloat оценивают через `pgstattuple`.

## 13. Wraparound и заморозка

### 13.1. Проблема

XID 32-битные и сравниваются по модулю 2³². Для текущей транзакции N всё, что лежит в пределах примерно 2³¹ «позади», считается прошлым, а остальное — будущим.

Пусть строка вставлена транзакцией 100 и с тех пор не трогалась. Когда счётчик уйдёт вперёд больше чем на 2³¹, её `xmin = 100` внезапно окажется «в будущем», и **строка станет невидимой**. Данные физически на месте, но для всех запросов их больше нет. Это и есть wraparound. Задача PostgreSQL — не допустить его любой ценой, вплоть до остановки записи.

### 13.2. Решение: freeze

Если `xmin` строки достаточно стар и закоммичен, VACUUM помечает её как **замороженную**: «видна всем, всегда, независимо от сравнения XID».

- До 9.4 `xmin` физически заменялся на `FrozenTransactionId = 2`.
- С 9.4 ставится комбинация флагов `HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID` (= `HEAP_XMIN_FROZEN`), а исходный `xmin` сохраняется для отладки и форензики.

Вместе с этим VACUUM замораживает и `xmax`. Если там стоит старый MultiXact или XID только блокировки, он заменяется или очищается.

### 13.3. Возраст и счётчики

- `pg_class.relfrozenxid` — гарантия «все XID в таблице не старше этого значения» (кроме замороженных).
- `pg_database.datfrozenxid` — минимум по таблицам базы.
- `age(xid)` — сколько транзакций прошло с этого XID.

```sql
SELECT datname, age(datfrozenxid) AS xid_age, mxid_age(datminmxid) AS mxid_age
FROM pg_database ORDER BY xid_age DESC;

SELECT c.oid::regclass AS rel, age(c.relfrozenxid) AS xid_age,
       mxid_age(c.relminmxid) AS mxid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;
```

Когда `datfrozenxid` сдвигается вперёд, сегменты pg_xact старше минимального `datfrozenxid` по кластеру удаляются. Поэтому заморозка нужна ещё и для того, чтобы pg_xact не рос бесконечно.

### 13.4. Параметры и уровни эскалации

Значения по умолчанию:

| Параметр | Дефолт | Что делает |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | строки моложе этого VACUUM не замораживает. Смысл в том, что их, вероятно, ещё обновят, и заморозка пропадёт впустую |
| `vacuum_freeze_table_age` | 150 млн | если `age(relfrozenxid)` больше этого значения, VACUUM становится **aggressive**: сканирует все страницы, не помеченные all-frozen в VM, а не только не all-visible |
| `autovacuum_freeze_max_age` | 200 млн | при превышении autovacuum запускается **принудительно**, даже при `autovacuum = off` для таблицы или кластера. В `pg_stat_activity` это видно как `autovacuum: VACUUM ... (to prevent wraparound)` |
| `vacuum_failsafe_age` (PG14+) | 1,6 млрд | аварийный режим: VACUUM отключает cost-throttling и пропускает чистку индексов, лишь бы быстрее сдвинуть `relfrozenxid` |

У MultiXact есть аналогичные параметры: `vacuum_multixact_freeze_min_age`, `vacuum_multixact_freeze_table_age`, `autovacuum_multixact_freeze_max_age` (по умолчанию 400 млн) и `vacuum_multixact_failsafe_age`. Кроме того, принудительный VACUUM может запуститься из-за **переполнения пространства members**, а не только из-за возраста ID.

Последние рубежи (значения для современных версий; в старых они были меньше):
- Примерно за **40 млн** транзакций до точки невозврата в лог и клиентам идут предупреждения `WARNING: database "x" must be vacuumed within N transactions`.
- Примерно за **3 млн** сервер **перестаёт выдавать новые XID**: `ERROR: database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение работает, запись нет. Это фактически авария.

### 13.5. Нюансы, о которые спотыкаются

1. **Анти-wraparound autovacuum не уступает блокировки.** Ваш `ALTER TABLE` (или любой DDL) встанет в очередь за ним, а за DDL встанут все остальные запросы к таблице. Классический сценарий внезапного «повисла таблица». Отменять такой VACUUM вручную можно, но он запустится снова, а возраст продолжит расти.
2. **Он может прийти в самый неудобный момент** и читать всю большую таблицу целиком. Поэтому на больших таблицах лучше делать плановый `VACUUM (FREEZE)` (или просто VACUUM с более ранним aggressive-порогом) в спокойное время, а не ждать 200 млн.
3. **Insert-only таблицы** до PG13 вообще не вакуумились по мёртвым строкам (их нет), и затем на них приходил гигантский анти-wraparound VACUUM. С PG13 их обрабатывает порог по вставкам.
4. **Бит all-frozen в VM** (с 9.6) позволяет aggressive VACUUM пропускать уже замороженные страницы. До 9.6 приходилось перечитывать всю таблицу.
5. **Оппортунистическая заморозка.** С PG16 VACUUM замораживает всю страницу, если при pruning всё равно пишется FPI (дополнительной записи почти не будет). В PG18 появилась «eager»-заморозка части all-visible страниц в обычном (не aggressive) VACUUM: `vacuum_max_eager_freeze_failure_rate`. Цель обоих механизмов — размазать стоимость заморозки и не копить её до aggressive-прохода.
6. **Горизонт мешает и заморозке.** Строку нельзя заморозить, пока её `xmin` не старше горизонта удаления. Транзакция, висящая неделю, блокирует не только чистку мусора, но и защиту от wraparound. В логах VACUUM видно, что `relfrozenxid` не двигается.
7. **Временные таблицы autovacuum не обрабатывает.** Сессия, которая держит temp-таблицу очень долго, может задрать `datfrozenxid`. Брошенные temp-таблицы от упавших сессий autovacuum умеет удалять.
8. **Подтранзакции тоже расходуют XID**, если внутри что-то пишется. PL/pgSQL-цикл с `EXCEPTION` на каждой итерации сжигает XID пачками.
9. **Восстановление после остановки записи.** В современных версиях не нужно идти в single-user mode (раньше это была стандартная рекомендация, теперь документация прямо её отговаривает). Правильная последовательность:
   1. найти и убрать то, что держит горизонт (prepared transactions, слоты, долгие сессии);
   2. запустить обычный `VACUUM`: он сам XID не потребляет. Начинать стоит с самых старых таблиц, например `vacuumdb --all --min-xid-age=...`, можно с `INDEX_CLEANUP off` для скорости;
   3. **не делать** `VACUUM FULL` и прочее, что требует XID.

### 13.6. А 64-битные XID?

Внутри давно есть `FullTransactionId`, а `xid8` доступен в SQL. Но в формате страницы XID остаётся 32-битным, ведь расширение заголовка каждой строки стоит места на диске. Патчи про 64-битные XID на диске годами обсуждаются; насколько я знаю, в основную ветку они не вошли, поэтому проблема wraparound по-прежнему актуальна. Если для вас это критично, проверьте состояние в свежем релизе: здесь я могу отставать от актуального положения дел.

## 14. Прочие нюансы

- **Подтранзакции и переполнение кэша.** В PGPROC кэшируется до 64 XID подтранзакций (`PGPROC_MAX_CACHED_SUBXIDS`). Если их больше, снапшот получает `suboverflowed = true`, и проверки видимости начинают ходить в `pg_subtrans`. Это SLRU с известными проблемами конкурентности, и на нагруженных системах всё может обвалиться по производительности. Особенно опасно на репликах. С PG17 размеры SLRU настраиваются (`subtransaction_buffers` и др.), но лучше просто не плодить сотни SAVEPOINT'ов в долгой транзакции.
- **Hot standby.** Реплика строит снапшоты из `KnownAssignedXids`, восстановленных по WAL. VACUUM на мастере может удалить строки, нужные запросу на реплике. Тогда реплика либо ждёт (`max_standby_streaming_delay`), либо отменяет запрос: `canceling statement due to conflict with recovery`. `hot_standby_feedback` устраняет конфликт, но переносит горизонт реплики на мастер, и мастер начинает пухнуть.
- **DDL не полностью MVCC-безопасен.** `TRUNCATE` и перезаписывающий `ALTER TABLE` создают новый файл. Транзакция на RR-снапшоте, которая ещё не трогала таблицу, после этого увидит её **пустой** или уже с новыми данными, а не версию на момент своего снапшота. Это задокументированное исключение.
- **Каталог читается особыми снапшотами** (catalog snapshot, `SnapshotSelf`, `SnapshotDirty` и т. п.), а не обычным MVCC-снапшотом транзакции. Поэтому изменения схемы, в отличие от данных, видны «сразу».
- **Порядок видимости не совпадает с порядком коммитов в WAL.** Транзакция может закоммититься раньше в WAL, но стать видимой позже другой. На мастере это незаметно, но это причина отдельных тонких аномалий между мастером и репликой.
- **Откат дешёвый.** Отмена транзакции — это просто запись `ABORTED` в pg_xact. Ничего не откатывается физически: созданные версии становятся мусором, который потом уберёт VACUUM. Оборотная сторона: отменённый массовый UPDATE оставляет после себя полную таблицу мусора.

## Короткое резюме

1. Каждая версия строки знает, кто её создал (`xmin`) и кто удалил или заблокировал (`xmax`).
2. Снапшот задаётся тремя элементами: `xmin`, `xmax` и списком активных транзакций. Видимость = (создатель закоммичен и «в прошлом» для снапшота) И (удаляющего нет, он откатился или «в будущем»).
3. Статусы транзакций лежат в pg_xact, а для скорости кэшируются в hint bits.
4. Старые версии копятся прямо в таблице. VACUUM удаляет те, что старше горизонта, а горизонт держит самая старая транзакция, слот или 2PC во всём кластере.
5. XID 32-битные и сравниваются по кругу. Поэтому старые строки обязательно нужно **замораживать**, иначе через ~2 млрд транзакций они «исчезнут». PostgreSQL защищается эскалацией: aggressive VACUUM → принудительный autovacuum → failsafe → запрет записи.
6. Главный практический враг почти всегда один и тот же: **то, что держит горизонт**. Это долгие и `idle in transaction` сессии, брошенные слоты репликации и забытые prepared transactions.

Если нужно, могу отдельно разобрать какой-то кусок глубже: например, пошагово пройти по `HeapTupleSatisfiesMVCC` в исходниках, разобрать SSI, или собрать демо-скрипт с `pageinspect`, где видно hint bits, HOT-цепочки и заморозку на живой странице.

## Базовая идея

Postgres не перезаписывает строку на месте. UPDATE создаёт новую версию (tuple) и помечает старую как удалённую транзакцией X. DELETE только ставит пометку. Обе версии лежат в heap, пока VACUUM не уберёт мёртвую. Каждая транзакция по своему снапшоту решает, какую версию ей видеть.

Отсюда главный плюс: читатели не блокируют писателей, и наоборот. Цена у этого тоже есть. Мусор копится в таблицах и индексах, его надо убирать, а 32-битные счётчики транзакций надо периодически «замораживать».

Информация о видимости хранится только в heap. В индексах нет ни xmin, ни xmax. Это объясняет половину того, что будет дальше.

## Заголовок версии строки

У каждого tuple есть заголовок `HeapTupleHeaderData` на 23 байта (с выравниванием 24):

- `t_xmin`: xid транзакции, которая создала версию.
- `t_xmax`: xid транзакции, которая удалила или заблокировала версию. 0, если таких не было.
- `t_cid`: номер команды внутри транзакции (cmin/cmax, про них ниже).
- `t_ctid`: физический адрес (страница, слот). У актуальной версии он указывает на неё саму, у обновлённой на следующую версию. По этой цепочке UPDATE находит свежую версию.
- `t_infomask`, `t_infomask2`: флаги, в том числе hint bits.

Руками это выглядит так:

```sql
CREATE TABLE t (id int PRIMARY KEY, v text);
INSERT INTO t VALUES (1, 'a');
SELECT ctid, xmin, xmax, * FROM t;
-- (0,1) | 752 | 0 | 1 | a

UPDATE t SET v = 'b' WHERE id = 1;
SELECT ctid, xmin, xmax, * FROM t;
-- (0,2) | 753 | 0 | 1 | b

CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid,
       heap_tuple_infomask_flags(t_infomask, t_infomask2)
FROM heap_page_items(get_raw_page('t', 0));
-- lp 1: xmin 752, xmax 753, ctid (0,2), HEAP_HOT_UPDATED
-- lp 2: xmin 753, xmax 0,   ctid (0,2), HEAP_ONLY_TUPLE
```

Старая версия физически на месте. Обычный SELECT её просто не показывает.

## XID, CLOG и hint bits

xid занимает 32 бита и выдаётся лениво: только когда транзакция впервые что-то пишет или явно вызывает `pg_current_xact_id()`. Читающая транзакция обходится virtual xid и номера не расходует. Несколько значений зарезервированы: 0 (invalid), 1 (bootstrap), 2 (frozen). Обычные xid начинаются с 3.

Статус транзакции хранится в `pg_xact` (CLOG): 2 бита на xid, четыре состояния: in progress, committed, aborted, sub-committed. Лезть в CLOG при проверке каждой строки дорого, хоть он и кэшируется в SLRU. Поэтому первый, кто выяснил статус, записывает его прямо в строку hint-битами: `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID` и аналогичные флаги для xmax.

Последствия:

- SELECT после большой вставки пишет на диск, потому что грязнит страницы hint-битами. С data checksums или `wal_log_hints` первая такая правка страницы после чекпойнта ещё и даёт full page image в WAL. Отсюда классический вопрос «почему мой SELECT генерит WAL».
- При `synchronous_commit = off` hint COMMITTED нельзя ставить, пока WAL не сброшен дальше коммит-записи. Иначе после краша останется строка, помеченная committed, от транзакции, которой не существует.

Момент коммита устроен так: commit record пишется в WAL, затем статус в CLOG, затем транзакция удаляется из ProcArray. Для остальных она становится видимой только на последнем шаге. Между вторым и третьим шагом есть окно: CLOG уже говорит committed, а для чужих снапшотов транзакция ещё идёт. Поэтому код видимости сначала проверяет снапшот и только потом CLOG, и порядок здесь принципиален.

С синхронной репликацией так же: пока ждём ack от реплики, транзакция висит в ProcArray и никому не видна. Если ожидание отменить, придёт warning «transaction has already committed locally», и изменения станут видны, хотя на реплику могли не доехать.

## Снапшот

Снапшот по сути состоит из трёх полей:

- `xmin`: самый старый xid, который на момент снимка ещё выполнялся. Всё, что меньше, гарантированно завершено.
- `xmax`: `latestCompletedXid + 1`. Всё, что `>= xmax`, на момент снимка не завершилось и невидимо.
- `xip[]`: xid из интервала `[xmin, xmax)`, которые были активны. Для подтранзакций есть отдельный `subxip[]`.

```sql
SELECT pg_current_snapshot();
-- 752:760:753,757
```

Проверка `XidInMVCCSnapshot(xid)` отвечает на вопрос «для меня эта транзакция ещё идёт?»:

```
xid <  snap.xmin  -> нет, статус берём из CLOG / hint bits
xid >= snap.xmax  -> да
иначе             -> да, если xid есть в xip
```

Снапшот хранит только активные транзакции, закоммиченные в нём не перечисляются. Поэтому он компактный, а статус завершённых транзакций берётся из CLOG.

Снапшот снимается функцией `GetSnapshotData`: она проходит по ProcArray под `ProcArrayLock` в shared-режиме. До 14-й версии на сотнях соединений это было узким местом. В 14 механизм переделали: плотные массивы xid и переиспользование снапшота, если с прошлого раза никто не закоммитился.

## Алгоритм видимости

Упрощённый `HeapTupleSatisfiesMVCC`:

```
1. xmin
   frozen                          -> ok, к шагу 2
   aborted (hint или CLOG)         -> невидима
   xmin == моя транзакция:
       cmin >= curcid              -> невидима (вставлена более поздней командой)
       иначе                       -> к шагу 2
   XidInMVCCSnapshot(xmin)         -> невидима
   по CLOG не committed            -> невидима, ставим XMIN_INVALID
   committed                       -> ставим XMIN_COMMITTED, к шагу 2

2. xmax
   пусто / aborted / только lock   -> видима
   xmax == моя транзакция:
       cmax >= curcid              -> видима (удалю позже)
       иначе                       -> невидима
   XidInMVCCSnapshot(xmax)         -> видима (удаление для меня ещё не случилось)
   committed                       -> невидима
   aborted                         -> видима
```

Если в xmax лежит multixact, из него достаётся xid обновляющей транзакции, если такая есть.

Из алгоритма следуют три вещи:

- `xmax != 0` ещё не значит, что строка удалена. Это может быть откаченное удаление или просто блокировка.
- Транзакция, которую застал краш, остаётся в CLOG со статусом in progress. Но в ProcArray её нет, поэтому она считается aborted.
- ROLLBACK мгновенный: физически ничего не откатывается, транзакция просто помечается aborted. Мусор после неё убирает VACUUM.

## Свои изменения: cmin/cmax и combo cid

Команды внутри транзакции нумеруются (CommandId, 32 бита), и снапшот несёт текущий `curcid`. Так решается Halloween problem: `UPDATE t SET x = x + 1` не видит версий, которые только что создал сам, иначе обновлял бы их по кругу. Следующая команда той же транзакции их уже видит.

Поле `t_cid` в заголовке одно, на 4 байта. Если транзакция и создала, и удалила строку, нужны оба значения, cmin и cmax. Тогда в `t_cid` пишется combo cid: индекс в локальной хеш-таблице бэкенда, где лежат пары (cmin, cmax). Другим транзакциям cid не нужен, поэтому локальной таблицы хватает.

## Уровни изоляции

**Read Committed** (по умолчанию). Новый снапшот берётся на каждый statement. В plpgsql VOLATILE-функция берёт новый снапшот на каждый запрос внутри себя, а STABLE и IMMUTABLE работают в снапшоте вызывающего запроса.

**Repeatable Read.** Один снапшот на всю транзакцию, и берётся он на первом statement, а BEGIN его не создаёт. Если открыть RR-транзакцию и минуту ничего не делать, снапшота ещё нет. Фантомов в постгресовом RR нет (это строже стандарта), а write skew возможен.

**Serializable.** RR плюс SSI. Rw-зависимости отслеживаются через predicate locks (`SIReadLock` в `pg_locks`). При опасной структуре, то есть двух rw-конфликтах подряд, одна транзакция получает serialization failure. Ретраи на клиенте обязательны.

**Read Uncommitted** в Postgres ведёт себя как Read Committed.

### Конкурентный UPDATE

UPDATE нашёл строку по своему снапшоту, а у неё в xmax xid живой транзакции. Тогда он ждёт эту транзакцию (в `pg_locks` это видно как `transactionid`). Дальше три варианта:

- Та откатилась: обновляем исходную версию.
- Та закоммитила, уровень RC: идём по `t_ctid` к новой версии, перепроверяем WHERE уже на ней (EvalPlanQual) и, если условие выполняется, обновляем её. Поэтому `SET balance = balance + 10` из двух сессий даёт +20 без потерянного обновления.
- Та закоммитила, уровень RR или Serializable: `ERROR: could not serialize access due to concurrent update`.

У EPQ в RC есть побочка. Внутри одного statement часть строк вы видите по снапшоту, а перепроверенные строки по свежему состоянию. Строка, которая в новой версии перестала подходить под WHERE, будет пропущена. Строка, которая стала подходить только в новой версии, не найдётся вовсе, потому что поиск шёл по старому снапшоту. С `UPDATE ... FROM` и джойнами эффекты ещё страннее.

## xmax и блокировки строк, multixact

`SELECT FOR UPDATE / NO KEY UPDATE / SHARE / KEY SHARE` не держат блокировки в lock manager, их там было бы слишком много. Вместо этого они пишут свой xid в xmax строки с флагом `HEAP_XMAX_LOCK_ONLY` и битами режима. Значит, SELECT FOR UPDATE модифицирует страницу, пишет WAL и тратит xid.

Если строку держат сразу несколько транзакций (несколько FOR SHARE, или KEY SHARE вместе с UPDATE), в xmax кладётся MultiXactId с флагом `HEAP_XMAX_IS_MULTI`. Список участников с режимами лежит в `pg_multixact/offsets` и `members`.

Главный источник мультиксактов на практике: внешние ключи. Проверка FK при вставке в дочернюю таблицу берёт `FOR KEY SHARE` на родительской строке. Много параллельных вставок детей одного родителя порождают поток мультиксактов. Обычный UPDATE, который не трогает ключевые колонки, берёт `FOR NO KEY UPDATE`. Этот режим с KEY SHARE не конфликтует; его ввели в 9.3 как раз из-за FK.

Мультиксакты тоже 32-битные, и wraparound у них свой. Про него ниже.

## Индексы, HOT, pruning

Индексная запись хранит TID и о видимости ничего не знает. Индекс может указывать на мёртвую версию, тогда index scan сходит в heap и там проверит. Index-only scan обходится без heap только для страниц, помеченных all-visible в visibility map.

**UPDATE без HOT** создаёт новую версию в heap и новую запись в каждом индексе таблицы, даже если колонки этого индекса не менялись. Получается write amplification.

**HOT (heap-only tuple).** Если не изменилась ни одна индексированная колонка и новая версия влезает на ту же страницу, индексы не трогаются вообще. Старая версия получает флаг `HEAP_HOT_UPDATED`, новая `HEAP_ONLY_TUPLE`. Индекс продолжает указывать на корень цепочки, дальше переход идёт по `t_ctid`. С 16-й версии summarizing-индексы (BRIN) HOT не ломают.

Поэтому для часто обновляемых таблиц ставят `fillfactor` меньше 100: так на странице остаётся место под HOT. Долю HOT-обновлений видно по `n_tup_hot_upd` относительно `n_tup_upd` в `pg_stat_user_tables`.

**Page pruning.** Любой бэкенд при чтении страницы может её подчистить (`heap_page_prune_opt`), если свободного места мало и есть версии, мёртвые для всех. Мёртвые HOT-версии удаляются целиком, корень цепочки становится `LP_REDIRECT`, страница дефрагментируется. Line pointer'ы, на которые ссылаются индексы, pruning может только пометить `LP_DEAD`. Перевести их в `LP_UNUSED` может только VACUUM, после того как вычистит индексы.

В btree есть и свои механизмы очистки:

- `kill_prior_tuple`: index scan помечает индексную запись мёртвой, если увидел в heap, что версия мертва для всех.
- bottom-up deletion (с 14): перед сплитом страницы индекс пытается выкинуть дубли-версии.

## Горизонт: кто держит мусор

Мёртвую версию можно удалить физически, только если её xmax закоммичен и старше горизонта, то есть самого старого xmin, который ещё может кому-то понадобиться. Горизонт держат:

- открытые транзакции с xid (`backend_xid` в `pg_stat_activity`);
- снапшоты (`backend_xmin`): долгие запросы, RR-транзакции, открытые курсоры;
- idle in transaction. Нюанс: в RC сессия, которая только читала, между запросами обычно отпускает снапшот. Если же она что-то записала, её xid держит горизонт до конца транзакции;
- забытые prepared transactions (`PREPARE TRANSACTION` без COMMIT PREPARED). Они держат горизонт вечно и переживают рестарт;
- слоты репликации через `xmin` и `catalog_xmin`. Неактивный слот держит горизонт бесконечно;
- реплики с `hot_standby_feedback = on`: их долгие запросы держат горизонт мастера.

С 14-й версии горизонтов несколько: для системного каталога, для обычных таблиц и для temp-таблиц. Логический слот через `catalog_xmin` держит только каталог. Горизонт для обычных таблиц считается по транзакциям своей базы, а слоты и walsender'ы влияют на все базы.

Если горизонт стоит, VACUUM всё равно работает, тратит IO и ничего не удаляет. В `VACUUM VERBOSE` и логах autovacuum это видно по строке `N are dead but not yet removable, oldest xmin: X`.

## VACUUM

Обычный (lazy) VACUUM работает по фазам:

1. **Скан heap.** Страницы, помеченные all-visible в VM, пропускаются (если VACUUM не aggressive). На каждой странице делается pruning, TID мёртвых line pointer'ов собираются в память, старые версии замораживаются, выставляются биты VM.
2. **Чистка индексов.** Для каждого индекса выполняется bulkdelete по собранному списку TID; для btree это полный проход по индексу. Если память под TID кончилась, фазы 1-3 повторяются, и индексы сканируются по несколько раз, а на больших таблицах это очень дорого. До 17-й версии список был массивом по 6 байт на TID с потолком 1 ГБ независимо от `maintenance_work_mem`. В 17 его заменили на TidStore на radix tree: он в разы компактнее и потолка нет.
3. **Второй проход по heap.** `LP_DEAD` превращаются в `LP_UNUSED`, и только теперь слоты свободны.
4. **Учёт.** Обновляются FSM, `reltuples`/`relpages`, `relfrozenxid`/`relminmxid`, `datfrozenxid`; обрезаются `pg_xact` и `pg_multixact`.
5. **Обрезка пустого хвоста таблицы.** Ненадолго берётся AccessExclusiveLock. На мастере это обычно незаметно, а на реплике блокировка проигрывается из WAL и рубит запросы. Отключается параметром таблицы `vacuum_truncate = off`, в 18 появился одноимённый GUC.

Если у таблицы нет индексов, всё делается за один проход.

Обычный VACUUM не возвращает место ОС, кроме хвоста: он делает его пригодным для переиспользования. Раздутую таблицу сжимает VACUUM FULL. Он переписывает таблицу под ACCESS EXCLUSIVE и требует ещё столько же места на диске. Онлайн-альтернативы: pg_repack или pg_squeeze.

### Autovacuum

Работает так: launcher запускает воркеров, по умолчанию их не больше трёх (`autovacuum_max_workers`).

**Триггер по мёртвым строкам:** `n_dead_tup > autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2) * reltuples`. На таблице в миллиард строк это 200 млн мёртвых до запуска. Поэтому большим таблицам `scale_factor` снижают на уровне таблицы. В 18 появился потолок `autovacuum_vacuum_max_threshold` (по умолчанию 100 млн).

**Триггер по вставкам** (с 13): `autovacuum_vacuum_insert_threshold` / `insert_scale_factor`. До него append-only таблицы не получали ни битов VM, ни заморозки вплоть до антивраппаунд-прохода.

**Троттлинг cost-based.** Каждая прочитанная и каждая загрязнённая страница стоит очков. Набрав `autovacuum_vacuum_cost_limit` (по умолчанию берётся `vacuum_cost_limit` = 200, бюджет делится между воркерами), воркер спит `autovacuum_vacuum_cost_delay`: 2 мс с 12-й версии, раньше было 20. Дефолты консервативные, на современных дисках лимит обычно поднимают в разы. Ручной VACUUM по умолчанию работает без задержек.

**Обычный autovacuum уступает.** Если кто-то ждёт блокировку, которую он держит, deadlock detector его отменяет. Антивраппаунд-автовакуум (в `pg_stat_activity` выглядит как `autovacuum: VACUUM ... (to prevent wraparound)`) не отменяется. Отсюда классическая авария: ALTER TABLE ждёт этот автовакуум, а за ALTER выстраиваются в очередь все запросы к таблице.

## Wraparound и заморозка

xid 32-битный, и сравниваются они по кругу: `(int32)(a - b) < 0`. Для любого xid около 2^31 (≈2.1 млрд) номеров лежат «в прошлом» и столько же «в будущем». Если ничего не делать, строка с `xmin = 1000` после 2^31 транзакций окажется «в будущем» для всех и пропадёт из выборок. Данные на диске будут целы, но невидимы.

Решение: заморозка. Версии с закоммиченным xmin старше горизонта получают флаг `HEAP_XMIN_FROZEN`. До 9.4 xmin перезаписывали на 2 (FrozenTransactionId), теперь исходное значение сохраняется для отладки. Замороженная версия видна всем, и её возраст больше не учитывается. Старый xmax от откаченной транзакции или голой блокировки при этом тоже вычищается.

Учёт ведётся так. `pg_class.relfrozenxid` гарантирует, что в таблице (включая её TOAST) нет незамороженных xid старше этого значения. `pg_database.datfrozenxid` равен минимуму по базе. Лимиты всего кластера определяются самой старой `datfrozenxid`. С 15-й версии `relfrozenxid` после VACUUM выставляется по фактически самому старому оставшемуся xid, поэтому продвигается заметно дальше.

Параметры:

- `vacuum_freeze_min_age` (50 млн): насколько старым должен быть xid, чтобы VACUUM заморозил его попутно. С 16 заморозка постраничная. Если на странице нужно заморозить хоть что-то или pruning всё равно генерирует FPI, замораживается вся страница, чтобы стать all-frozen.
- `vacuum_freeze_table_age` (150 млн): если `age(relfrozenxid)` выше, VACUUM становится aggressive и читает все страницы, кроме all-frozen. На огромной таблице без all-frozen страниц это полный проход.
- `autovacuum_freeze_max_age` (200 млн): выше этого порога autovacuum запускается для таблицы принудительно, даже при `autovacuum = off`. Это тот самый `(to prevent wraparound)`.
- `vacuum_failsafe_age` (1.6 млрд, с 14): VACUUM переходит в аварийный режим. Индексы пропускает, cost delay игнорирует, только замораживает.
- В 18 обычный VACUUM ещё и прихватывает часть страниц all-visible, но не all-frozen, чтобы размазать работу будущего aggressive-прохода (`vacuum_max_eager_freeze_failure_rate`).

Ближе к краю начинаются предупреждения. За ~40 млн xid до точки wraparound в лог и клиентам сыплется `WARNING: database "x" must be vacuumed within N transactions`. За ~3 млн база перестаёт выдавать новые xid: `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение при этом работает, запись нет. Пороги 40/3 млн действуют с 14-й версии, раньше было примерно 11 и 1 млн; насчёт точной версии изменения я не на 100% уверен.

Как лечить. Сначала убрать то, что держит горизонт: забытые prepared transactions, мёртвые слоты, зависшие сессии. Потом запустить обычный VACUUM в этой базе. Документация с 16-й версии говорит делать это в нормальном режиме, single-user mode больше не нужен (раньше советовали именно его). VACUUM FULL в такой ситуации не делать.

Самый важный нюанс: горизонт ограничивает и заморозку. Порог заморозки равен `min(горизонт, nextXid - freeze_min_age)`. Если транзакция висит неделю, за эту неделю ни одна таблица не заморозит ни одного xid новее её. Автовакуум будет крутиться без остановки и ничего не сможет сделать. Большинство реальных wraparound-аварий выглядят именно так: забытый слот, prepared transaction или idle in transaction, при живом и работающем автовакууме.

Ещё два капкана:

- Temp-таблицы автовакуум не обрабатывает вообще, их видит только сессия-владелец. Долгоживущее соединение в пуле с temp-таблицей тянет её `relfrozenxid` в прошлое. Осиротевшие после краша temp-таблицы автовакуум дропает.
- Расход xid. Каждая пишущая транзакция в autocommit тратит xid, SELECT FOR UPDATE тоже. Каждый SAVEPOINT или EXCEPTION-блок в plpgsql, внутри которого была запись, тратит ещё один xid на подтранзакцию. При 10k пишущих TPS порог 200 млн проходится примерно за 5.5 часов, и антивраппаунд-проходы идут постоянно. Батчинг сильно снижает расход.

### Мультиксакты

У мультиксактов свой набор параметров:

- `vacuum_multixact_freeze_min_age`: 5 млн;
- `vacuum_multixact_freeze_table_age`: 150 млн;
- `autovacuum_multixact_freeze_max_age`: 400 млн.

Возраст смотрят через `mxid_age(relminmxid)`. Отдельно ограничено пространство members, у него тоже 32-битная адресация. Autovacuum начинает агрессивничать раньше, если members заполняются, даже при небольшом `mxid_age`. Ошибка при исчерпании похожая: `database is not accepting commands that generate new MultiXactIds`.

### 64 бита

В ядре уже есть `FullTransactionId` (epoch + xid), и `pg_current_xact_id()` возвращает `xid8`. Но в заголовке строки на диске по-прежнему 32 бита. Насколько я знаю, 64-битные xid в heap в ваниль не вошли; в Postgres Pro Enterprise они есть.

## Реплики

Hot standby строит снапшоты по записям running-xacts из WAL. Если мастер вычистил версии, нужные запросу на реплике, при проигрывании WAL возникает конфликт. Реплика ждёт `max_standby_streaming_delay`, потом отменяет запрос с ошибкой `canceling statement due to conflict with recovery`.

Вариантов три, у каждого своя цена:

- `hot_standby_feedback = on`: реплика сообщает мастеру свой xmin, и её долгие запросы раздувают таблицы на мастере;
- больший delay: реплика начинает отставать;
- отдельная реплика под аналитику.

`vacuum_defer_cleanup_age` убрали в 16.

## Подводные камни

- Откаченный UPDATE на 100 млн строк оставил 100 млн мёртвых версий и раздутые индексы, хотя сам ROLLBACK прошёл мгновенно.
- Подтранзакции. ProcArray кэширует до 64 subxid на бэкенд (`PGPROC_MAX_CACHED_SUBXIDS`). Если их больше, наступает overflow, и проверки видимости начинают ходить в SLRU `pg_subtrans`. Это известный обрыв производительности, особенно заметный на репликах. Сюда же ORM, которые оборачивают каждый запрос в SAVEPOINT. В 17 размеры SLRU стали настраиваемыми (`subtransaction_buffers` и др.); это смягчает проблему, но не устраняет.
- TRUNCATE и переписывающие ALTER TABLE не MVCC-safe. RR-транзакция, которая ещё не трогала таблицу, после чужого закоммиченного TRUNCATE увидит её пустой.
- Последовательности живут вне MVCC: `nextval` не откатывается, отсюда дыры в нумерации.
- `COPY ... FREEZE` в таблицу, созданную или обрезанную в той же транзакции, сразу пишет замороженные строки. С 14 он ставит и биты VM, и последующий VACUUM почти ничего не делает.
- `old_snapshot_threshold`, который позволял ломать долгие снапшоты ради вакуума, удалили в 17.
- Страховки от зависших сессий: `idle_in_transaction_session_timeout`, `transaction_timeout` (с 17), `statement_timeout`.

## 08-english

> What's the practical difference between git rebase and git merge, and when should I pick each?

### baseline (2284 chars)

## Суть

Обе команды переносят изменения из одной ветки в другую. Разница в том, как выглядит история после этого.

**`git merge`** создаёт merge-коммит с двумя родителями. История остаётся такой, какой была на самом деле: видно, что ветка жила отдельно и в какой-то момент слилась.

```
      A---B---C  feature
     /         \
D---E---F---G---M  main
```

**`git rebase`** переписывает коммиты ветки поверх новой базы. Получаются **новые коммиты с новыми хешами**, а история становится линейной, будто вы начали работу от свежего `main`.

```
D---E---F---G---A'--B'--C'  feature
```

## Практические последствия

| | merge | rebase |
|---|---|---|
| История | честная, ветвистая | линейная, чистая |
| Хеши коммитов | не меняются | меняются |
| Безопасно для общих веток | да | **нет** |
| Конфликты | решаются один раз | могут всплывать на каждом коммите |
| `git bisect`, `git log` | шумнее | удобнее |
| Откат фичи целиком | `git revert -m 1 <merge>` | нужно ревертить каждый коммит |

## Когда что брать

**Rebase:**
- Подтянуть свежий `main` в **свою локальную** ветку, которую ещё никто не забрал: `git pull --rebase` или `git rebase main`.
- Причесать коммиты перед PR: `git rebase -i` позволяет склеить «fix typo», переупорядочить коммиты и поправить сообщения.
- В проекте принята линейная история (rebase-and-merge или squash в PR).

**Merge:**
- Ветка уже запушена и с ней работают другие люди.
- Нужно сохранить факт интеграции, например долгоживущие ветки `release/*` или слияние `develop` в `main`.
- Хочется откатывать фичу одним действием.

## Золотое правило

**Не делайте rebase коммитов, которые уже кто-то забрал.** После rebase придётся делать `push --force`, а у коллег история разойдётся с вашей. Если всё же пришлось, используйте `git push --force-with-lease`: он не затрёт чужие коммиты, появившиеся на удалённой ветке после вашего последнего fetch.

## Типичный рабочий процесс

1. Работаете в своей фича-ветке и периодически делаете `git rebase main`, чтобы оставаться актуальным.
2. Перед PR вызываете `git rebase -i main` и чистите коммиты.
3. Сама интеграция в `main` проходит через merge или squash-merge в PR, смотря что принято в команде.

Если в команде уже есть договорённость, следуйте ей: единообразие важнее, чем выбор одного из двух подходов.

### current (2112 chars)

Оба способа сводят изменения из одной ветки в другую. Разница в том, что остаётся в истории.

**merge** берёт две ветки и создаёт merge-коммит с двумя родителями. Существующие коммиты не трогаются, SHA остаются прежними. История честная: видно, что была ветка и когда её влили. Минус в том, что при активной работе граф превращается в лапшу из `Merge branch 'main' into feature`.

**rebase** берёт твои коммиты и переигрывает их поверх новой базы. Получаются новые коммиты с новыми SHA, а история становится линейной, будто ты начал работу от свежего main. Читать её и гонять `git bisect` проще. Минус: это переписывание истории.

Практические последствия:

- Rebase ветки, которую уже кто-то стянул, ломает жизнь коллегам: у них старые SHA, у тебя новые. Отсюда главное правило: не ребейзить то, с чем работают другие. Свою личную ветку можно, после этого пушишь через `git push --force-with-lease`, не через голый `--force`.
- Конфликты. При merge решаешь их один раз. При rebase возможно на каждом коммите по очереди, если десять коммитов трогают одно место, будет больно. Тут помогает `git config rerere.enabled true`.
- Откат. Merge-коммит откатывается целиком через `git revert -m 1 <sha>`. После rebase фича размазана по отдельным коммитам, и откатывать придётся их.

Когда что брать:

- **rebase**: подтянуть свежий main в свою локальную ветку перед PR (`git rebase main`), почистить свои коммиты через `git rebase -i` (сквошнуть "fix typo", переписать сообщения), `git pull --rebase` вместо пула с лишним merge-коммитом.
- **merge**: влить готовую фичу в main или в общую ветку, интегрировать долгоживущие ветки (release, develop), любая ситуация, где важно сохранить, что изменения пришли пачкой из отдельной ветки.

Самый частый рабочий вариант: локально ребейзишь свою ветку на main и чистишь коммиты, а в main она попадает через merge или squash-merge в PR. Squash-merge сжимает всю фичу в один коммит в main. Это удобно, если промежуточные коммиты никому не нужны, но теряется детализация.

Если в команде уже принята конвенция, следуй ей. Смешивать подходы хаотично хуже, чем выбрать любой из них.

## 5. Certbot

В 24.04 версия из apt (2.9) рабочая:

```bash

```

Официально EFF рекомендует ставить через snap (`sudo snap install --classic certbot`). Это даёт более свежую версию, но для задачи разницы нет. Выбери что-то одно, не ставь оба способа сразу.

## 6. Получить сертификат

```bash
sudo certbot --nginx \
  -d example.com -d www.example.com \
  -m you@yourmail.tld --agree-tos --no-eff-email \
  --redirect
```

Certbot сделает три вещи:
- пройдёт проверку HTTP-01 через порт 80;
- допишет в твой server-блок `listen 443 ssl`, пути к сертификату и `include /etc/letsencrypt/options-ssl-nginx.conf`;
- добавит отдельный server-блок с редиректом с 80 на 443 (флаг `--redirect`).

Если `www` не нужен, убери `-d www.example.com` и из `server_name`.

## 9. Опционально: HTTP/2 и HSTS

В nginx 1.24 директивы `http2 on;` ещё нет (она появилась в 1.25.1), поэтому HTTP/2 включается в строке listen внутри HTTPS-блока:

```nginx
listen 443 ssl http2;
listen [::]:443 ssl http2;
```

HSTS добавляй только когда убедился, что HTTPS работает стабильно. Браузеры запомнят его на весь `max-age`, и откатить это будет сложно:

```nginx
add_header Strict-Transport-Security "max-age=31536000" always;
```

После правок: `sudo nginx -t && sudo systemctl reload nginx`.

## 10. Со стороны приложения

- Оно должно слушать `127.0.0.1:8000`, а не `0.0.0.0`.
- Приложению нужно доверять заголовкам `X-Forwarded-*` от nginx, иначе оно будет считать, что запрос пришёл по http, и генерировать неправильные ссылки и редиректы. Примеры:
  - uvicorn: `--proxy-headers --forwarded-allow-ips=127.0.0.1`
  - gunicorn: `--forwarded-allow-ips=127.0.0.1`
  - Django: `SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")`
- Запускать приложение лучше через systemd-юнит, чтобы оно поднималось после ребута.

## 10-followup

> а если это симлинк, который указывает на удалённый файл? что вернёт твоя проверка

### baseline (981 chars)

`-f` и `-e` вернут **false** (код 1): они проверяют то, на что указывает ссылка, а цели нет. `-L` вернёт **true**, потому что смотрит на саму ссылку и не идёт по ней.

Можно проверить:

```bash
touch target && ln -s target link && rm target

[[ -e link ]]; echo $?   # 1
[[ -f link ]]; echo $?   # 1
[[ -L link ]]; echo $?   # 0
```

Так что первая проверка из моего ответа (`-f`) скажет «файла нет», хотя запись в каталоге есть. Это важно, например, перед `ln -s` или `touch`: путь занят, и создание упадёт или пойдёт не туда.

Что использовать в зависимости от задачи:

```bash
# есть ли что-нибудь по этому пути, включая битую ссылку
[[ -e "$f" || -L "$f" ]]

# именно битая ссылка
[[ -L "$f" && ! -e "$f" ]]

# живой обычный файл (битая ссылка не пройдёт)
[[ -f "$f" ]]
```

Ещё один нюанс: если ссылка указывает на каталог, к которому нет прав на поиск (`x`), `-e` тоже вернёт false. Цель при этом есть, но проверить её нельзя, и снаружи это выглядит так же, как битая ссылка.

### current (630 chars)

`-f` вернёт false. Она идёт по ссылке к цели, а цели нет. С `-e`, `-r` и остальными то же самое.

Сама ссылка при этом существует, и её видит только `-L` (или синоним `-h`), потому что он смотрит на саму ссылку и за ней не ходит.

Битую ссылку ловят так:

```bash
if [[ -L file && ! -e file ]]; then
  echo "битый симлинк"
fi
```

А «есть хоть что-то с таким именем, даже битая ссылка» проверяется через `[[ -e file || -L file ]]`.

Есть подвох, если после `! -f` ты собираешься создавать файл. `echo x > file` пройдёт по битой ссылке и создаст файл там, куда она указывает, а не на её месте. Если это важно, сначала проверь `-L`.
