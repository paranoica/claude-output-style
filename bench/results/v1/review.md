## 02-howto

> как в python прочитать jsonl построчно и пропустить битые строки, но залогировать номер строки

### baseline (2410 chars)

Генератор, который отдаёт валидные записи, а битые строки пропускает и пишет в лог с номером:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[dict[str, Any]]:
    """Yield JSON objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON object for each valid line.
    """
    # Binary mode so a single line with bad UTF-8 doesn't abort the whole read.
    with open(path, "rb") as f:
        for lineno, raw in enumerate(f, start=1):
            if not raw.strip():
                continue
            try:
                obj = json.loads(raw)
            except (json.JSONDecodeError, UnicodeDecodeError) as e:
                logger.warning("%s:%d: skipping malformed line: %s", path, lineno, e)
                continue
            if not isinstance(obj, dict):
                logger.warning(
                    "%s:%d: expected object, got %s", path, lineno, type(obj).__name__
                )
                continue
            yield obj
```

Использование:

```python
logging.basicConfig(level=logging.INFO)

for record in read_jsonl("data.jsonl"):
    ...
```

Что здесь важно:

- **`enumerate(f, start=1)`** даёт номер строки как в редакторе, начиная с 1.
- **Файл открывается в режиме `"rb"`.** `json.loads` принимает `bytes` и сам декодирует UTF-8. Если открыть файл в текстовом режиме, то одна строка с битой кодировкой выбросит `UnicodeDecodeError` прямо из цикла `for`, и чтение оборвётся целиком, а не пропустит одну строку.
- **Пустые строки пропускаются молча.** Обычно это хвостовой `\n` в конце файла, а не ошибка. Если пустые строки тоже нужно считать битыми, уберите эту проверку.
- **Проверка `isinstance(obj, dict)`** нужна, потому что строки `42` или `"abc"` являются валидным JSON, но, скорее всего, не тем, что вы ждёте. Если в файле допустимы любые JSON-значения, проверку можно убрать и поменять тип на `Iterator[Any]`.
- В лог попадает текст исключения. У `JSONDecodeError` там есть позиция внутри строки (`line 1 column 15 (char 14)`), что помогает найти место поломки.

Если нужно ещё и узнать количество пропущенных строк в конце, проще всего завести счётчик и вывести итог после цикла через `logger.info`. Могу показать вариант с ним.

### both (1544 chars)

Читай файл через `enumerate(f, start=1)`, каждую строку разбирай в `try/except json.JSONDecodeError` и при ошибке пиши в лог номер строки:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid line.
    """
    with open(path, encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                logger.warning("%s:%d: invalid JSON (%s)", path, lineno, e.msg)


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    for record in read_jsonl("data.jsonl"):
        print(record)
```

Генератор держит в памяти одну строку, так что подходит и для больших файлов. Пустые строки пропускаются без записи в лог: обычно это просто перевод строки в конце файла.

Если в файле может встретиться битая кодировка, `UnicodeDecodeError` вылетит на итерации по файлу и `except` вокруг `json.loads` его не поймает. В таком случае открывай файл с `errors="replace"`: испорченные байты заменятся на `�`, и такая строка, скорее всего, не разберётся как JSON и попадёт в лог как обычная битая строка.

### claudemd (1518 chars)

Используйте `enumerate(f, start=1)` и оберните `json.loads` в `try/except`:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid non-empty line.
    """
    with open(path, "rb") as f:
        for lineno, raw in enumerate(f, start=1):
            line = raw.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except ValueError as e:
                logger.warning("%s:%d: skipped malformed line: %s", path, lineno, e)


for record in read_jsonl("data.jsonl"):
    ...
```

Файл открывается в бинарном режиме, потому что `json.loads` принимает `bytes` и сам декодирует UTF-8. Если в строке окажется битая кодировка, `UnicodeDecodeError` возникнет внутри `try` и пропустится только эта строка. В текстовом режиме такая ошибка вылетела бы при итерации по файлу и оборвала бы чтение целиком. `ValueError` ловит оба случая, потому что `JSONDecodeError` и `UnicodeDecodeError` от него наследуются.

Пустые строки пропускаются молча, так как в JSONL они обычно встречаются в конце файла и ошибкой не считаются. Если нужно ещё и посчитать битые строки, заведите счётчик в блоке `except` и выведите его после цикла.

### current (1632 chars)

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def iter_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid line.
    """
    with open(path, encoding="utf-8", errors="replace") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                logger.warning("%s:%d: invalid JSON (%s)", path, lineno, e.msg)
```

Использование:

```python
logging.basicConfig(level=logging.INFO)
for rec in iter_jsonl("data.jsonl"):
    ...
```

Пара нюансов:

- `errors="replace"` нужен, чтобы битая кодировка не роняла весь цикл с `UnicodeDecodeError`. Такая строка превратится в мусор с `\ufffd` и, скорее всего, отвалится на `json.loads`, то есть тоже залогируется. Если нужно ловить кодировку отдельно, читай файл в бинарном режиме (`"rb"`) и делай `line.decode("utf-8")` внутри того же `try`, добавив `UnicodeDecodeError` в `except`.
- Пустые строки молча пропускаются. Хочешь видеть их в логе, убери `continue` и логируй.
- `json.loads` спокойно примет `42` или `"foo"` как валидную строку. Если ждёшь только объекты, добавь проверку `isinstance(obj, dict)` и логируй остальное как битое.
- Если нужна статистика в конце, заведи счётчик пропущенных и выведи после цикла.

### style (1509 chars)

Читай файл через `enumerate(f, start=1)`, на каждой строке делай `json.loads` в `try/except json.JSONDecodeError` и при ошибке пиши номер в лог:

```python
import json
import logging
from collections.abc import Iterator
from pathlib import Path
from typing import Any

logger = logging.getLogger(__name__)


def read_jsonl(path: str | Path) -> Iterator[Any]:
    """Yield parsed objects from a JSONL file, skipping malformed lines.

    Args:
        path: Path to the JSONL file.

    Yields:
        Parsed JSON value for each valid line.
    """
    with open(path, encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                logger.warning("%s:%d: invalid JSON (%s)", path, lineno, e.msg)
```

Использование:

```python
logging.basicConfig(level=logging.INFO)

for record in read_jsonl("data.jsonl"):
    ...
```

Пустые строки пропускаются молча. Если их тоже надо считать битыми, убери проверку `if not line`.

Если в файле может встретиться невалидный UTF-8, построчная обработка упадёт на чтении раньше, чем дойдёт до `json.loads`, с `UnicodeDecodeError`. Тогда открывай файл с `errors="replace"`. Другой вариант: открыть в режиме `"rb"` и декодировать каждую строку внутри того же `try`, добавив `UnicodeDecodeError` в `except`. Так битая кодировка тоже попадёт в лог с номером строки.

## 03-concept

> Объясни, что такое идемпотентность в HTTP API и зачем нужен Idempotency-Key.

### baseline (5123 chars)

# Идемпотентность в HTTP API

## Что это

Операция **идемпотентна**, если повторное выполнение с теми же параметрами оставляет систему в том же состоянии, что и однократное. Ответ при этом может отличаться: первый `DELETE` вернёт `204`, второй `404`. Важно другое: состояние сервера после N вызовов такое же, как после одного.

Идемпотентность не равна «безопасности». **Safe**-методы вообще не меняют состояние (`GET`, `HEAD`, `OPTIONS`). Идемпотентные могут менять состояние, но повтор ничего не добавляет.

## Методы по RFC 9110

| Метод | Safe | Идемпотентен | Почему |
|---|---|---|---|
| `GET`, `HEAD`, `OPTIONS` | да | да | ничего не меняют |
| `PUT` | нет | да | «положи ресурс в такое состояние», и повтор даёт то же состояние |
| `DELETE` | нет | да | удалённое остаётся удалённым |
| `POST` | нет | **нет** | «создай ещё один», и каждый вызов создаёт новый |
| `PATCH` | нет | **не гарантируется** | `{"balance": 100}` идемпотентен, `{"op": "increment"}` нет |

Это контракт, а не магия. Если ваш `PUT` инкрементирует счётчик, он нарушает спецификацию, и клиенты, прокси и ретраи будут вести себя неправильно.

## Зачем это нужно: проблема ретраев

Сеть ненадёжна. Типичный сценарий:

```
Клиент ── POST /payments {amount: 100} ──▶ Сервер
                                          списал деньги
Клиент ◀──── ✗ таймаут / обрыв ────────── ответ потерялся
```

Клиент не знает, что произошло:
- запрос не дошёл до сервера;
- дошёл, но упал при обработке;
- обработался, но потерялся ответ.

Если ретраить, можно списать деньги дважды. Если не ретраить, платёж может так и не пройти. Для идемпотентных методов ответ простой: ретраим смело. Для `POST` нужен дополнительный механизм.

## Idempotency-Key

Клиент генерирует уникальный ключ (обычно UUID v4) **на одну логическую операцию** и шлёт его в заголовке:

```http
POST /payments HTTP/1.1
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 100, "currency": "RUB"}
```

При ретрае клиент отправляет **тот же ключ**. Сервер видит, что запрос уже был, и не выполняет операцию заново, а возвращает сохранённый результат.

Так `POST` становится идемпотентным, хотя по своей семантике он таким не является. Подход популяризировал Stripe, сейчас он есть в API PayPal, Adyen, многих банков и описан в IETF-драфте `draft-ietf-httpapi-idempotency-key-header`.

## Как это реализуется на сервере

```
1. Пришёл запрос с ключом K
2. Ищем K в хранилище (scope: ключ + клиент/аккаунт)
   ├─ не найден → атомарно записываем K со статусом "processing" и хешем тела,
   │              выполняем операцию, сохраняем ответ (статус + тело), "completed"
   ├─ найден, "completed", хеш тела совпадает → возвращаем сохранённый ответ
   ├─ найден, хеш тела НЕ совпадает → 422 (ключ переиспользован с другими данными)
   └─ найден, "processing" → 409 Conflict (параллельный дубль, пусть клиент повторит позже)
3. Через TTL (обычно 24 ч) ключ удаляется
```

На чём обычно ошибаются:

- **Гонка при проверке.** Последовательность «проверил, что ключа нет, потом вставил» без атомарности пропустит два параллельных дубля. Нужен `INSERT ... ON CONFLICT`, уникальный индекс или `SET NX` в Redis.
- **Атомарность с бизнес-операцией.** Если ключ лежит в Redis, а платёж в Postgres, между ними может случиться падение. Надёжнее хранить ключ в той же БД и в той же транзакции, что и сам эффект.
- **Проверка тела.** Без сравнения хеша ошибка клиента (тот же ключ для другого платежа) молча вернёт чужой результат.
- **Scope ключа.** Ключ уникален в рамках клиента или аккаунта, а не глобально. Иначе один клиент может получить ответ другого.
- **Что кешировать.** Успешные ответы и детерминированные ошибки (`4xx` валидации) сохраняют. Ответы `5xx` обычно не сохраняют, чтобы ретрай мог пройти.
- **Внешние побочные эффекты.** Если внутри вызывается сторонний платёжный шлюз, ему тоже нужно передавать idempotency key, иначе дубль возникнет уровнем ниже.

## Обязанности клиента

- Генерировать ключ **один раз на намерение пользователя**, а не на каждую HTTP-попытку. Самая частая ошибка: новый UUID внутри цикла ретраев сводит всю защиту на нет.
- Ретраить с экспоненциальной задержкой и jitter.
- Не переиспользовать ключ для другой операции.

## Альтернативы и смежные приёмы

- **Естественные ключи.** Если у операции есть бизнес-идентификатор (номер заказа клиента), достаточно уникального индекса по нему.
- **`PUT` с клиентским ID.** `PUT /orders/{client-generated-uuid}` идемпотентен по определению, и отдельный заголовок не нужен.
- **Условные запросы.** `If-Match` с `ETag` защищает от потерянных обновлений, но это другая задача: конкурентность, а не дубли.
- **Дедупликация в очередях.** В брокерах та же идея называется «exactly-once processing» и строится на at-least-once доставке плюс идемпотентный консьюмер.

## Коротко

Идемпотентность позволяет безопасно повторять запросы при сбоях сети. `GET`, `PUT` и `DELETE` идемпотентны по спецификации, `POST` нет. `Idempotency-Key` делает `POST` идемпотентным: клиент помечает операцию уникальным ключом, а сервер запоминает результат и при повторе отдаёт его, не выполняя операцию снова.

### both (2627 chars)

Идемпотентная операция даёт одинаковый эффект на состоянии сервера, сколько бы раз её ни повторили: один запрос или десять одинаковых приводят к одному и тому же результату.

## Какие методы идемпотентны

По RFC 9110 идемпотентны `GET`, `HEAD`, `OPTIONS`, `PUT` и `DELETE`. `POST` и `PATCH` идемпотентными не считаются.

Речь идёт об эффекте на сервере, ответ при этом может отличаться. Первый `DELETE /orders/42` вернёт `204`, повторный вернёт `404`, но заказ в обоих случаях удалён ровно один раз. `PUT /users/7 {"name": "Ann"}` сколько угодно раз оставляет пользователя с именем Ann. А `POST /payments` при каждом вызове создаёт новый платёж.

## Зачем это нужно

Сеть ненадёжна. Клиент отправил запрос, получил таймаут и не знает, что произошло: запрос не дошёл, сервер упал посреди обработки или всё выполнилось, но потерялся ответ. Безопасно повторить можно только идемпотентный запрос. Повтор `POST /payments` в такой ситуации может списать деньги дважды.

## Idempotency-Key

Этот заголовок делает идемпотентным неидемпотентный по природе запрос. Клиент генерирует уникальный ключ (обычно UUID) на одну логическую операцию и при всех повторах этой операции отправляет тот же ключ:

```http
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

Сервер при первом запросе с этим ключом выполняет операцию и сохраняет ключ вместе с результатом. При повторе он находит ключ и возвращает сохранённый ответ, ничего не выполняя заново. Для следующего, нового платежа клиент генерирует новый ключ.

Подход популяризовал Stripe, сейчас он описан в черновике IETF `draft-ietf-httpapi-idempotency-key-header`.

## Что должен делать сервер

1. Привязывать ключ к клиенту или аккаунту, чтобы ключи разных клиентов не пересекались.
2. Сохранять вместе с ключом отпечаток тела запроса. Если пришёл тот же ключ с другим телом, это ошибка клиента, обычно отвечают `422`.
3. Обрабатывать гонку: если второй запрос с тем же ключом пришёл, пока первый ещё выполняется, отвечать `409` или ждать завершения. Запись ключа нужно создавать атомарно, например через уникальный индекс в БД и вставку в той же транзакции, что и сама операция.
4. Хранить ключи ограниченное время (у Stripe 24 часа) и чистить по TTL.
5. Решить, какие ответы кешировать. Ошибки валидации обычно не сохраняют, чтобы клиент мог исправить запрос и повторить с тем же ключом. Результат операции, которая начала менять состояние, сохраняют, включая ошибку.

В итоге клиент получает простое правило: при таймауте или сетевой ошибке повторяй запрос с тем же ключом, дубликата не будет.

### claudemd (2874 chars)

Идемпотентная операция при повторном выполнении с теми же данными оставляет сервер в том же состоянии, что и после первого выполнения. Сколько бы раз клиент ни отправил такой запрос, эффект будет как от одного.

## Какие методы идемпотентны

По RFC 9110 идемпотентны `GET`, `HEAD`, `OPTIONS`, `PUT` и `DELETE`. Не идемпотентны `POST` и, в общем случае, `PATCH`.

- `PUT /users/42` с одним и тем же телом: после первого и после десятого вызова пользователь выглядит одинаково.
- `DELETE /orders/7`: первый вызов удаляет заказ, второй может вернуть `404`, но состояние сервера то же. Идемпотентность касается эффекта, ответы могут различаться.
- `POST /payments`: каждый вызов создаёт новый платёж. Два вызова означают два списания.

Безопасность (safe) и идемпотентность различаются: `GET` безопасен, потому что ничего не меняет, а `DELETE` меняет состояние, но повтор не добавляет новых изменений.

## Зачем нужен Idempotency-Key

Проблема возникает при сбоях сети. Клиент отправил `POST /payments`, соединение оборвалось по таймауту, и клиент не знает, дошёл ли запрос. Если не повторять, платёж может потеряться. Если повторить, деньги могут списаться дважды.

`Idempotency-Key` делает `POST` идемпотентным на уровне конкретной операции:

```http
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

1. Клиент генерирует уникальный ключ (обычно UUID v4) один раз на логическую операцию, до первой попытки.
2. При всех повторах этой операции отправляется тот же ключ. Для новой операции нужен новый ключ.
3. Сервер при первом запросе выполняет операцию и сохраняет ключ вместе с ответом.
4. При повторе с тем же ключом сервер ничего не выполняет заново и возвращает сохранённый ответ.

## На что обратить внимание при реализации на сервере

- Область ключа: ключи хранятся в пределах клиента или аккаунта, иначе ключи разных пользователей могут совпасть.
- Отпечаток запроса: вместе с ключом сохраняется хеш тела. Тот же ключ с другим телом считается ошибкой клиента, черновик IETF (`draft-ietf-httpapi-idempotency-key-header`) предлагает `422`.
- Параллельные запросы: если запрос с этим ключом ещё обрабатывается, второй получает `409 Conflict`, а не запускает операцию повторно. Для этого нужна блокировка или уникальный индекс на ключ.
- Атомарность: запись ключа и бизнес-эффект (создание платежа) должны фиксироваться в одной транзакции. Иначе при падении между ними повтор либо продублирует операцию, либо вернёт ответ на операцию, которой не было.
- Срок хранения: ключи хранятся ограниченное время. Stripe, например, держит их 24 часа. Срок должен покрывать окно, в котором клиент реально будет повторять запрос.

Так устроены API Stripe, Adyen, PayPal и многих других платёжных систем: без такого механизма безопасные автоматические ретраи для создающих операций невозможны.

**Идемпотентность** означает, что повторный запрос оставляет сервер в том же состоянии, что и первый. Один раз отправил или пять, итог одинаковый.

По спеке HTTP (RFC 9110) идемпотентны `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`. Не идемпотентны `POST` и `PATCH`.

Идемпотентность касается состояния, а не ответа. Первый `DELETE /orders/42` вернёт 204, второй вернёт 404, но заказ в обоих случаях удалён. Это нормально.

Ещё её путают с безопасностью (safe). Safe методы вообще ничего не меняют (`GET`). `DELETE` меняет состояние, значит он не safe, но идемпотентен.

## Зачем нужен Idempotency-Key

Сеть ненадёжна. Клиент шлёт `POST /payments` и ловит таймаут. Возможны три исхода:

- запрос не дошёл;
- дошёл, но упал на сервере;
- дошёл и выполнился, а потерялся только ответ.

Клиент не знает, какой из них случился. Если не ретраить, платёж может потеряться. Если ретраить, деньги могут списаться дважды. С `PUT` и `DELETE` ретрай безопасен, с `POST` нет.

`Idempotency-Key` делает `POST` идемпотентным вручную. Клиент генерирует уникальный ключ (обычно UUID v4) на одну логическую операцию и шлёт его в заголовке:

```http

Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

Сервер смотрит, видел ли он этот ключ раньше:

- ключ новый: выполняет операцию и сохраняет ключ вместе с ответом;
- ключ уже есть, операция завершена: отдаёт сохранённый ответ и ничего не выполняет заново;
- ключ есть, но первый запрос ещё обрабатывается: обычно 409 Conflict.

Подход популяризовал Stripe. В IETF есть черновик `draft-ietf-httpapi-idempotency-key-header`. Насколько я знаю, RFC он так и не стал, поэтому детали поведения у разных API отличаются.

## Где обычно косячат

**Ключ генерируется заново на каждый ретрай.** Тогда он бесполезен. Ключ создаётся один раз на операцию («оплатить заказ 42») и переиспользуется во всех попытках. Новая операция получает новый ключ.

**Нет атомарности.** Если сначала списать деньги, а потом записать ключ, то падение между этими шагами снова даёт дубль. Ключ и побочный эффект должны фиксироваться в одной транзакции. Если эффект во внешней системе, ключ нужно прокидывать туда же.

**Гонки.** Два одинаковых запроса пришли одновременно, оба проверили ключ, оба не нашли. Нужна блокировка или уникальный индекс, чтобы второй запрос упал на вставке.

**Тот же ключ, другое тело.** Это баг клиента. Надо хранить хэш тела рядом с ключом и при несовпадении отвечать ошибкой (обычно 422), а не молча отдавать старый ответ.

**Скоуп и TTL.** Ключ должен быть уникален в рамках клиента или аккаунта, иначе чужие ключи могут случайно совпасть. Хранить вечно не нужно: у Stripe, например, 24 часа. Ретраи за пределами этого окна уже будут считаться новыми запросами.

**Что сохранять.** Успешные ответы сохранять нужно. С 5xx решения разные. Если сохранить 5xx, клиент навсегда застрянет на ошибке. Если не сохранять, придётся гарантировать, что при ошибке побочный эффект откатился.

Короче, `Idempotency-Key` позволяет клиенту спокойно ретраить неидемпотентные операции, а сервер отвечает за то, чтобы операция выполнилась ровно один раз.

## Идемпотентность в HTTP

RFC 9110 относит к идемпотентным методы GET, HEAD, OPTIONS, PUT и DELETE. `PUT /users/42` с одним и тем же телом можно отправить пять раз, и пользователь будет в том же состоянии. `DELETE /orders/7` удалит заказ один раз, остальные вызовы ничего не изменят.

## Как работает Idempotency-Key

Клиент генерирует уникальный ключ (обычно UUID v4) на одну логическую операцию и передаёт его в заголовке. При ретраях отправляется тот же ключ.

```http
POST /payments HTTP/1.1
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
Content-Type: application/json

{"amount": 1000, "currency": "RUB"}
```

Сервер при первом запросе выполняет операцию и сохраняет ключ вместе с результатом. При повторе с тем же ключом операция не выполняется заново, клиент получает сохранённый ответ. Схему популяризировал Stripe, сейчас в IETF есть черновик стандарта `draft-ietf-httpapi-idempotency-key-header`.

## Что учесть на сервере

1. Ключ ограничивается областью клиента (аккаунт, API-ключ), иначе разные клиенты могут столкнуться.
2. Вместе с ключом хранится отпечаток запроса, например хеш тела. Тот же ключ с другим телом означает ошибку клиента, обычно отвечают 422.
3. Если запрос с этим ключом ещё выполняется, второй получает 409 и не запускает операцию параллельно. Нужна блокировка или уникальный индекс по ключу.
4. Запись о ключе и сам бизнес-эффект фиксируются атомарно, в одной транзакции. Иначе возможен сценарий, где платёж создан, а ключ не записан, и ретрай создаст второй.
5. У ключей есть срок жизни (у Stripe 24 часа), после него запись удаляется.
6. Ошибки валидации, случившиеся до начала выполнения, обычно не сохраняют, чтобы клиент мог исправить запрос и повторить с тем же ключом.

Частая ошибка на стороне клиента: генерировать новый ключ на каждую попытку. Тогда защита не работает, ключ должен создаваться один раз на операцию и переиспользоваться во всех её ретраях.

## Причина

Пул и `main()` работают в **разных event loop'ах**:

1. При импорте модуля `asyncio.get_event_loop()` создаёт loop A, и в нём через `run_until_complete` создаётся пул. Внутренние futures пула и сокеты соединений привязываются к loop A.
2. `asyncio.run(main())` всегда создаёт **новый** loop B и запускает `main()` в нём.
3. `process()` выполняется в loop B, а `pool.acquire()` ждёт future из loop A. Отсюда `got Future <Future pending> attached to a different loop`.

Так этот код сломан изначально. Если он работал, значит, раньше какой-то из этих факторов был другим.

## 1. Основная идея

PostgreSQL **не перезаписывает строку на месте**. Любое изменение создаёт новую **версию строки** (tuple):

- `INSERT` создаёт версию.
- `DELETE` помечает существующую версию как удалённую. Физически она остаётся на странице.
- `UPDATE` делает то же, что `DELETE` + `INSERT`: старая версия помечается удалённой, рядом создаётся новая.

Каждая транзакция смотрит на данные через **снапшот**, то есть через правило «какие транзакции для меня уже завершились». По этому правилу она сама решает, какую из версий видеть. Отсюда главное свойство: **читатели не блокируют писателей, писатели не блокируют читателей**.

Цена такого подхода в том, что старые версии копятся в таблице. Убирать их кто-то должен, и этим занимается VACUUM.

Undo-лога, как в Oracle или InnoDB, в PostgreSQL нет. Старые версии лежат прямо в heap, вперемешку с живыми. Почти все особенности PostgreSQL (bloat, VACUUM, HOT, wraparound) следуют из этого решения.

### 2.1. Что такое XID

- 32-битное беззнаковое число, растёт монотонно.
- **Выдаётся лениво**, только при первой записи: INSERT/UPDATE/DELETE, `SELECT FOR UPDATE`, DDL. Читающая транзакция получает лишь **virtual xid** (`backendID/localXID`) и счётчик XID не расходует. Это важно для wraparound: скорость «старения» базы определяется числом **пишущих** транзакций, а не всех подряд.
- Особые значения:
  - `0` — `InvalidTransactionId`;
  - `1` — `BootstrapTransactionId`;
  - `2` — `FrozenTransactionId`;
  - обычные XID начинаются с `3`.
- Внутри сервера есть 64-битный `FullTransactionId`: эпоха плюс 32-битный XID. Наружу он доступен как тип `xid8` через `pg_current_xact_id()`. **На диске в заголовке строки XID по-прежнему 32-битный**, и проблема wraparound возникает именно поэтому.

### 2.2. Статус транзакции: pg_xact (бывший pg_clog)

На каждую транзакцию отводится 2 бита: `IN_PROGRESS`, `COMMITTED`, `ABORTED`, `SUB_COMMITTED`. Данные лежат в SLRU-кэше и в файлах `pg_xact/`.

Подтранзакции (`SAVEPOINT`, блоки `EXCEPTION` в PL/pgSQL) получают собственные XID. Связь «подтранзакция → родитель» хранится в `pg_subtrans`.

### 2.3. Сравнение XID: модульная арифметика

XID сравниваются по кругу:

```c
/* упрощённо, TransactionIdPrecedes */
return (int32)(id1 - id2) < 0;
```

Для любого XID примерно 2³¹ (≈2,1 млрд) значений считаются «прошлым», а другие 2³¹ — «будущим». Подробнее об этом в разделе про wraparound.

## 3. Заголовок версии строки (HeapTupleHeader)

Каждая версия строки несёт примерно 23 байта служебных данных:

| Поле | Смысл |
|---|---|
| `t_xmin` | XID транзакции, создавшей версию |
| `t_xmax` | XID транзакции, удалившей или заблокировавшей версию (0, если таких не было) |
| `t_cid` | command id внутри транзакции: cmin, cmax или combo cid |
| `t_ctid` | ссылка на **следующую** версию той же строки (или на себя, если версия последняя) |
| `t_infomask` | флаги: hint bits, тип блокировки, multixact и т. п. |
| `t_infomask2` | число атрибутов, `HEAP_HOT_UPDATED`, `HEAP_ONLY_TUPLE`, `HEAP_KEYS_UPDATED` |

Посмотреть на это можно своими глазами:

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
CREATE TABLE t(id int, v text);
INSERT INTO t VALUES (1, 'a');
UPDATE t SET v = 'b' WHERE id = 1;

SELECT xmin, xmax, ctid, * FROM t;   -- видна только актуальная версия

SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid,
       t_infomask::bit(16), t_infomask2::bit(16)
FROM heap_page_items(get_raw_page('t', 0));
```

На странице окажутся обе версии. У первой `t_xmax` равен XID апдейта, а `t_ctid = (0,2)`. У второй `t_xmin` равен тому же XID, `t_xmax = 0`, `t_ctid = (0,2)`.

**Нюанс:** ненулевой `xmax` **не означает**, что строка удалена. Он бывает ненулевым у вполне видимой строки в трёх случаях:
- транзакция, удалявшая строку, откатилась;
- на строку брали блокировку (`SELECT FOR UPDATE/SHARE`), см. раздел 7;
- `xmax` содержит MultiXactId.

## 4. Снапшот

### 4.1. Из чего он состоит

Снапшот строится функцией `GetSnapshotData()` по данным ProcArray, общей таблицы активных бэкендов.

| Поле | Значение |
|---|---|
| `xmin` | наименьший XID, активный в момент снятия снапшота. Всё, что `< xmin`, уже завершено (коммитом или откатом) |
| `xmax` | `latestCompletedXid + 1`, первый ещё «не случившийся» XID. Всё, что `>= xmax`, для снапшота относится к будущему |
| `xip[]` | список XID из диапазона `[xmin, xmax)`, которые были активны на момент снапшота |
| `subxip[]` | активные подтранзакции (`suboverflowed`, если кэш переполнился) |
| `curcid` | текущий command id, нужен для видимости собственных изменений |

Текущий снапшот можно увидеть так: `SELECT pg_current_snapshot();`. Пример вывода: `100:105:100,102`.

### 4.2. Как XID проверяется против снапшота (`XidInMVCCSnapshot`)

```
if xid <  snap.xmin  → транзакция завершена до снапшота; дальше статус берётся из pg_xact
if xid >= snap.xmax  → транзакция «в будущем», её изменения не видны
if xid in snap.xip   → транзакция была активна, её изменения не видны
иначе                → транзакция завершена; статус берётся из pg_xact
```

Ключевая мысль: **снапшот не хранит список закоммиченных транзакций.** Он хранит только границы и список активных. Всё прочее вычисляется через pg_xact.

### 4.3. Когда снимается снапшот (уровни изоляции)

- **Read Committed** (по умолчанию): новый снапшот на **каждый оператор**. Поэтому два одинаковых SELECT внутри одной транзакции могут вернуть разные данные.
- **Repeatable Read**: один снапшот на всю транзакцию. Он снимается **при первом запросе, а не при `BEGIN`**. Это частая ловушка: `BEGIN ISOLATION LEVEL REPEATABLE READ; ... pause ...; SELECT` зафиксирует данные на момент SELECT.
- **Serializable**: тот же снапшот, что в RR, плюс SSI (Serializable Snapshot Isolation). SSI ставит предикатные блокировки `SIREAD`, отслеживает rw-зависимости между транзакциями и откатывает одну из них при обнаружении «опасной структуры», то есть двух подряд rw-рёбер в цикле. Возможны ложноположительные откаты.
- **Read Uncommitted** в PostgreSQL ведёт себя как Read Committed. Грязного чтения нет вообще.

Снапшотом можно поделиться: `pg_export_snapshot()` в одной транзакции и `SET TRANSACTION SNAPSHOT '...'` в другой. Так работает параллельный `pg_dump -j`.

### 4.4. Стоимость снапшота

`GetSnapshotData()` проходит по ProcArray. При тысячах соединений это заметно. В PG14 эту функцию серьёзно переработали: данные о XID лежат плотными массивами, а снапшот переиспользуется, если с прошлого раза не было коммитов (`xactCompletionCount`). Тем не менее огромное число соединений без пулера остаётся плохой идеей, в том числе из-за этого.

## 5. Правила видимости

Упрощённая логика `HeapTupleSatisfiesMVCC()`.

### 5.1. Проверка xmin: видна ли версия как созданная

```
if xmin — моя транзакция (или моя подтранзакция):
    if cmin >= curcid → не видна (вставлена этой же или более поздней командой)
    иначе переходим к проверке xmax
elif XidInMVCCSnapshot(xmin) → не видна (создатель ещё был активен)
elif xmin committed (pg_xact) → видна как созданная
else (aborted / crashed)      → не видна
```

### 5.2. Проверка xmax: не удалена ли версия

```
if xmax invalid / только блокировка (LOCK_ONLY) → видна
if xmax — моя транзакция:
    cmax >= curcid → видна (удалена командой, которая ещё «не случилась»)
    иначе          → не видна
if XidInMVCCSnapshot(xmax) → видна (удаляющий ещё не завершился для меня)
if xmax committed          → не видна
else (aborted)             → видна
```

### 5.3. Почему порядок проверок важен

Сначала проверяется снапшот, и только потом pg_xact. Причина в порядке действий при коммите: транзакция сначала пишет статус в pg_xact, а затем убирает себя из ProcArray. Если смотреть в pg_xact первым, можно увидеть `COMMITTED` у транзакции, которая для твоего снапшота ещё активна. Это нарушило бы изоляцию.

Для оператора, который не является снапшотным чтением (например, проверка уникальности), используется отдельная проверка `TransactionIdIsInProgress()`, тоже перед pg_xact.

### 5.4. Command ID: cmin, cmax, combo cid

Внутри одной транзакции видимость определяется номером команды. Именно поэтому `UPDATE t SET x = x + 1` не зацикливается на только что вставленных версиях (так называемая Halloween problem): новая версия имеет `cmin = текущей команде` и для этой же команды невидима.

Под `cmin` и `cmax` в заголовке есть только одно поле. Если одна транзакция и вставила, и удалила строку, туда пишется **combo cid**: индекс в локальной (backend-local) хэш-таблице пар `(cmin, cmax)`. Другим транзакциям эти значения не нужны: для них чужая незакоммиченная транзакция целиком невидима.

## 6. Hint bits: почему SELECT пишет на диск

Ходить в pg_xact за каждой строкой дорого. Поэтому, как только статус `xmin` или `xmax` выяснен окончательно, бэкенд кэширует его прямо в заголовке строки флагами из `t_infomask`:

- `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID`
- `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID`

Нюансы:

1. **Хинты выставляет первый, кто прочитал строку**, причём даже обычный `SELECT`. Страница становится dirty. Отсюда эффект «после массовой загрузки первый SELECT медленный и генерирует запись». Чтобы избежать этого, после загрузки стоит сделать `VACUUM` (или `VACUUM FREEZE`), а при загрузке использовать `COPY ... FREEZE`.
2. Сами по себе хинты в WAL не пишутся. Но при включённых `data_checksums` или `wal_log_hints = on` первая модификация страницы после чекпоинта порождает **full page image** в WAL. Чтение тогда начинает генерировать WAL.
3. При `synchronous_commit = off` хинт нельзя ставить, пока WAL не сброшен на диск дальше LSN коммит-записи. Иначе после краха на странице окажется «committed» у транзакции, которой фактически нет. Это проверяется в `SetHintBits()`.
4. Хинт «in progress» не кэшируется: этот статус временный.

## 7. Блокировки строк тоже живут в xmax

В PostgreSQL нет таблицы блокировок строк в памяти, иначе она переполнялась бы на миллионах строк. Блокировка записывается прямо в строку:

- `SELECT ... FOR UPDATE` пишет свой XID в `xmax` и ставит `HEAP_XMAX_LOCK_ONLY` и `HEAP_XMAX_EXCL_LOCK`. Это физическая модификация страницы, и транзакция получает настоящий XID.
- Уровни блокировок: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`. Обычный `UPDATE`, не трогающий ключевые колонки, берёт `NO KEY UPDATE`. Он совместим с `KEY SHARE`, которую берут проверки внешних ключей. Это сильно снижает конфликты FK.
- **MultiXact.** Если строку держат сразу несколько транзакций (например, несколько `FOR SHARE`, или `KEY SHARE` плюс апдейтер), в `xmax` пишется MultiXactId (`HEAP_XMAX_IS_MULTI`). Это ссылка в `pg_multixact/offsets` и `pg_multixact/members`. MultiXact имеет собственное 32-битное пространство и **собственный wraparound** (см. раздел 13).
- Ожидание блокировки устроено так: тот, кто наткнулся на чужой `xmax` от активной транзакции, ждёт на **блокировке XID этой транзакции** (каждая транзакция держит эксклюзивный lock на собственный XID). В `pg_locks` это видно как `locktype = transactionid`.

## 8. Конкурирующие UPDATE

Пусть T1 и T2 одновременно обновляют одну строку, и T1 успела первой.

**Read Committed.** T2 ждёт завершения T1.
- Если T1 откатилась, T2 обновляет исходную версию.
- Если T1 закоммитилась, T2 идёт по цепочке `t_ctid` к новейшей версии и **заново проверяет WHERE** на ней. Этот механизм называется EvalPlanQual. Если условие всё ещё выполняется, T2 обновляет новую версию.
- Отсюда известные аномалии RC: часть оператора работает по старому снапшоту, часть по новой версии строки. Например, `UPDATE ... SET balance = balance - 100 WHERE balance >= 100` проверит условие на новой версии, а вот подзапросы в том же операторе видят старый снапшот.

**Repeatable Read и Serializable.** Если T1 закоммитилась, T2 получает `ERROR: could not serialize access due to concurrent update`. Приложение обязано уметь повторять транзакцию.

## 9. HOT: Heap-Only Tuples

Без оптимизаций каждый UPDATE создаёт новую версию, а значит, новую запись **в каждом индексе**: индекс указывает на конкретный TID `(page, offset)`. Это дорого.

**HOT-обновление** применяется при двух условиях:
1. не изменилась ни одна колонка, входящая в индексы (с PG16 колонки только BRIN-индексов не мешают HOT);
2. новая версия помещается на **ту же страницу**.

Тогда новая версия получает флаг `HEAP_ONLY_TUPLE`, старая получает `HEAP_HOT_UPDATED`, и **в индексы ничего не пишется**. Индекс по-прежнему указывает на корень HOT-цепочки, а сканирование идёт по `t_ctid` внутри страницы.

**Page pruning** (`heap_page_prune`) работает «мимоходом», без VACUUM. Когда бэкенд читает страницу, на которой мало места (заполнена больше чем примерно на `max(fillfactor, 90%)`), он может вычистить мёртвые версии HOT-цепочек внутри страницы. Корневой line pointer превращается в `LP_REDIRECT` на живую версию, место от мёртвых освобождается. Line pointers, на которые ссылаются индексы, при этом остаются: их может освободить только VACUUM вместе с чисткой индексов.

Практические выводы:
- `fillfactor = 70–90` на часто обновляемых таблицах оставляет место для HOT.
- Не индексируйте лишнего: каждый индекс по обновляемой колонке убивает HOT.
- Доля HOT видна так: `pg_stat_user_tables.n_tup_hot_upd / n_tup_upd`.

## 10. Индексы и видимость

**В индексах нет информации о видимости**, то есть нет xmin и xmax. Поэтому:

- Index Scan всегда ходит в heap, чтобы проверить видимость.
- **Index Only Scan** может не ходить в heap, если страница помечена в **visibility map** как all-visible: все строки на ней видимы всем транзакциям. VM поддерживается VACUUM'ом. Без регулярного VACUUM index-only scan деградирует до обычного (в `EXPLAIN ANALYZE` смотрите `Heap Fetches`).
- B-tree помечает записи, указывающие на заведомо мёртвые строки, как `LP_DEAD` (killed tuples) прямо при сканировании и потом может их вычистить. Начиная с PG14 есть **bottom-up deletion**: перед сплитом страницы индекса B-tree пытается удалить дубликаты-версии, порождённые не-HOT апдейтами.

## 11. Горизонт удаления (xmin horizon)

Мёртвую версию можно физически удалить, только если её **не может увидеть ни один существующий или будущий снапшот**. Формально это значит, что `xmax` закоммичен и старше **горизонта**. Горизонт вычисляется как минимум из:

- `xmin` всех активных снапшотов во всех бэкендах (`pg_stat_activity.backend_xmin`) и XID активных транзакций (`backend_xid`);
- `xmin` и `catalog_xmin` **слотов репликации** (`pg_replication_slots`);
- `xmin`, присылаемого репликами при `hot_standby_feedback = on`;
- **подготовленных транзакций** (`pg_prepared_xacts`, 2PC).

Начиная с PG14 горизонты считаются раздельно: для каталога, для обычных таблиц, для временных таблиц, с учётом базы данных. Но долгоживущая транзакция в **любой** базе кластера всё равно влияет на shared-каталоги, а слоты влияют на всё.

### Кто держит горизонт

1. **Долгие транзакции**, особенно `idle in transaction`. Приложение открыло транзакцию и ушло думать. Лечится `idle_in_transaction_session_timeout`.
2. **Долгие запросы**: аналитика, `pg_dump` на RR-снапшоте.
3. **Брошенный слот репликации.** Это ещё и неограниченный рост WAL; частично защищает `max_slot_wal_keep_size`.
4. **Забытые prepared transactions.** Они переживают рестарт!
5. **`hot_standby_feedback = on`** с долгими запросами на реплике.

Диагностика:

```sql
-- бэкенды, держащие горизонт
SELECT pid, datname, usename, state, backend_xid, backend_xmin,
       age(backend_xmin) AS xmin_age, xact_start, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL OR backend_xid IS NOT NULL
ORDER BY greatest(age(backend_xmin), age(backend_xid)) DESC;

-- слоты
SELECT slot_name, active, xmin, catalog_xmin,
       age(xmin) AS xmin_age, age(catalog_xmin) AS catalog_xmin_age
FROM pg_replication_slots;

-- 2PC
SELECT gid, prepared, owner, database, age(transaction)
FROM pg_prepared_xacts;
```

Пока горизонт стоит, VACUUM отрабатывает, но ничего не удаляет. В `VACUUM VERBOSE` это видно по строке `dead row versions cannot be removed yet`, в логах autovacuum — по растущему `removable cutoff` / `oldest xmin` age.

## 12. VACUUM

### 12.1. Что он делает

1. **Удаляет мёртвые версии**, которые старше горизонта, и освобождает место для повторного использования внутри таблицы.
2. **Чистит индексы** от ссылок на удалённые строки.
3. **Обновляет visibility map**: биты all-visible и all-frozen.
4. **Обновляет free space map (FSM)**, чтобы INSERT и UPDATE знали, куда писать.
5. **Замораживает** старые версии. Это защита от wraparound, подробнее в разделе 13.
6. **Сдвигает `relfrozenxid` и `relminmxid`** таблицы, а затем `datfrozenxid` базы. Это позволяет обрезать pg_xact и pg_multixact.
7. Обновляет `reltuples` и `relpages`. Статистику распределений собирает не он, а `ANALYZE`.

### 12.2. Фазы обычного VACUUM

```
1. Сканирование heap.
   Страницы, помеченные all-visible в VM, пропускаются (кроме aggressive-режима).
   На каждой странице выполняется pruning; TID мёртвых строк копятся в памяти,
   при необходимости строки замораживаются.
2. Vacuum indexes.
   Каждый индекс полностью сканируется (для B-tree), ссылки на собранные TID удаляются.
3. Vacuum heap.
   Line pointers удалённых строк становятся LP_UNUSED.
   Если память под TID кончилась, шаги 2–3 повторяются циклом.
4. Cleanup индексов, обновление FSM/VM/pg_class.
5. Truncate.
   Если в хвосте файла пустые страницы, файл обрезается.
   Это единственный случай, когда обычный VACUUM возвращает место ОС.
   Нужен кратковременный ACCESS EXCLUSIVE lock, который может мешать репликам.
```

Нюансы:
- Память под TID задаётся `maintenance_work_mem` (для autovacuum — `autovacuum_work_mem`). До PG17 был жёсткий потолок 1 ГБ и плоский массив, так что на больших таблицах индексы сканировались несколько раз. В PG17 появился TidStore на radix tree: он намного компактнее, и лимита в 1 ГБ больше нет.
- Обычный VACUUM берёт `SHARE UPDATE EXCLUSIVE` и не мешает DML.
- `VACUUM FULL` **переписывает таблицу** целиком под `ACCESS EXCLUSIVE` и требует до двух объёмов таблицы на диске. Для боевых систем обычно лучше `pg_repack` или `pg_squeeze`.
- Опции: `INDEX_CLEANUP off` (быстро, но индексы не чистятся), `PARALLEL n` (параллельная чистка индексов, только ручной VACUUM), `SKIP_LOCKED`, `PROCESS_TOAST`, `BUFFER_USAGE_LIMIT` (PG16).
- Таблица `TOAST` вакуумится отдельно, у неё свои `relfrozenxid` и мёртвые строки.

### 12.3. Autovacuum

Таблица попадает в очередь, когда:

```
n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples
             (50)                         (0.2)
```

Дополнительные триггеры:
- С PG13 есть порог по вставкам: `autovacuum_vacuum_insert_threshold` / `_scale_factor`. Он нужен, чтобы insert-only таблицы получали VM и заморозку.
- В PG18 добавили `autovacuum_vacuum_max_threshold`, верхнюю границу порога. Иначе `0.2 * 1 млрд строк` означало бы, что VACUUM придёт только после 200 млн мёртвых строк.
- Принудительный запуск по возрасту `relfrozenxid` (см. раздел 13).

Типичные проблемы и настройки:
- `scale_factor = 0.2` слишком велик для больших таблиц. Его настраивают пер-табличным `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01)`.
- Throttling: `autovacuum_vacuum_cost_limit` / `_cost_delay`. Дефолты консервативны. С PG12 `cost_delay` равен 2 мс, но на быстрых дисках лимит часто поднимают.
- `autovacuum_max_workers` (по умолчанию 3) — это число воркеров на весь кластер, а cost limit делится между ними. Если добавить воркеров без увеличения лимита, каждый станет медленнее.
- Обычный autovacuum **уступает** блокировку: если кому-то нужен конфликтующий lock (например, DDL), воркер отменяется. Анти-wraparound autovacuum так не делает (см. раздел 13).

Мониторинг: `pg_stat_user_tables` (`n_dead_tup`, `last_autovacuum`, `autovacuum_count`), `pg_stat_progress_vacuum`, `log_autovacuum_min_duration = 0` (или небольшой порог) в логах. Реальный bloat оценивают через `pgstattuple`.

## 13. Wraparound и заморозка

### 13.1. Проблема

XID 32-битные и сравниваются по модулю 2³². Для текущей транзакции N всё, что лежит в пределах примерно 2³¹ «позади», считается прошлым, а остальное — будущим.

Пусть строка вставлена транзакцией 100 и с тех пор не трогалась. Когда счётчик уйдёт вперёд больше чем на 2³¹, её `xmin = 100` внезапно окажется «в будущем», и **строка станет невидимой**. Данные физически на месте, но для всех запросов их больше нет. Это и есть wraparound. Задача PostgreSQL — не допустить его любой ценой, вплоть до остановки записи.

### 13.2. Решение: freeze

Если `xmin` строки достаточно стар и закоммичен, VACUUM помечает её как **замороженную**: «видна всем, всегда, независимо от сравнения XID».

- До 9.4 `xmin` физически заменялся на `FrozenTransactionId = 2`.
- С 9.4 ставится комбинация флагов `HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID` (= `HEAP_XMIN_FROZEN`), а исходный `xmin` сохраняется для отладки и форензики.

Вместе с этим VACUUM замораживает и `xmax`. Если там стоит старый MultiXact или XID только блокировки, он заменяется или очищается.

### 13.3. Возраст и счётчики

- `pg_class.relfrozenxid` — гарантия «все XID в таблице не старше этого значения» (кроме замороженных).
- `pg_database.datfrozenxid` — минимум по таблицам базы.
- `age(xid)` — сколько транзакций прошло с этого XID.

```sql
SELECT datname, age(datfrozenxid) AS xid_age, mxid_age(datminmxid) AS mxid_age
FROM pg_database ORDER BY xid_age DESC;

SELECT c.oid::regclass AS rel, age(c.relfrozenxid) AS xid_age,
       mxid_age(c.relminmxid) AS mxid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;
```

Когда `datfrozenxid` сдвигается вперёд, сегменты pg_xact старше минимального `datfrozenxid` по кластеру удаляются. Поэтому заморозка нужна ещё и для того, чтобы pg_xact не рос бесконечно.

### 13.4. Параметры и уровни эскалации

Значения по умолчанию:

| Параметр | Дефолт | Что делает |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | строки моложе этого VACUUM не замораживает. Смысл в том, что их, вероятно, ещё обновят, и заморозка пропадёт впустую |
| `vacuum_freeze_table_age` | 150 млн | если `age(relfrozenxid)` больше этого значения, VACUUM становится **aggressive**: сканирует все страницы, не помеченные all-frozen в VM, а не только не all-visible |
| `autovacuum_freeze_max_age` | 200 млн | при превышении autovacuum запускается **принудительно**, даже при `autovacuum = off` для таблицы или кластера. В `pg_stat_activity` это видно как `autovacuum: VACUUM ... (to prevent wraparound)` |
| `vacuum_failsafe_age` (PG14+) | 1,6 млрд | аварийный режим: VACUUM отключает cost-throttling и пропускает чистку индексов, лишь бы быстрее сдвинуть `relfrozenxid` |

У MultiXact есть аналогичные параметры: `vacuum_multixact_freeze_min_age`, `vacuum_multixact_freeze_table_age`, `autovacuum_multixact_freeze_max_age` (по умолчанию 400 млн) и `vacuum_multixact_failsafe_age`. Кроме того, принудительный VACUUM может запуститься из-за **переполнения пространства members**, а не только из-за возраста ID.

Последние рубежи (значения для современных версий; в старых они были меньше):
- Примерно за **40 млн** транзакций до точки невозврата в лог и клиентам идут предупреждения `WARNING: database "x" must be vacuumed within N transactions`.
- Примерно за **3 млн** сервер **перестаёт выдавать новые XID**: `ERROR: database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение работает, запись нет. Это фактически авария.

### 13.5. Нюансы, о которые спотыкаются

1. **Анти-wraparound autovacuum не уступает блокировки.** Ваш `ALTER TABLE` (или любой DDL) встанет в очередь за ним, а за DDL встанут все остальные запросы к таблице. Классический сценарий внезапного «повисла таблица». Отменять такой VACUUM вручную можно, но он запустится снова, а возраст продолжит расти.
2. **Он может прийти в самый неудобный момент** и читать всю большую таблицу целиком. Поэтому на больших таблицах лучше делать плановый `VACUUM (FREEZE)` (или просто VACUUM с более ранним aggressive-порогом) в спокойное время, а не ждать 200 млн.
3. **Insert-only таблицы** до PG13 вообще не вакуумились по мёртвым строкам (их нет), и затем на них приходил гигантский анти-wraparound VACUUM. С PG13 их обрабатывает порог по вставкам.
4. **Бит all-frozen в VM** (с 9.6) позволяет aggressive VACUUM пропускать уже замороженные страницы. До 9.6 приходилось перечитывать всю таблицу.
5. **Оппортунистическая заморозка.** С PG16 VACUUM замораживает всю страницу, если при pruning всё равно пишется FPI (дополнительной записи почти не будет). В PG18 появилась «eager»-заморозка части all-visible страниц в обычном (не aggressive) VACUUM: `vacuum_max_eager_freeze_failure_rate`. Цель обоих механизмов — размазать стоимость заморозки и не копить её до aggressive-прохода.
6. **Горизонт мешает и заморозке.** Строку нельзя заморозить, пока её `xmin` не старше горизонта удаления. Транзакция, висящая неделю, блокирует не только чистку мусора, но и защиту от wraparound. В логах VACUUM видно, что `relfrozenxid` не двигается.
7. **Временные таблицы autovacuum не обрабатывает.** Сессия, которая держит temp-таблицу очень долго, может задрать `datfrozenxid`. Брошенные temp-таблицы от упавших сессий autovacuum умеет удалять.
8. **Подтранзакции тоже расходуют XID**, если внутри что-то пишется. PL/pgSQL-цикл с `EXCEPTION` на каждой итерации сжигает XID пачками.
9. **Восстановление после остановки записи.** В современных версиях не нужно идти в single-user mode (раньше это была стандартная рекомендация, теперь документация прямо её отговаривает). Правильная последовательность:
   1. найти и убрать то, что держит горизонт (prepared transactions, слоты, долгие сессии);
   2. запустить обычный `VACUUM`: он сам XID не потребляет. Начинать стоит с самых старых таблиц, например `vacuumdb --all --min-xid-age=...`, можно с `INDEX_CLEANUP off` для скорости;
   3. **не делать** `VACUUM FULL` и прочее, что требует XID.

### 13.6. А 64-битные XID?

Внутри давно есть `FullTransactionId`, а `xid8` доступен в SQL. Но в формате страницы XID остаётся 32-битным, ведь расширение заголовка каждой строки стоит места на диске. Патчи про 64-битные XID на диске годами обсуждаются; насколько я знаю, в основную ветку они не вошли, поэтому проблема wraparound по-прежнему актуальна. Если для вас это критично, проверьте состояние в свежем релизе: здесь я могу отставать от актуального положения дел.

## 14. Прочие нюансы

- **Подтранзакции и переполнение кэша.** В PGPROC кэшируется до 64 XID подтранзакций (`PGPROC_MAX_CACHED_SUBXIDS`). Если их больше, снапшот получает `suboverflowed = true`, и проверки видимости начинают ходить в `pg_subtrans`. Это SLRU с известными проблемами конкурентности, и на нагруженных системах всё может обвалиться по производительности. Особенно опасно на репликах. С PG17 размеры SLRU настраиваются (`subtransaction_buffers` и др.), но лучше просто не плодить сотни SAVEPOINT'ов в долгой транзакции.
- **Hot standby.** Реплика строит снапшоты из `KnownAssignedXids`, восстановленных по WAL. VACUUM на мастере может удалить строки, нужные запросу на реплике. Тогда реплика либо ждёт (`max_standby_streaming_delay`), либо отменяет запрос: `canceling statement due to conflict with recovery`. `hot_standby_feedback` устраняет конфликт, но переносит горизонт реплики на мастер, и мастер начинает пухнуть.
- **DDL не полностью MVCC-безопасен.** `TRUNCATE` и перезаписывающий `ALTER TABLE` создают новый файл. Транзакция на RR-снапшоте, которая ещё не трогала таблицу, после этого увидит её **пустой** или уже с новыми данными, а не версию на момент своего снапшота. Это задокументированное исключение.
- **Каталог читается особыми снапшотами** (catalog snapshot, `SnapshotSelf`, `SnapshotDirty` и т. п.), а не обычным MVCC-снапшотом транзакции. Поэтому изменения схемы, в отличие от данных, видны «сразу».
- **Порядок видимости не совпадает с порядком коммитов в WAL.** Транзакция может закоммититься раньше в WAL, но стать видимой позже другой. На мастере это незаметно, но это причина отдельных тонких аномалий между мастером и репликой.
- **Откат дешёвый.** Отмена транзакции — это просто запись `ABORTED` в pg_xact. Ничего не откатывается физически: созданные версии становятся мусором, который потом уберёт VACUUM. Оборотная сторона: отменённый массовый UPDATE оставляет после себя полную таблицу мусора.

## Короткое резюме

1. Каждая версия строки знает, кто её создал (`xmin`) и кто удалил или заблокировал (`xmax`).
2. Снапшот задаётся тремя элементами: `xmin`, `xmax` и списком активных транзакций. Видимость = (создатель закоммичен и «в прошлом» для снапшота) И (удаляющего нет, он откатился или «в будущем»).
3. Статусы транзакций лежат в pg_xact, а для скорости кэшируются в hint bits.
4. Старые версии копятся прямо в таблице. VACUUM удаляет те, что старше горизонта, а горизонт держит самая старая транзакция, слот или 2PC во всём кластере.
5. XID 32-битные и сравниваются по кругу. Поэтому старые строки обязательно нужно **замораживать**, иначе через ~2 млрд транзакций они «исчезнут». PostgreSQL защищается эскалацией: aggressive VACUUM → принудительный autovacuum → failsafe → запрет записи.
6. Главный практический враг почти всегда один и тот же: **то, что держит горизонт**. Это долгие и `idle in transaction` сессии, брошенные слоты репликации и забытые prepared transactions.

Если нужно, могу отдельно разобрать какой-то кусок глубже: например, пошагово пройти по `HeapTupleSatisfiesMVCC` в исходниках, разобрать SSI, или собрать демо-скрипт с `pageinspect`, где видно hint bits, HOT-цепочки и заморозку на живой странице.

### both (21890 chars)

MVCC в PostgreSQL хранит прямо в таблице несколько версий каждой строки, и каждая транзакция по своему снапшоту решает, какую версию видеть. VACUUM убирает версии, которые уже никому не видны, и замораживает старые xid, чтобы 32-битный счётчик транзакций при переполнении не превратил прошлое в будущее.

Ниже по слоям: от заголовка кортежа до wraparound.

## 1. Версии строк и заголовок кортежа

В heap-таблице строка существует как набор версий (tuple). У каждой версии есть заголовок `HeapTupleHeaderData` (23 байта плюс выравнивание). Для MVCC в нём важны поля:

| Поле | Смысл |
|---|---|
| `t_xmin` | xid транзакции, которая создала версию (INSERT или UPDATE) |
| `t_xmax` | xid транзакции, которая удалила или заблокировала версию; 0, если такой не было |
| `t_cid` | номер команды внутри транзакции (cmin/cmax, при необходимости combo CID) |
| `t_ctid` | физический адрес `(страница, слот)` этой версии или следующей версии в цепочке обновлений |
| `t_infomask`, `t_infomask2` | флаги: hint bits, признак блокировки, multixact, HOT и т.д. |

Операции на уровне версий:

- **INSERT** создаёт версию с `xmin = мой xid`, `xmax = 0`.
- **DELETE** ничего не стирает. Он записывает в `xmax` старой версии свой xid.
- **UPDATE** равен DELETE + INSERT: старой версии ставится `xmax`, создаётся новая версия с новым `xmin`, а `t_ctid` старой указывает на новую. Так получается цепочка версий.

В любой таблице это видно через системные столбцы:

```sql
SELECT xmin, xmax, ctid, * FROM t;
```

Подробнее, вместе с мёртвыми версиями, показывает `pageinspect`:

```sql
CREATE EXTENSION pageinspect;
CREATE TABLE t (id int, v text);
INSERT INTO t VALUES (1, 'a');
UPDATE t SET v = 'b' WHERE id = 1;

SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('t', 0));
```

Получатся две версии: первая с `t_xmax` = xid UPDATE и `t_ctid = (0,2)`, вторая с `t_xmax = 0` и `t_ctid = (0,2)`, то есть указывает сама на себя, что означает «последняя в цепочке».

Ненулевой `xmax` ещё не означает, что строка удалена. Транзакция удаления могла откатиться, а `SELECT ... FOR UPDATE/SHARE` тоже пишет свой xid в `xmax`, только с флагом `HEAP_XMAX_LOCK_ONLY`. Отличить эти случаи можно только по флагам и статусу транзакции.

### cmin/cmax и combo CID

Внутри одной транзакции xid одинаковый, и различать изменения приходится по номеру команды (CommandId). Каждый оператор получает `curcid`, и версия, созданная командой с номером ≥ текущего, этой команде не видна. Поэтому `UPDATE t SET x = x + 1` не обрабатывает повторно только что созданные им же версии (защита от Halloween problem).

На диске под cmin и cmax одно поле. Если транзакция и создала, и удалила одну версию, туда пишется combo CID: ключ в локальной для бэкенда таблице, которая хранит пару (cmin, cmax). Снаружи транзакции эти значения не нужны, поэтому хранить их на диске незачем.

## 2. Идентификаторы транзакций

xid 32-битный и выдаётся лениво, при первой записи. Транзакция, которая только читает, получает виртуальный xid (`vxid`, вида `backendID/localXID`) и счётчик не расходует. `pg_current_xact_id()` (раньше `txid_current()`) выдаёт xid принудительно, поэтому в тестах он расходует счётчик.

Зарезервированные значения: `0` Invalid, `1` Bootstrap, `2` Frozen. Обычные xid начинаются с 3.

Есть и 64-битное представление `FullTransactionId` (эпоха плюс xid, тип `xid8`), но в заголовке кортежа хранятся только 32 бита. Из-за этого и существует проблема wraparound.

### Статус транзакции: pg_xact и hint bits

Итог транзакции хранится в `pg_xact` (раньше `pg_clog`): 2 бита на xid, четыре состояния (in progress, committed, aborted, sub-committed). Это SLRU-кэш поверх файлов.

Ходить в `pg_xact` при каждой проверке видимости дорого, поэтому первый читатель, который узнал итог транзакции, записывает его в `t_infomask` кортежа как hint bits:

- `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID`
- `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID`

Следствия:

- Обычный `SELECT` может пачкать страницы и вызывать запись на диск. После массовой загрузки первое чтение таблицы часто оказывается заметно медленнее последующих.
- При включённых checksums или `wal_log_hints = on` первая установка hint bit на странице после checkpoint пишет в WAL full page image. Отсюда WAL-трафик от чтений.
- При `synchronous_commit = off` hint bit «committed» нельзя ставить, пока commit-запись не сброшена в WAL. Иначе после сбоя транзакция окажется откаченной, а hint bit будет утверждать обратное.

### Подтранзакции

SAVEPOINT и блоки `EXCEPTION` в PL/pgSQL создают подтранзакции со своими xid. Связь «подтранзакция → родитель» хранится в `pg_subtrans`. В PGPROC каждого бэкенда кэшируется до 64 subxid (`PGPROC_MAX_CACHED_SUBXIDS`). При переполнении снапшоты помечаются как suboverflowed, и проверка видимости для каждого подозрительного xid идёт через `pg_subtrans`. На нагруженных системах это даёт ожидания `SubtransSLRU` / `SubtransBuffer` и резкую деградацию. Хватает одной долгой транзакции с сотней savepoint'ов, чтобы замедлить всех.

## 3. Снапшот

Снапшот фиксирует, какие транзакции на момент его взятия считались завершёнными. Основные поля:

- `xmin`: самый старый xid, который ещё был активен. Все xid меньше него завершены, и их видимость определяется только тем, commit это был или abort.
- `xmax`: первый ещё не выданный xid (последний завершённый + 1). Все xid ≥ него для снапшота находятся в будущем и не видны.
- `xip[]`: список xid, активных в момент снапшота, из диапазона `[xmin, xmax)`.
- `subxip[]` и флаг suboverflowed для подтранзакций.
- `curcid` для своих же изменений.

Посмотреть снапшот:

```sql
SELECT pg_current_snapshot();   -- например 1000:1005:1001,1003
```

Здесь xid 1000 и 1002 (если он был) завершены, а 1001 и 1003 ещё шли в момент снапшота. Для этого снапшота 1004 завершился и виден, если закоммичен. Всё ≥ 1005 не видно.

Проверка «был ли xid активен для снапшота» (`XidInMVCCSnapshot`):

```
если xid < snap.xmin:          завершён, смотреть commit/abort
если xid >= snap.xmax:         будущее, считать активным (невидим)
иначе:                         активен, если xid в xip[] (или в subxip[])
```

### Тонкость: момент «коммита» для видимости

Транзакция становится видимой другим, когда её убирают из ProcArray, хотя запись в `pg_xact` появляется чуть раньше. Поэтому код видимости сначала проверяет «активен ли xid» (по снапшоту или ProcArray) и только потом смотрит в `pg_xact`. Если поменять порядок, найдётся окно, в котором транзакция в `pg_xact` уже committed, а в снапшоте ещё активна, и разные проверки дадут несогласованный ответ.

Снапшот берётся под `ProcArrayLock`. С PG14 построение снапшота сильно ускорили (кэширование, плотные массивы xid в ProcArray), так что при тысячах соединений это стало заметно дешевле.

## 4. Правила видимости

Упрощённая логика `HeapTupleSatisfiesMVCC`:

```
видима(tuple, snap):
    # кто создал версию
    если xmin заморожен:                        создание видно
    иначе если xmin это моя транзакция:
        если cmin >= snap.curcid:               невидима (вставлена позже текущей команды)
    иначе если xmin активен по снапшоту:        невидима
    иначе если xmin откатился:                  невидима
    # создание видно, теперь кто удалил
    если xmax пуст, откатился или LOCK_ONLY:    видима
    если xmax это моя транзакция:
        видима, если cmax >= snap.curcid
    если xmax активен по снапшоту:              видима (удаление ещё не случилось)
    иначе:                                      невидима (удаление закоммичено до снапшота)
```

Кроме MVCC-снапшотов в ядре есть служебные режимы видимости:

- `SnapshotDirty` видит и незакоммиченные версии. Он используется при проверке уникальности: если найдена строка с таким же ключом от активной транзакции, вставка ждёт её завершения.
- `SnapshotSelf`, `SnapshotAny`, `SnapshotToast`, а также катalog snapshot для системных таблиц, который обновляется чаще пользовательского.

## 5. Уровни изоляции

**Read Committed** (по умолчанию): новый снапшот на каждый оператор. Внутри одного оператора данные согласованы, между операторами нет.

**Repeatable Read**: снапшот берётся при первом операторе транзакции, не при `BEGIN`. Если между `BEGIN` и первым запросом прошло время, изменения за этот промежуток будут видны. Чтобы зафиксировать момент сразу, выполните любой запрос.

**Serializable**: снапшот как в RR плюс SSI (Serializable Snapshot Isolation). Чтения оставляют предикатные блокировки `SIREAD`, система отслеживает rw-зависимости между транзакциями и при опасной структуре (две смежные rw-зависимости) откатывает одну с `could not serialize access`. Приложение обязано уметь повторять транзакции.

**Read Uncommitted** в PostgreSQL ведёт себя как Read Committed. Грязного чтения нет.

### Конфликты записи

Если UPDATE или DELETE находит версию, у которой `xmax` принадлежит активной транзакции, он ждёт её завершения (на блокировке xid). Дальше:

- В **Read Committed**, если та транзакция закоммитилась, срабатывает EvalPlanQual: переход по `t_ctid` к последней версии строки, повторная проверка `WHERE` на ней и обновление уже её. Отсюда классические аномалии RC: оператор может обновить строку, которая на момент его снапшота условию не подходила, или пропустить строку, которая стала подходить, но не попала в исходную выборку.
- В **Repeatable Read / Serializable** при коммите конкурента возникает ошибка `could not serialize access due to concurrent update`.

### Блокировки строк и MultiXact

`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` пишут в `xmax` xid с флагом lock-only. Отдельной таблицы блокировок строк нет: блокировка хранится в самом кортеже. Если строку держат несколько транзакций сразу (например, несколько вставок в дочернюю таблицу, проверка FK которых берёт `FOR KEY SHARE` на родительскую строку), в `xmax` пишется MultiXactId с флагом `HEAP_XMAX_IS_MULTI`. Состав мультитранзакции хранится в `pg_multixact/offsets` и `pg_multixact/members`.

У MultiXactId те же 32 бита и та же проблема wraparound, об этом ниже.

## 6. Индексы и HOT

В индексных записях нет xmin/xmax. Индекс указывает на версии строки в heap, и при Index Scan видимость каждой найденной версии проверяется по heap. Поэтому:

- UPDATE в общем случае добавляет новую запись во все индексы, даже если индексированные колонки не менялись.
- Index Only Scan может не ходить в heap только для страниц, отмеченных all-visible в visibility map. Именно VACUUM ставит этот бит.
- Индексные сканы помечают записи, указывающие на мёртвые для всех версии, флагом `LP_DEAD` (kill bits), и следующие вставки в B-tree могут их удалить без VACUUM. С PG14 к этому добавилось bottom-up deletion для B-tree, которое срабатывает при «версионном» раздувании индекса.

**HOT (Heap-Only Tuple)** снимает основную часть этой нагрузки. Если ни одна индексированная колонка не изменилась и новая версия помещается на ту же страницу, индексы не трогаются: новая версия помечается `HEAP_ONLY_TUPLE`, старая `HEAP_HOT_UPDATED`, индекс продолжает указывать на корень цепочки. Шансы на HOT повышает `fillfactor` < 100: на странице остаётся место для новых версий. Долю HOT видно в `pg_stat_user_tables.n_tup_hot_upd` относительно `n_tup_upd`.

**Page pruning** (`heap_page_prune_opt`) выполняется при обычном чтении страницы, если она почти заполнена: мёртвые версии HOT-цепочек вычищаются, корневой line pointer превращается в redirect. Это внутристраничная уборка без VACUUM, но индексы она не трогает, и line pointers, на которые ссылаются индексы, остаются в состоянии `LP_DEAD` до VACUUM.

## 7. Горизонт: когда версия становится мёртвой

Версия мертва, если её удаление закоммичено и не существует снапшота, которому она ещё может быть видна. Граница задаётся горизонтом (OldestXmin): минимальным xmin среди всего, что может держать старые данные:

- `backend_xmin` и `backend_xid` в `pg_stat_activity`: открытые транзакции, в том числе `idle in transaction`, долгие запросы, курсоры, а в RR/Serializable вся транзакция целиком;
- подготовленные транзакции (`pg_prepared_xacts`), которые переживают рестарт;
- слоты репликации: `xmin` и `catalog_xmin` в `pg_replication_slots`, включая брошенные логические слоты;
- реплики с `hot_standby_feedback = on`, которые передают свой xmin на primary.

Один долгий снапшот останавливает очистку во всех таблицах базы, а для системных каталогов во всём кластере. С PG14 горизонты разделены по типам отношений (`GlobalVisState`: общие каталоги, каталоги, обычные данные, временные таблицы), так что, например, логический слот сдерживает в основном каталоги.

Защита: `idle_in_transaction_session_timeout`, `transaction_timeout` (PG17), `max_slot_wal_keep_size` для слотов, мониторинг возраста `backend_xmin`. Параметр `old_snapshot_threshold` удалён в PG17.

На репликах проблема зеркальная: VACUUM на primary удаляет версии, которые нужны запросу на реплике, и реплика либо задерживает применение WAL (`max_standby_streaming_delay`), либо отменяет запрос. `hot_standby_feedback` решает это ценой раздувания на primary.

## 8. Что делает VACUUM

### Удаление мёртвых версий

Обычный `VACUUM` (без FULL) работает с `ShareUpdateExclusiveLock` и не мешает чтению и записи:

1. **Сканирование heap.** Страницы, отмеченные в visibility map как all-visible, можно пропустить. На остальных выполняется pruning, а TID мёртвых line pointers собираются в память. Объём ограничен `maintenance_work_mem` / `autovacuum_work_mem`. До PG17 это был массив с потолком 1 ГБ, с PG17 используется TidStore на основе radix tree, он компактнее и потолка 1 ГБ не имеет.
2. **Очистка индексов.** Каждый индекс сканируется целиком (`ambulkdelete`), записи с собранными TID удаляются. Если память закончилась раньше конца heap, фазы 1–2 повторяются, и индексы проходятся ещё раз. Это главная причина медленного VACUUM больших таблиц с многими индексами.
3. **Второй проход по heap.** Line pointers переводятся из `LP_DEAD` в `LP_UNUSED`, место учитывается в free space map.
4. **Обрезка хвоста.** Если в конце файла есть пустые страницы, они отдаются ОС. Для этого нужна кратковременная `AccessExclusiveLock`, на репликах это может прерывать запросы. Отключается параметром `vacuum_truncate`.

Место внутри файла переиспользуется, но файл не сжимается, кроме хвоста. Вернуть место ОС может только перезапись таблицы: `VACUUM FULL` или `CLUSTER` (с `AccessExclusiveLock` на всё время), либо `pg_repack` / `pg_squeeze` с короткими блокировками.

### Visibility map

На каждую страницу в VM два бита: all-visible (все версии видны всем) и all-frozen (все версии заморожены). VACUUM их ставит, любая модификация страницы снимает. От all-visible зависят Index Only Scan и пропуск страниц обычным VACUUM, от all-frozen пропуск страниц агрессивным VACUUM.

С PG13 autovacuum запускается и по числу вставок (`autovacuum_vacuum_insert_threshold`, `..._scale_factor`). До этого append-only таблицы не получали VACUUM до anti-wraparound: VM не заполнялась, Index Only Scan не работал, а потом весь объём замораживался разом.

### Статистика и служебное

VACUUM обновляет `pg_class.relpages`, `reltuples`, `relallvisible`, сдвигает `relfrozenxid`/`relminmxid` и, через `datfrozenxid`, позволяет обрезать старые сегменты `pg_xact` и `pg_multixact`. Статистику для планировщика собирает ANALYZE (autovacuum запускает его отдельно по своим порогам).

### Autovacuum

Таблица попадает в очередь, когда `n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples` (по умолчанию 50 + 20%). Для таблицы на сотни миллионов строк 20% это слишком поздно, поэтому для больших таблиц scale factor обычно снижают на уровне таблицы:

```sql
ALTER TABLE big SET (autovacuum_vacuum_scale_factor = 0.01);
```

В PG18 появился `autovacuum_vacuum_max_threshold` (по умолчанию 100 млн), который ограничивает порог сверху.

Скорость ограничена cost-based delay: `autovacuum_vacuum_cost_limit` и `autovacuum_vacuum_cost_delay` (2 мс по умолчанию с PG12). Лимит делится между всеми работающими воркерами, так что увеличение `autovacuum_max_workers` без увеличения лимита каждый воркер замедляет. Обычный autovacuum уступает блокировкам: если кто-то ждёт конфликтующую блокировку, он отменяется. Anti-wraparound autovacuum не уступает.

## 9. Wraparound и заморозка

### Почему это проблема

xid сравниваются по модулю 2³²: для любого xid примерно 2³¹ значений считаются прошлым, 2³¹ будущим (`TransactionIdPrecedes` использует знаковую разность). Если версия строки с `xmin = 100` доживёт до момента, когда текущий xid уйдёт вперёд больше чем на 2³¹ (~2,1 млрд), её `xmin` окажется в будущем, и строка пропадёт из всех снапшотов. Данные физически на месте, но логически исчезли.

### Заморозка

Решение: пометить старую версию как замороженную, то есть видимую всем независимо от сравнения xid. До 9.4 VACUUM заменял `xmin` на `FrozenTransactionId` (2). С 9.4 ставится комбинация флагов `HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID` (`HEAP_XMIN_FROZEN`), а исходный xmin остаётся для диагностики. Замораживаются и `xmax`: lock-only и откаченные очищаются, MultiXact разрешаются или заменяются.

Заморозить можно только xid старше горизонта (OldestXmin). Поэтому долгая транзакция или брошенный слот мешают не только удалять мёртвые версии, но и защищаться от wraparound.

Для каждой таблицы хранится `pg_class.relfrozenxid`: все xid старше него в таблице гарантированно заморожены. `pg_database.datfrozenxid` это минимум по таблицам базы. Расстояние до wraparound измеряется функцией `age()`.

### Параметры заморозки

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | версии с xmin старше этого возраста VACUUM замораживает на обрабатываемых страницах |
| `vacuum_freeze_table_age` | 150 млн | при `age(relfrozenxid)` выше этого VACUUM становится агрессивным: читает все страницы, кроме all-frozen, включая all-visible |
| `autovacuum_freeze_max_age` | 200 млн | принудительный autovacuum «to prevent wraparound», даже при `autovacuum = off` |
| `vacuum_failsafe_age` (PG14) | 1,6 млрд | аварийный режим: VACUUM снимает cost delay, пропускает очистку индексов и делает только то, что нужно для сдвига relfrozenxid |

Как менялась логика заморозки:

- **PG9.6**: бит all-frozen в VM. До этого агрессивный VACUUM читал таблицу целиком.
- **PG16**: заморозка страницей целиком. Если на странице есть что замораживать обязательно, замораживается всё допустимое, а если pruning уже пишет FPI в WAL, страница замораживается заодно, поскольку запись почти бесплатна.
- **PG18**: eager scanning. Обычный, неагрессивный VACUUM в ограниченном объёме заходит на all-visible, но не all-frozen страницы и замораживает их (`vacuum_max_eager_freeze_failure_rate`). Это сглаживает тяжёлые проходы агрессивного VACUUM.

### Что происходит при приближении к краю

- Примерно за 40 млн xid до wraparound каждая выдача xid сопровождается WARNING `database "x" must be vacuumed within N transactions`.
- Примерно за 3 млн система отказывается выдавать новые xid: ошибка `database is not accepting commands that assign new XIDs to avoid wraparound data loss`. Чтение работает, запись нет.

Выход: найти и устранить то, что держит горизонт (долгая транзакция, prepared transaction, слот), затем выполнить `VACUUM` для самых старых таблиц. Старые инструкции требовали single-user mode, но в актуальной документации рекомендуется обычный VACUUM в многопользовательском режиме, так как VACUUM сам xid не расходует. Без устранения причины VACUUM не сдвинет relfrozenxid, сколько его ни запускай.

### MultiXact wraparound

У MultiXactId своя пара: `relminmxid` / `datminmxid`, `vacuum_multixact_freeze_min_age` (5 млн), `vacuum_multixact_freeze_table_age` (150 млн), `autovacuum_multixact_freeze_max_age` (400 млн). Отдельно может закончиться пространство members (тоже 32-битный адрес). При его заполнении PostgreSQL снижает эффективный порог и запускает anti-wraparound VACUUM раньше. Нагрузки с массовыми FK-вставками на «горячие» родительские строки или с частыми `FOR SHARE` попадают в эту ситуацию чаще, чем в обычный xid wraparound.

## 10. Мониторинг

Возраст по базам и таблицам:

```sql
SELECT datname, age(datfrozenxid) AS xid_age, mxid_age(datminmxid) AS mxid_age
FROM pg_database ORDER BY xid_age DESC;

SELECT c.oid::regclass, age(c.relfrozenxid) AS xid_age, mxid_age(c.relminmxid) AS mxid_age,
       pg_size_pretty(pg_total_relation_size(c.oid))
FROM pg_class c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY xid_age DESC LIMIT 20;
```

Кто держит горизонт:

```sql
SELECT pid, state, age(backend_xmin) AS xmin_age, xact_start, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY xmin_age DESC;

SELECT slot_name, active, age(xmin) AS xmin_age, age(catalog_xmin) AS catalog_xmin_age
FROM pg_replication_slots;

SELECT gid, prepared, age(transaction) FROM pg_prepared_xacts;
```

Состояние очистки:

```sql
SELECT relname, n_live_tup, n_dead_tup, n_tup_hot_upd, n_tup_upd,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

SELECT * FROM pg_stat_progress_vacuum;
```

Для точной оценки раздувания подходят `pgstattuple` и `pgstattuple_approx`. Оценки по статистике дают только порядок величины.

## 11. Места, где MVCC не работает

- `TRUNCATE` и DDL с перезаписью таблицы (`ALTER TABLE ... ALTER TYPE`, `VACUUM FULL`, `CLUSTER`) не MVCC-безопасны: конкурентная транзакция в Repeatable Read, взявшая снапшот до перезаписи, после неё увидит пустую таблицу. Это описано в разделе Caveats документации по MVCC.
- Последовательности нетранзакционны: `nextval` не откатывается, отсюда дыры в нумерации.
- Каталоги читаются через catalog snapshot, который обновляется чаще транзакционного, поэтому изменение схемы может стать видимым внутри RR-транзакции раньше, чем изменение данных.
- Снапшот можно экспортировать (`pg_export_snapshot()`) и импортировать в другой сессии (`SET TRANSACTION SNAPSHOT`). Так `pg_dump -j` получает согласованный дамп несколькими процессами.

### claudemd (21049 chars)

MVCC в PostgreSQL устроен так: UPDATE и DELETE не перезаписывают строку на месте, а оставляют старую версию и помечают её номерами транзакций. Каждый запрос по своему снапшоту решает, какие версии ему видны. Платить за это приходится мусором из мёртвых версий, его убирает VACUUM, и конечностью 32-битных номеров транзакций, отсюда wraparound.

Ниже по слоям, от байтов на странице до эксплуатационных последствий.

## 1. Номера транзакций (XID)

- XID это 32-битный счётчик. Выдаётся лениво: пока транзакция только читает, у неё есть лишь виртуальный идентификатор (`virtualxid`, вида `3/1234`), и настоящий XID не расходуется. Настоящий XID выдаётся при первой записи или при вызове `pg_current_xact_id()` / `txid_current()`.
- Зарезервированные значения: `0` это InvalidTransactionId, `1` это bootstrap, `2` это FrozenTransactionId. Обычные XID начинаются с 3.
- XID сравниваются по модулю 2³²: для любого XID примерно 2 млрд значений считаются «прошлым» и 2 млрд «будущим». Корень проблемы wraparound именно в этом.
- Подтранзакции (SAVEPOINT, блоки `EXCEPTION` в PL/pgSQL) получают собственные XID. Связь с родителем хранится в `pg_subtrans`.
- В памяти есть 64-битный `FullTransactionId` (эпоха плюс XID), его возвращает `pg_current_xact_id()`. В заголовках кортежей на диске XID остаётся 32-битным. Патчи на 64-битные XID на диске обсуждаются давно, но в основную ветку, насколько я знаю, не приняты.

## 2. Что лежит в заголовке версии строки

Каждая версия (tuple) в heap несёт заголовок `HeapTupleHeaderData`:

| Поле | Смысл |
|---|---|
| `t_xmin` | XID транзакции, создавшей версию (INSERT или новая версия при UPDATE) |
| `t_xmax` | XID транзакции, удалившей версию (DELETE, UPDATE) **или** заблокировавшей её (`SELECT FOR UPDATE/SHARE`); 0, если ничего не было |
| `t_cid` | номер команды внутри транзакции (cmin/cmax), нужен для видимости внутри своей же транзакции |
| `t_ctid` | ссылка (блок, позиция) на более новую версию; у последней версии указывает на себя |
| `t_infomask`, `t_infomask2` | битовые флаги |

Ключевые флаги `t_infomask`:

- `HEAP_XMIN_COMMITTED`, `HEAP_XMIN_INVALID`: hint bits, уже известный статус xmin. Если стоят оба, версия **заморожена** (с 9.4 заморозка ставит эти биты и оставляет исходный xmin для отладки, раньше xmin перезаписывался на 2).
- `HEAP_XMAX_COMMITTED`, `HEAP_XMAX_INVALID`: то же для xmax.
- `HEAP_XMAX_LOCK_ONLY`: xmax означает блокировку строки, удаления не было.
- `HEAP_XMAX_IS_MULTI`: в xmax записан MultiXactId (несколько блокировщиков), а не XID.
- `HEAP_KEYS_UPDATED`: обновлялись ключевые колонки, это влияет на конфликт `FOR KEY SHARE` с `FOR NO KEY UPDATE`.
- В `t_infomask2`: `HEAP_HOT_UPDATED` и `HEAP_ONLY_TUPLE` для HOT-цепочек.

Если xmin и xmax принадлежат одной транзакции (вставили и удалили в одной), в одном поле `t_cid` нужно хранить и cmin, и cmax. Тогда туда пишется **combo CID**: индекс в локальной для бэкенда таблице пар (cmin, cmax). Эта таблица живёт только в памяти бэкенда и после завершения транзакции не нужна.

Посмотреть всё это руками:

```sql
CREATE EXTENSION pageinspect;
CREATE TABLE t(id int, v text);
INSERT INTO t VALUES (1, 'a');
UPDATE t SET v = 'b' WHERE id = 1;

SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid,
       to_hex(t_infomask) AS infomask
FROM heap_page_items(get_raw_page('t', 0));
```

Будут две версии: у первой `t_xmax` равен XID апдейта, а `t_ctid` указывает на вторую.

## 3. Статус транзакций: CLOG и hint bits

Заголовок хранит только номер транзакции. Чем она закончилась, хранится отдельно, в **CLOG** (`pg_xact`): по 2 бита на XID, значения in progress, committed, aborted, sub-committed. Работа с ним идёт через SLRU-буферы в shared memory.

Чтобы не лезть в CLOG при каждом чтении, первый, кто увидел версию с уже завершённой транзакцией, проставляет hint bit (`HEAP_XMIN_COMMITTED` и т.п.) прямо в странице. Нюансы:

- Поэтому обычный `SELECT` может пачкать страницы и вызывать запись на диск. После массовой загрузки первый проход по таблице проставляет хинты и пишет почти всю таблицу заново.
- При включённых `data_checksums` или `wal_log_hints` первая установка хинта на странице после чекпоинта порождает full page image в WAL. Так `SELECT` генерирует WAL.
- Хинт ставится, только когда это безопасно. Для асинхронного коммита (`synchronous_commit = off`) хинт нельзя ставить, пока WAL коммита не сброшен на диск, иначе после краша на странице останется «committed» для транзакции, которой фактически нет.

## 4. Снапшот

Снапшот (`SnapshotData`) фиксирует, какие транзакции на момент его взятия уже завершились. Основные поля:

- `xmin`: самый старый XID, который был активен. Все XID меньше него завершены, и их статус берётся из CLOG.
- `xmax`: первый ещё не выданный XID (`latestCompletedXid + 1`). Всё, что `>= xmax`, началось после снапшота и невидимо.
- `xip[]`: XID, активные на момент снапшота, в интервале `[xmin, xmax)`.
- `subxip[]` и флаг `suboverflowed`: активные подтранзакции.
- `curcid`: номер текущей команды, для видимости своих изменений.

Строится снапшот в `GetSnapshotData()` проходом по ProcArray (массив активных бэкендов). Начиная с PG14 эта операция сильно оптимизирована для большого числа соединений, и снапшот может переиспользоваться, если с прошлого раза никто не коммитил.

`pg_current_snapshot()` показывает текущий снапшот в виде `xmin:xmax:xip_list`, например `100:105:101,103`. Читается так: 100 и раньше завершены, 101 и 103 ещё идут (их изменения не видны), 102 и 104 завершены (видны, если закоммичены), 105 и дальше не видны.

**Переполнение подтранзакций.** Каждый бэкенд кэширует в ProcArray до 64 XID подтранзакций (`PGPROC_MAX_CACHED_SUBXIDS`). Если у какой-то транзакции их больше, снапшоты всех бэкендов помечаются `suboverflowed`, и для проверки любого XID из интервала снапшота приходится лезть в `pg_subtrans`, чтобы найти родителя. На нагруженной системе это даёт резкий провал производительности (конкуренция за SLRU `pg_subtrans`). Типичный источник: цикл в PL/pgSQL с `BEGIN ... EXCEPTION` внутри или ORM, ставящий SAVEPOINT на каждый запрос. На репликах эффект проявляется ещё сильнее.

## 5. Правила видимости

Упрощённо логика `HeapTupleSatisfiesMVCC` выглядит так. Версия видна снапшоту, если выполнены оба условия.

**A. Создание видно:**
- xmin это наша транзакция, и `cmin < curcid` (вставлено предыдущей командой, не текущей); или
- xmin закоммичен **и** с точки зрения снапшота не активен: `xmin < snapshot.xmax` и xmin отсутствует в `xip[]` / `subxip[]`.

**B. Удаление не видно:**
- xmax пуст (`HEAP_XMAX_INVALID`); или
- xmax это только блокировка (`LOCK_ONLY`); или
- транзакция xmax откатилась; или
- xmax это наша транзакция, но `cmax >= curcid` (удаляем текущей командой, сама команда ещё видит строку); или
- xmax с точки зрения снапшота ещё активен или из будущего.

Тонкость в порядке проверок. Сначала смотрят, активен ли XID **с точки зрения снапшота** (`XidInMVCCSnapshot`), и только потом идут в CLOG. Транзакция могла закоммититься после взятия снапшота, и тогда в CLOG она уже committed, но снапшоту обязана казаться активной. В функциях, где снапшота нет (например, `HeapTupleSatisfiesUpdate`), сначала вызывается `TransactionIdIsInProgress()` по ProcArray, потом CLOG. При коммите статус пишется в CLOG раньше, чем транзакция убирается из ProcArray, и обратный порядок проверок дал бы гонку.

Кроме MVCC-снапшота есть и другие режимы видимости: `SnapshotSelf`, `SnapshotAny` (видит всё, используется VACUUM и `pageinspect`), `SnapshotDirty` (видит и незакоммиченное, нужен для проверки уникальности и FK), а также **catalog snapshot**, которым читаются системные каталоги. Поэтому DDL видна иначе, чем данные.

## 6. Уровни изоляции поверх снапшотов

- **Read Committed** (по умолчанию): новый снапшот на **каждый оператор**. Две одинаковые выборки в одной транзакции могут вернуть разное.
- **Repeatable Read**: снапшот берётся при первом операторе (не при `BEGIN`) и держится до конца транзакции. Фантомов в PostgreSQL на этом уровне тоже нет, это строже стандарта.
- **Serializable**: тот же снапшот плюс SSI. Отслеживаются rw-зависимости через предикатные блокировки (SIREAD), опасные структуры прерываются ошибкой сериализации. Блокировок на чтение нет.
- **Read Uncommitted** физически работает как Read Committed: грязного чтения в PostgreSQL нет.

**Конкурентная запись.** Допустим, UPDATE натыкается на строку, у которой xmax принадлежит другой активной транзакции. UPDATE ждёт её завершения (блокировкой на XID этой транзакции). Дальше:

- если та откатилась, продолжаем как ни в чём не бывало;
- если закоммитила, то в **Read Committed** срабатывает EvalPlanQual: по цепочке `t_ctid` находится свежая версия, условие `WHERE` проверяется на ней заново, и если оно всё ещё истинно, обновляется она. Отсюда известные аномалии RC: например, `UPDATE ... SET x = x + 1` не теряет инкременты, а сложный запрос с подзапросом может увидеть несогласованное состояние, потому что подзапрос не перевычисляется;
- в **Repeatable Read / Serializable** вылетает `could not serialize access due to concurrent update`, и транзакцию нужно повторить целиком. Приложение обязано уметь ретраить.

## 7. UPDATE, HOT и page pruning

UPDATE это фактически «пометить старую версию xmax'ом и вставить новую». Отсюда:

- Без оптимизаций каждый UPDATE добавляет запись во **все** индексы таблицы, даже если индексируемые колонки не менялись.
- **HOT (Heap-Only Tuple)**: если не менялась ни одна индексированная колонка и на той же странице есть место, новая версия кладётся на ту же страницу с флагом `HEAP_ONLY_TUPLE`, а индексы не трогаются. Индекс продолжает указывать на корень цепочки, а дальше поиск идёт по `t_ctid` внутри страницы. С PG16 изменение колонок только в «суммирующих» индексах (BRIN) HOT не ломает.
- Шансы на HOT повышает `fillfactor < 100`: на странице остаётся запас.
- **Page pruning** (`heap_page_prune`): при чтении страницы, если свободного места мало, бэкенд может прямо на ходу вычистить мёртвые HOT-версии и схлопнуть цепочку, превратив корневой line pointer в `LP_REDIRECT`. Это делается без VACUUM и без обращения к индексам. Указатели, на которые ссылаются индексы, pruning освободить не может: он только помечает их `LP_DEAD`, а окончательно освобождает их VACUUM после чистки индексов.
- В B-tree с PG13/14 есть дедупликация и bottom-up deletion: при угрозе расщепления страницы индекс сам пытается удалить записи, указывающие на мёртвые версии. Это сдерживает распухание индексов от не-HOT апдейтов.

## 8. Блокировки строк и MultiXact

`SELECT FOR UPDATE` пишет XID в xmax с флагом `LOCK_ONLY`: блокировка строки хранится в самой строке, отдельной таблицы блокировок для неё нет. Поэтому `FOR UPDATE` на миллионе строк не съедает память, зато пишет на диск каждую страницу.

Если строку держат несколько транзакций сразу (`FOR SHARE`, `FOR KEY SHARE`, их обычно ставят проверки FK) или блокировка совмещается с обновлением, в xmax пишется **MultiXactId**: ссылка в `pg_multixact` на список (XID, режим). У MultiXact есть собственный 32-битный счётчик и собственный wraparound, плюс отдельное пространство «members», которое тоже может кончиться. Нагрузки с интенсивными FK-проверками на одних и тех же родительских строках упираются именно сюда.

## 9. Горизонт: что считается «мёртвым»

Версия мертва для всех, когда её xmax закоммичен и старше любого снапшота, который ещё может существовать. Эта граница называется xmin horizon (в коде `GlobalVisState`, раньше `OldestXmin`). Её удерживают:

- `backend_xmin` и `backend_xid` каждого бэкенда в `pg_stat_activity`, включая сессии `idle in transaction`;
- долгие запросы и транзакции Repeatable Read;
- `xmin` и `catalog_xmin` слотов репликации (`pg_replication_slots`), в том числе брошенных;
- `hot_standby_feedback = on`: долгий запрос на реплике держит горизонт на мастере;
- подготовленные транзакции (`pg_prepared_xacts`), про которые забыли.

Горизонт **общий для всего кластера** (для пользовательских таблиц с PG14 считается в рамках базы, но слоты и feedback действуют глобально). Одна забытая транзакция в любой сессии мешает чистке во всех таблицах. В выводе `VACUUM VERBOSE` это видно как `dead but not yet removable` / `removable cutoff ... which was N XIDs old`.

Найти виновника:

```sql
SELECT pid, state, backend_xmin, age(backend_xmin) AS xmin_age,
       now() - xact_start AS xact_dur, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

SELECT slot_name, active, xmin, catalog_xmin,
       age(xmin), age(catalog_xmin)
FROM pg_replication_slots;

SELECT gid, prepared, age(transaction) FROM pg_prepared_xacts;
```

## 10. VACUUM: что он делает по шагам

Обычный (lazy) VACUUM работает без эксклюзивной блокировки (`ShareUpdateExclusiveLock`), не мешает чтению и записи:

1. **Проход по heap.** Пропускает страницы, отмеченные в visibility map как all-visible (если это не агрессивный режим). На остальных выполняет pruning, собирает TID мёртвых версий, замораживает подходящие кортежи.
2. **Чистка индексов.** Для каждого индекса вызывается `ambulkdelete` со списком мёртвых TID. Это полный проход по индексу. Если TID не помещаются в `maintenance_work_mem` / `autovacuum_work_mem`, приходится чистить индексы несколько раз. До PG17 был жёсткий потолок 1 ГБ и массив по 6 байт на TID, с PG17 используется компактный TidStore на radix tree, лимита в 1 ГБ больше нет. Индексы можно чистить параллельно (`VACUUM (PARALLEL n)`, у автовакуума такого режима нет).
3. **Второй проход по heap.** Line pointers мёртвых версий переводятся в `LP_UNUSED`, место становится доступным для новых вставок.
4. **Служебные структуры.** Обновляются FSM (карта свободного места), visibility map (биты all-visible и all-frozen), `relfrozenxid` / `relminmxid` в `pg_class`, статистика.
5. **Усечение хвоста.** Если в конце файла пустые страницы, VACUUM пытается их отрезать. Для этого на короткое время нужна `AccessExclusiveLock`, и на репликах это может прерывать запросы. Отключается через `vacuum_truncate = off` на таблице.

Важные следствия:

- Обычный VACUUM не возвращает место ОС (кроме хвоста): он делает его переиспользуемым внутри таблицы. Сжать таблицу может `VACUUM FULL` или `CLUSTER` (полная переписка под `AccessExclusiveLock`) либо `pg_repack` / `pg_squeeze` онлайн.
- **Visibility map** нужна не только VACUUM. Index-only scan может не ходить в heap только для all-visible страниц. Если VM устарела, «index only» на деле читает heap (это видно в `Heap Fetches` в `EXPLAIN ANALYZE`).
- `INSERT`-only таблицы до PG13 почти не вакуумились автоматически. Из-за этого VM не обновлялась, index-only scan деградировал, а заморозка копилась до огромного агрессивного прохода. С PG13 есть `autovacuum_vacuum_insert_threshold` / `_scale_factor`.

**Autovacuum** запускается для таблицы, когда

```
n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples
```

(по умолчанию 50 + 20%). Для больших таблиц 20% это очень много, поэтому `scale_factor` обычно снижают на уровне конкретных таблиц. В PG18 появился `autovacuum_vacuum_max_threshold`, верхняя граница для этого порога. Скорость ограничивают `autovacuum_vacuum_cost_limit` / `cost_delay`. Значения по умолчанию рассчитаны на медленные диски, на SSD их почти всегда стоит ослабить, иначе автовакуум не успевает за нагрузкой. Обычный автовакуум уступает место: если кому-то нужна конфликтующая блокировка на таблицу, он отменяется сам. Поэтому частые DDL или `LOCK TABLE` могут годами не давать ему закончить.

## 11. Заморозка и wraparound

**Проблема.** Сравнение XID идёт по кругу. Версия с `xmin = 100` видна, пока 100 находится «в прошлом». Если счётчик уйдёт на 2³¹ вперёд, тот же 100 окажется «в будущем», и строка внезапно станет невидимой: данные формально целы, но пропали из всех запросов.

**Решение: заморозка.** Достаточно старые закоммиченные версии помечаются как frozen, и такая версия видна всем навсегда, независимо от сравнения XID. После заморозки старый XID можно безопасно переиспользовать.

Учёт ведётся так:

- `pg_class.relfrozenxid`: все XID в таблице не старше этого значения (всё более старое уже заморожено).
- `pg_database.datfrozenxid`: минимум `relfrozenxid` по базе.
- CLOG старше минимального `datfrozenxid` по кластеру можно удалять, поэтому `pg_xact` и усекается после вакуумов.

Параметры:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | версии старше этого возраста замораживаются при обычном проходе |
| `vacuum_freeze_table_age` | 150 млн | если `age(relfrozenxid)` больше, VACUUM становится **агрессивным**: читает все страницы, которые не all-frozen, включая all-visible |
| `autovacuum_freeze_max_age` | 200 млн | при превышении запускается принудительный антивраппаунд-автовакуум, **даже если autovacuum выключен** |
| `vacuum_failsafe_age` | 1,6 млрд | (PG14+) аварийный режим: отключаются задержки, пропускается чистка индексов, лишь бы успеть заморозить |
| `vacuum_multixact_*`, `autovacuum_multixact_freeze_max_age` | 5 млн / 150 млн / 400 млн | то же для MultiXact |

Нюансы, на которые чаще всего напарываются:

- **Антивраппаунд-автовакуум не уступает блокировки.** В `pg_stat_activity` он виден как `autovacuum: VACUUM ... (to prevent wraparound)`. Если в этот момент приходит `ALTER TABLE`, он встаёт в очередь за вакуумом, а за ним выстраиваются все остальные запросы к таблице. Внезапная «блокировка всего» на большой таблице часто объясняется именно этим.
- **Шторм заморозки.** Таблица, загруженная одним большим батчем, имеет почти одинаковые xmin. Через ~200 млн транзакций ей нужен агрессивный проход целиком, со всем I/O и записью в WAL. С PG16 заморозка идёт постранично (если на странице что-то замораживается, замораживается всё, что можно) и есть оппортунистическая заморозка, когда full page image и так пишется. В PG18 добавлено «нетерпеливое» сканирование all-visible страниц обычным вакуумом (`vacuum_max_eager_freeze_failure_rate`), чтобы размазать заморозку во времени. Это сглаживает проблему, но не отменяет её.
- Агрессивный вакуум тоже не может заморозить то, что моложе горизонта. Если горизонт держит забытая транзакция или слот, `relfrozenxid` не двигается, сколько вакуум ни гоняй. Сначала ищется и устраняется держатель горизонта (раздел 9), потом вакуум.
- **Последние рубежи.** Когда до wraparound остаётся 40 млн XID, в лог и клиентам идут предупреждения. Когда остаётся 3 млн (так с PG14, раньше было 1 млн), сервер перестаёт выдавать новые XID: `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Читать можно, писать нельзя. Раньше документация предписывала выход в single-user mode. С PG16 рекомендуется обычный `VACUUM` (без `FULL` и без `FREEZE`, чтобы не делать лишнего) в обычном режиме от суперпользователя по таблицам с наибольшим возрастом, после устранения держателя горизонта.
- **Временные таблицы** автовакуум не обрабатывает вообще: он не видит чужие временные таблицы. Долгоживущая сессия с временной таблицей, в которую много пишут, способна сама держать `datfrozenxid`.

Мониторинг:

```sql
-- Возраст по базам
SELECT datname, age(datfrozenxid), mxid_age(datminmxid)
FROM pg_database ORDER BY 2 DESC;

-- Самые «старые» таблицы в текущей базе
SELECT c.oid::regclass, age(c.relfrozenxid), mxid_age(c.relminmxid),
       pg_size_pretty(pg_total_relation_size(c.oid))
FROM pg_class c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;

-- Что сейчас делает вакуум
SELECT * FROM pg_stat_progress_vacuum;
```

Алерт обычно ставят на `age(datfrozenxid)` примерно на 500 млн–1 млрд: это далеко выше нормального порога автовакуума, но с большим запасом до 2 млрд.

## 12. Что не подчиняется MVCC

- **Последовательности**: `nextval` не откатывается и виден всем сразу, отсюда дыры в id.
- **`TRUNCATE`** и переписывающие `ALTER TABLE` не MVCC-безопасны. Транзакция Repeatable Read, взявшая снапшот до них, увидит таблицу пустой (документация прямо это оговаривает).
- **Advisory locks** и `pg_notify`: свои правила, не через снапшот.
- **Системные каталоги** читаются catalog snapshot, который обновляется чаще транзакционного. Поэтому новые объекты бывают видны внутри уже идущей RR-транзакции.

## Как это связывается в эксплуатации

Почти все практические проблемы MVCC сводятся к трём цепочкам:

1. Долгая или забытая транзакция, слот или prepared xact держит горизонт → VACUUM не может удалить мёртвые версии → bloat таблиц и индексов, деградация index-only scan.
2. Тот же держатель горизонта или слабо настроенный автовакуум → `relfrozenxid` не продвигается → антивраппаунд-вакуумы, блокировки с DDL, в пределе остановка записи.
3. Частые не-HOT апдейты и подтранзакции → лишняя нагрузка на индексы и `pg_subtrans`, которую не видно в плане запроса.

Отсюда стандартный набор мер: `idle_in_transaction_session_timeout` и разумный `statement_timeout`, мониторинг `backend_xmin` и слотов (плюс `max_slot_wal_keep_size`), понижение `autovacuum_vacuum_scale_factor` и ослабление cost limit для больших и горячих таблиц, `fillfactor` под HOT для часто обновляемых таблиц и алерт на возраст `datfrozenxid`.

### current (23288 chars)

## Базовая идея

Postgres не перезаписывает строку на месте. UPDATE создаёт новую версию (tuple) и помечает старую как удалённую транзакцией X. DELETE только ставит пометку. Обе версии лежат в heap, пока VACUUM не уберёт мёртвую. Каждая транзакция по своему снапшоту решает, какую версию ей видеть.

Отсюда главный плюс: читатели не блокируют писателей, и наоборот. Цена у этого тоже есть. Мусор копится в таблицах и индексах, его надо убирать, а 32-битные счётчики транзакций надо периодически «замораживать».

Информация о видимости хранится только в heap. В индексах нет ни xmin, ни xmax. Это объясняет половину того, что будет дальше.

## Заголовок версии строки

У каждого tuple есть заголовок `HeapTupleHeaderData` на 23 байта (с выравниванием 24):

- `t_xmin`: xid транзакции, которая создала версию.
- `t_xmax`: xid транзакции, которая удалила или заблокировала версию. 0, если таких не было.
- `t_cid`: номер команды внутри транзакции (cmin/cmax, про них ниже).
- `t_ctid`: физический адрес (страница, слот). У актуальной версии он указывает на неё саму, у обновлённой на следующую версию. По этой цепочке UPDATE находит свежую версию.
- `t_infomask`, `t_infomask2`: флаги, в том числе hint bits.

Руками это выглядит так:

```sql
CREATE TABLE t (id int PRIMARY KEY, v text);
INSERT INTO t VALUES (1, 'a');
SELECT ctid, xmin, xmax, * FROM t;
-- (0,1) | 752 | 0 | 1 | a

UPDATE t SET v = 'b' WHERE id = 1;
SELECT ctid, xmin, xmax, * FROM t;
-- (0,2) | 753 | 0 | 1 | b

CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid,
       heap_tuple_infomask_flags(t_infomask, t_infomask2)
FROM heap_page_items(get_raw_page('t', 0));
-- lp 1: xmin 752, xmax 753, ctid (0,2), HEAP_HOT_UPDATED
-- lp 2: xmin 753, xmax 0,   ctid (0,2), HEAP_ONLY_TUPLE
```

Старая версия физически на месте. Обычный SELECT её просто не показывает.

## XID, CLOG и hint bits

xid занимает 32 бита и выдаётся лениво: только когда транзакция впервые что-то пишет или явно вызывает `pg_current_xact_id()`. Читающая транзакция обходится virtual xid и номера не расходует. Несколько значений зарезервированы: 0 (invalid), 1 (bootstrap), 2 (frozen). Обычные xid начинаются с 3.

Статус транзакции хранится в `pg_xact` (CLOG): 2 бита на xid, четыре состояния: in progress, committed, aborted, sub-committed. Лезть в CLOG при проверке каждой строки дорого, хоть он и кэшируется в SLRU. Поэтому первый, кто выяснил статус, записывает его прямо в строку hint-битами: `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID` и аналогичные флаги для xmax.

Последствия:

- SELECT после большой вставки пишет на диск, потому что грязнит страницы hint-битами. С data checksums или `wal_log_hints` первая такая правка страницы после чекпойнта ещё и даёт full page image в WAL. Отсюда классический вопрос «почему мой SELECT генерит WAL».
- При `synchronous_commit = off` hint COMMITTED нельзя ставить, пока WAL не сброшен дальше коммит-записи. Иначе после краша останется строка, помеченная committed, от транзакции, которой не существует.

Момент коммита устроен так: commit record пишется в WAL, затем статус в CLOG, затем транзакция удаляется из ProcArray. Для остальных она становится видимой только на последнем шаге. Между вторым и третьим шагом есть окно: CLOG уже говорит committed, а для чужих снапшотов транзакция ещё идёт. Поэтому код видимости сначала проверяет снапшот и только потом CLOG, и порядок здесь принципиален.

С синхронной репликацией так же: пока ждём ack от реплики, транзакция висит в ProcArray и никому не видна. Если ожидание отменить, придёт warning «transaction has already committed locally», и изменения станут видны, хотя на реплику могли не доехать.

## Снапшот

Снапшот по сути состоит из трёх полей:

- `xmin`: самый старый xid, который на момент снимка ещё выполнялся. Всё, что меньше, гарантированно завершено.
- `xmax`: `latestCompletedXid + 1`. Всё, что `>= xmax`, на момент снимка не завершилось и невидимо.
- `xip[]`: xid из интервала `[xmin, xmax)`, которые были активны. Для подтранзакций есть отдельный `subxip[]`.

```sql
SELECT pg_current_snapshot();
-- 752:760:753,757
```

Проверка `XidInMVCCSnapshot(xid)` отвечает на вопрос «для меня эта транзакция ещё идёт?»:

```
xid <  snap.xmin  -> нет, статус берём из CLOG / hint bits
xid >= snap.xmax  -> да
иначе             -> да, если xid есть в xip
```

Снапшот хранит только активные транзакции, закоммиченные в нём не перечисляются. Поэтому он компактный, а статус завершённых транзакций берётся из CLOG.

Снапшот снимается функцией `GetSnapshotData`: она проходит по ProcArray под `ProcArrayLock` в shared-режиме. До 14-й версии на сотнях соединений это было узким местом. В 14 механизм переделали: плотные массивы xid и переиспользование снапшота, если с прошлого раза никто не закоммитился.

## Алгоритм видимости

Упрощённый `HeapTupleSatisfiesMVCC`:

```
1. xmin
   frozen                          -> ok, к шагу 2
   aborted (hint или CLOG)         -> невидима
   xmin == моя транзакция:
       cmin >= curcid              -> невидима (вставлена более поздней командой)
       иначе                       -> к шагу 2
   XidInMVCCSnapshot(xmin)         -> невидима
   по CLOG не committed            -> невидима, ставим XMIN_INVALID
   committed                       -> ставим XMIN_COMMITTED, к шагу 2

2. xmax
   пусто / aborted / только lock   -> видима
   xmax == моя транзакция:
       cmax >= curcid              -> видима (удалю позже)
       иначе                       -> невидима
   XidInMVCCSnapshot(xmax)         -> видима (удаление для меня ещё не случилось)
   committed                       -> невидима
   aborted                         -> видима
```

Если в xmax лежит multixact, из него достаётся xid обновляющей транзакции, если такая есть.

Из алгоритма следуют три вещи:

- `xmax != 0` ещё не значит, что строка удалена. Это может быть откаченное удаление или просто блокировка.
- Транзакция, которую застал краш, остаётся в CLOG со статусом in progress. Но в ProcArray её нет, поэтому она считается aborted.
- ROLLBACK мгновенный: физически ничего не откатывается, транзакция просто помечается aborted. Мусор после неё убирает VACUUM.

## Свои изменения: cmin/cmax и combo cid

Команды внутри транзакции нумеруются (CommandId, 32 бита), и снапшот несёт текущий `curcid`. Так решается Halloween problem: `UPDATE t SET x = x + 1` не видит версий, которые только что создал сам, иначе обновлял бы их по кругу. Следующая команда той же транзакции их уже видит.

Поле `t_cid` в заголовке одно, на 4 байта. Если транзакция и создала, и удалила строку, нужны оба значения, cmin и cmax. Тогда в `t_cid` пишется combo cid: индекс в локальной хеш-таблице бэкенда, где лежат пары (cmin, cmax). Другим транзакциям cid не нужен, поэтому локальной таблицы хватает.

## Уровни изоляции

**Read Committed** (по умолчанию). Новый снапшот берётся на каждый statement. В plpgsql VOLATILE-функция берёт новый снапшот на каждый запрос внутри себя, а STABLE и IMMUTABLE работают в снапшоте вызывающего запроса.

**Repeatable Read.** Один снапшот на всю транзакцию, и берётся он на первом statement, а BEGIN его не создаёт. Если открыть RR-транзакцию и минуту ничего не делать, снапшота ещё нет. Фантомов в постгресовом RR нет (это строже стандарта), а write skew возможен.

**Serializable.** RR плюс SSI. Rw-зависимости отслеживаются через predicate locks (`SIReadLock` в `pg_locks`). При опасной структуре, то есть двух rw-конфликтах подряд, одна транзакция получает serialization failure. Ретраи на клиенте обязательны.

**Read Uncommitted** в Postgres ведёт себя как Read Committed.

### Конкурентный UPDATE

UPDATE нашёл строку по своему снапшоту, а у неё в xmax xid живой транзакции. Тогда он ждёт эту транзакцию (в `pg_locks` это видно как `transactionid`). Дальше три варианта:

- Та откатилась: обновляем исходную версию.
- Та закоммитила, уровень RC: идём по `t_ctid` к новой версии, перепроверяем WHERE уже на ней (EvalPlanQual) и, если условие выполняется, обновляем её. Поэтому `SET balance = balance + 10` из двух сессий даёт +20 без потерянного обновления.
- Та закоммитила, уровень RR или Serializable: `ERROR: could not serialize access due to concurrent update`.

У EPQ в RC есть побочка. Внутри одного statement часть строк вы видите по снапшоту, а перепроверенные строки по свежему состоянию. Строка, которая в новой версии перестала подходить под WHERE, будет пропущена. Строка, которая стала подходить только в новой версии, не найдётся вовсе, потому что поиск шёл по старому снапшоту. С `UPDATE ... FROM` и джойнами эффекты ещё страннее.

## xmax и блокировки строк, multixact

`SELECT FOR UPDATE / NO KEY UPDATE / SHARE / KEY SHARE` не держат блокировки в lock manager, их там было бы слишком много. Вместо этого они пишут свой xid в xmax строки с флагом `HEAP_XMAX_LOCK_ONLY` и битами режима. Значит, SELECT FOR UPDATE модифицирует страницу, пишет WAL и тратит xid.

Если строку держат сразу несколько транзакций (несколько FOR SHARE, или KEY SHARE вместе с UPDATE), в xmax кладётся MultiXactId с флагом `HEAP_XMAX_IS_MULTI`. Список участников с режимами лежит в `pg_multixact/offsets` и `members`.

Главный источник мультиксактов на практике: внешние ключи. Проверка FK при вставке в дочернюю таблицу берёт `FOR KEY SHARE` на родительской строке. Много параллельных вставок детей одного родителя порождают поток мультиксактов. Обычный UPDATE, который не трогает ключевые колонки, берёт `FOR NO KEY UPDATE`. Этот режим с KEY SHARE не конфликтует; его ввели в 9.3 как раз из-за FK.

Мультиксакты тоже 32-битные, и wraparound у них свой. Про него ниже.

## Индексы, HOT, pruning

Индексная запись хранит TID и о видимости ничего не знает. Индекс может указывать на мёртвую версию, тогда index scan сходит в heap и там проверит. Index-only scan обходится без heap только для страниц, помеченных all-visible в visibility map.

**UPDATE без HOT** создаёт новую версию в heap и новую запись в каждом индексе таблицы, даже если колонки этого индекса не менялись. Получается write amplification.

**HOT (heap-only tuple).** Если не изменилась ни одна индексированная колонка и новая версия влезает на ту же страницу, индексы не трогаются вообще. Старая версия получает флаг `HEAP_HOT_UPDATED`, новая `HEAP_ONLY_TUPLE`. Индекс продолжает указывать на корень цепочки, дальше переход идёт по `t_ctid`. С 16-й версии summarizing-индексы (BRIN) HOT не ломают.

Поэтому для часто обновляемых таблиц ставят `fillfactor` меньше 100: так на странице остаётся место под HOT. Долю HOT-обновлений видно по `n_tup_hot_upd` относительно `n_tup_upd` в `pg_stat_user_tables`.

**Page pruning.** Любой бэкенд при чтении страницы может её подчистить (`heap_page_prune_opt`), если свободного места мало и есть версии, мёртвые для всех. Мёртвые HOT-версии удаляются целиком, корень цепочки становится `LP_REDIRECT`, страница дефрагментируется. Line pointer'ы, на которые ссылаются индексы, pruning может только пометить `LP_DEAD`. Перевести их в `LP_UNUSED` может только VACUUM, после того как вычистит индексы.

В btree есть и свои механизмы очистки:

- `kill_prior_tuple`: index scan помечает индексную запись мёртвой, если увидел в heap, что версия мертва для всех.
- bottom-up deletion (с 14): перед сплитом страницы индекс пытается выкинуть дубли-версии.

## Горизонт: кто держит мусор

Мёртвую версию можно удалить физически, только если её xmax закоммичен и старше горизонта, то есть самого старого xmin, который ещё может кому-то понадобиться. Горизонт держат:

- открытые транзакции с xid (`backend_xid` в `pg_stat_activity`);
- снапшоты (`backend_xmin`): долгие запросы, RR-транзакции, открытые курсоры;
- idle in transaction. Нюанс: в RC сессия, которая только читала, между запросами обычно отпускает снапшот. Если же она что-то записала, её xid держит горизонт до конца транзакции;
- забытые prepared transactions (`PREPARE TRANSACTION` без COMMIT PREPARED). Они держат горизонт вечно и переживают рестарт;
- слоты репликации через `xmin` и `catalog_xmin`. Неактивный слот держит горизонт бесконечно;
- реплики с `hot_standby_feedback = on`: их долгие запросы держат горизонт мастера.

С 14-й версии горизонтов несколько: для системного каталога, для обычных таблиц и для temp-таблиц. Логический слот через `catalog_xmin` держит только каталог. Горизонт для обычных таблиц считается по транзакциям своей базы, а слоты и walsender'ы влияют на все базы.

Если горизонт стоит, VACUUM всё равно работает, тратит IO и ничего не удаляет. В `VACUUM VERBOSE` и логах autovacuum это видно по строке `N are dead but not yet removable, oldest xmin: X`.

## VACUUM

Обычный (lazy) VACUUM работает по фазам:

1. **Скан heap.** Страницы, помеченные all-visible в VM, пропускаются (если VACUUM не aggressive). На каждой странице делается pruning, TID мёртвых line pointer'ов собираются в память, старые версии замораживаются, выставляются биты VM.
2. **Чистка индексов.** Для каждого индекса выполняется bulkdelete по собранному списку TID; для btree это полный проход по индексу. Если память под TID кончилась, фазы 1-3 повторяются, и индексы сканируются по несколько раз, а на больших таблицах это очень дорого. До 17-й версии список был массивом по 6 байт на TID с потолком 1 ГБ независимо от `maintenance_work_mem`. В 17 его заменили на TidStore на radix tree: он в разы компактнее и потолка нет.
3. **Второй проход по heap.** `LP_DEAD` превращаются в `LP_UNUSED`, и только теперь слоты свободны.
4. **Учёт.** Обновляются FSM, `reltuples`/`relpages`, `relfrozenxid`/`relminmxid`, `datfrozenxid`; обрезаются `pg_xact` и `pg_multixact`.
5. **Обрезка пустого хвоста таблицы.** Ненадолго берётся AccessExclusiveLock. На мастере это обычно незаметно, а на реплике блокировка проигрывается из WAL и рубит запросы. Отключается параметром таблицы `vacuum_truncate = off`, в 18 появился одноимённый GUC.

Если у таблицы нет индексов, всё делается за один проход.

Обычный VACUUM не возвращает место ОС, кроме хвоста: он делает его пригодным для переиспользования. Раздутую таблицу сжимает VACUUM FULL. Он переписывает таблицу под ACCESS EXCLUSIVE и требует ещё столько же места на диске. Онлайн-альтернативы: pg_repack или pg_squeeze.

### Autovacuum

Работает так: launcher запускает воркеров, по умолчанию их не больше трёх (`autovacuum_max_workers`).

**Триггер по мёртвым строкам:** `n_dead_tup > autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2) * reltuples`. На таблице в миллиард строк это 200 млн мёртвых до запуска. Поэтому большим таблицам `scale_factor` снижают на уровне таблицы. В 18 появился потолок `autovacuum_vacuum_max_threshold` (по умолчанию 100 млн).

**Триггер по вставкам** (с 13): `autovacuum_vacuum_insert_threshold` / `insert_scale_factor`. До него append-only таблицы не получали ни битов VM, ни заморозки вплоть до антивраппаунд-прохода.

**Троттлинг cost-based.** Каждая прочитанная и каждая загрязнённая страница стоит очков. Набрав `autovacuum_vacuum_cost_limit` (по умолчанию берётся `vacuum_cost_limit` = 200, бюджет делится между воркерами), воркер спит `autovacuum_vacuum_cost_delay`: 2 мс с 12-й версии, раньше было 20. Дефолты консервативные, на современных дисках лимит обычно поднимают в разы. Ручной VACUUM по умолчанию работает без задержек.

**Обычный autovacuum уступает.** Если кто-то ждёт блокировку, которую он держит, deadlock detector его отменяет. Антивраппаунд-автовакуум (в `pg_stat_activity` выглядит как `autovacuum: VACUUM ... (to prevent wraparound)`) не отменяется. Отсюда классическая авария: ALTER TABLE ждёт этот автовакуум, а за ALTER выстраиваются в очередь все запросы к таблице.

## Wraparound и заморозка

xid 32-битный, и сравниваются они по кругу: `(int32)(a - b) < 0`. Для любого xid около 2^31 (≈2.1 млрд) номеров лежат «в прошлом» и столько же «в будущем». Если ничего не делать, строка с `xmin = 1000` после 2^31 транзакций окажется «в будущем» для всех и пропадёт из выборок. Данные на диске будут целы, но невидимы.

Решение: заморозка. Версии с закоммиченным xmin старше горизонта получают флаг `HEAP_XMIN_FROZEN`. До 9.4 xmin перезаписывали на 2 (FrozenTransactionId), теперь исходное значение сохраняется для отладки. Замороженная версия видна всем, и её возраст больше не учитывается. Старый xmax от откаченной транзакции или голой блокировки при этом тоже вычищается.

Учёт ведётся так. `pg_class.relfrozenxid` гарантирует, что в таблице (включая её TOAST) нет незамороженных xid старше этого значения. `pg_database.datfrozenxid` равен минимуму по базе. Лимиты всего кластера определяются самой старой `datfrozenxid`. С 15-й версии `relfrozenxid` после VACUUM выставляется по фактически самому старому оставшемуся xid, поэтому продвигается заметно дальше.

Параметры:

- `vacuum_freeze_min_age` (50 млн): насколько старым должен быть xid, чтобы VACUUM заморозил его попутно. С 16 заморозка постраничная. Если на странице нужно заморозить хоть что-то или pruning всё равно генерирует FPI, замораживается вся страница, чтобы стать all-frozen.
- `vacuum_freeze_table_age` (150 млн): если `age(relfrozenxid)` выше, VACUUM становится aggressive и читает все страницы, кроме all-frozen. На огромной таблице без all-frozen страниц это полный проход.
- `autovacuum_freeze_max_age` (200 млн): выше этого порога autovacuum запускается для таблицы принудительно, даже при `autovacuum = off`. Это тот самый `(to prevent wraparound)`.
- `vacuum_failsafe_age` (1.6 млрд, с 14): VACUUM переходит в аварийный режим. Индексы пропускает, cost delay игнорирует, только замораживает.
- В 18 обычный VACUUM ещё и прихватывает часть страниц all-visible, но не all-frozen, чтобы размазать работу будущего aggressive-прохода (`vacuum_max_eager_freeze_failure_rate`).

Ближе к краю начинаются предупреждения. За ~40 млн xid до точки wraparound в лог и клиентам сыплется `WARNING: database "x" must be vacuumed within N transactions`. За ~3 млн база перестаёт выдавать новые xid: `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение при этом работает, запись нет. Пороги 40/3 млн действуют с 14-й версии, раньше было примерно 11 и 1 млн; насчёт точной версии изменения я не на 100% уверен.

Как лечить. Сначала убрать то, что держит горизонт: забытые prepared transactions, мёртвые слоты, зависшие сессии. Потом запустить обычный VACUUM в этой базе. Документация с 16-й версии говорит делать это в нормальном режиме, single-user mode больше не нужен (раньше советовали именно его). VACUUM FULL в такой ситуации не делать.

Самый важный нюанс: горизонт ограничивает и заморозку. Порог заморозки равен `min(горизонт, nextXid - freeze_min_age)`. Если транзакция висит неделю, за эту неделю ни одна таблица не заморозит ни одного xid новее её. Автовакуум будет крутиться без остановки и ничего не сможет сделать. Большинство реальных wraparound-аварий выглядят именно так: забытый слот, prepared transaction или idle in transaction, при живом и работающем автовакууме.

Ещё два капкана:

- Temp-таблицы автовакуум не обрабатывает вообще, их видит только сессия-владелец. Долгоживущее соединение в пуле с temp-таблицей тянет её `relfrozenxid` в прошлое. Осиротевшие после краша temp-таблицы автовакуум дропает.
- Расход xid. Каждая пишущая транзакция в autocommit тратит xid, SELECT FOR UPDATE тоже. Каждый SAVEPOINT или EXCEPTION-блок в plpgsql, внутри которого была запись, тратит ещё один xid на подтранзакцию. При 10k пишущих TPS порог 200 млн проходится примерно за 5.5 часов, и антивраппаунд-проходы идут постоянно. Батчинг сильно снижает расход.

### Мультиксакты

У мультиксактов свой набор параметров:

- `vacuum_multixact_freeze_min_age`: 5 млн;
- `vacuum_multixact_freeze_table_age`: 150 млн;
- `autovacuum_multixact_freeze_max_age`: 400 млн.

Возраст смотрят через `mxid_age(relminmxid)`. Отдельно ограничено пространство members, у него тоже 32-битная адресация. Autovacuum начинает агрессивничать раньше, если members заполняются, даже при небольшом `mxid_age`. Ошибка при исчерпании похожая: `database is not accepting commands that generate new MultiXactIds`.

### 64 бита

В ядре уже есть `FullTransactionId` (epoch + xid), и `pg_current_xact_id()` возвращает `xid8`. Но в заголовке строки на диске по-прежнему 32 бита. Насколько я знаю, 64-битные xid в heap в ваниль не вошли; в Postgres Pro Enterprise они есть.

## Реплики

Hot standby строит снапшоты по записям running-xacts из WAL. Если мастер вычистил версии, нужные запросу на реплике, при проигрывании WAL возникает конфликт. Реплика ждёт `max_standby_streaming_delay`, потом отменяет запрос с ошибкой `canceling statement due to conflict with recovery`.

Вариантов три, у каждого своя цена:

- `hot_standby_feedback = on`: реплика сообщает мастеру свой xmin, и её долгие запросы раздувают таблицы на мастере;
- больший delay: реплика начинает отставать;
- отдельная реплика под аналитику.

`vacuum_defer_cleanup_age` убрали в 16.

## Подводные камни

- Откаченный UPDATE на 100 млн строк оставил 100 млн мёртвых версий и раздутые индексы, хотя сам ROLLBACK прошёл мгновенно.
- Подтранзакции. ProcArray кэширует до 64 subxid на бэкенд (`PGPROC_MAX_CACHED_SUBXIDS`). Если их больше, наступает overflow, и проверки видимости начинают ходить в SLRU `pg_subtrans`. Это известный обрыв производительности, особенно заметный на репликах. Сюда же ORM, которые оборачивают каждый запрос в SAVEPOINT. В 17 размеры SLRU стали настраиваемыми (`subtransaction_buffers` и др.); это смягчает проблему, но не устраняет.
- TRUNCATE и переписывающие ALTER TABLE не MVCC-safe. RR-транзакция, которая ещё не трогала таблицу, после чужого закоммиченного TRUNCATE увидит её пустой.
- Последовательности живут вне MVCC: `nextval` не откатывается, отсюда дыры в нумерации.
- `COPY ... FREEZE` в таблицу, созданную или обрезанную в той же транзакции, сразу пишет замороженные строки. С 14 он ставит и биты VM, и последующий VACUUM почти ничего не делает.
- `old_snapshot_threshold`, который позволял ломать долгие снапшоты ради вакуума, удалили в 17.
- Страховки от зависших сессий: `idle_in_transaction_session_timeout`, `transaction_timeout` (с 17), `statement_timeout`.

### style (26463 chars)

MVCC в PostgreSQL устроен так: каждая версия строки хранит в заголовке номер транзакции, которая её создала (`xmin`), и номер транзакции, которая её удалила или заменила (`xmax`). Каждый запрос смотрит на таблицу через снапшот, то есть через список транзакций, которые для него «уже случились». Старые версии остаются прямо в таблице, поэтому их нужно чистить (VACUUM). Номера транзакций 32-битные и идут по кругу, поэтому старые номера нужно «замораживать», иначе наступит wraparound.

Ниже по слоям, от заголовка строки до заморозки.

## 1. Базовая модель: версии лежат в самой таблице

В Oracle и MySQL/InnoDB строка обновляется на месте, а старая версия уходит в undo-лог. В PostgreSQL undo нет. Любой `UPDATE` пишет в heap новую физическую версию строки (tuple), а старую помечает как удалённую. `DELETE` только помечает версию. Физически ничего не стирается до VACUUM или pruning.

Из этого следует всё остальное:
- читатели не блокируют писателей и наоборот: каждый видит свою версию;
- откат транзакции бесплатный: её версии просто становятся невидимыми по статусу «aborted» в CLOG, ничего не нужно возвращать;
- мусор копится в самих таблицах и индексах, отсюда bloat и необходимость VACUUM;
- `UPDATE` по сути равен `DELETE` + `INSERT` и обычно требует новых записей во всех индексах (кроме HOT, об этом ниже).

## 2. Идентификаторы транзакций (xid)

`xid` 32-битный, около 4,2 млрд значений. Специальные значения:
- `0` InvalidTransactionId, «нет транзакции»;
- `1` BootstrapTransactionId;
- `2` FrozenTransactionId, «старше всех»;
- обычные xid начинаются с `3`.

Xid выдаётся лениво, при первой записи. Пока транзакция только читает, у неё есть лишь виртуальный идентификатор (`virtualxid` вида `backendID/localXID`), который не расходует глобальный счётчик. Поэтому read-only нагрузка не приближает wraparound. `pg_current_xact_id()` (раньше `txid_current()`) принудительно выдаёт xid, а `pg_current_xact_id_if_assigned()` нет.

Внутри ядра есть 64-битный `FullTransactionId` (эпоха + xid), его видно через тип `xid8`. Но в заголовках строк на диске по-прежнему 32 бита, и вся проблема wraparound отсюда.

Сравнение xid круговое (modulo 2³¹): для любого xid примерно 2,1 млрд значений считаются «прошлым», а 2,1 млрд «будущим». Нормальные xid сравниваются через `TransactionIdPrecedes`, где фактически вычисляется знак `(int32)(a - b)`.

## 3. Заголовок версии строки

Каждый tuple начинается с `HeapTupleHeaderData` (23 байта + выравнивание):

| Поле | Смысл |
|---|---|
| `t_xmin` | xid транзакции, вставившей версию |
| `t_xmax` | xid удалившей/обновившей или заблокировавшей версию; `0`, если нет |
| `t_cid` | command id внутри транзакции (cmin и/или cmax, при необходимости combo cid) |
| `t_ctid` | ссылка на себя или на следующую версию той же строки |
| `t_infomask`, `t_infomask2` | флаги: hint bits, тип блокировки, HOT, число атрибутов |
| `t_hoff` | смещение до данных |

Несколько тонкостей:

`xmax ≠ 0` не означает, что строка удалена. Туда же пишется xid транзакции, которая взяла строчную блокировку (`SELECT ... FOR UPDATE/SHARE`, проверка внешних ключей). Такая запись помечается флагом `HEAP_XMAX_LOCK_ONLY`. Если транзакция-удалитель откатилась, `xmax` тоже остаётся ненулевым, а версия при этом живая. Следующий `UPDATE` просто перезапишет `xmax`.

`ctid` образует цепочку версий. У актуальной версии `ctid` указывает на неё саму. У старой указывает на новую. Именно по этой цепочке Read Committed находит свежую версию при конфликте обновлений.

`cmin`/`cmax` нужны, чтобы транзакция правильно видела свои собственные изменения между командами. Каждая команда внутри транзакции получает свой command id (`curcid`). Строка, вставленная командой 3, не видна команде 2 и видна команде 4. Поэтому `UPDATE t SET x = x + 1` не зацикливается на строках, которые сам же только что вставил (Halloween problem). Если версию одна и та же транзакция и создала, и удалила, нужны оба значения, а поле одно. Тогда туда пишется combo cid, индекс в локальной для бэкенда таблице пар (cmin, cmax). Это память конкретной сессии, поэтому другим она и не нужна: для других транзакций эта версия всё равно невидима.

## 4. Как это выглядит на практике

```sql
CREATE EXTENSION pageinspect;
CREATE TABLE t (id int, v text);

INSERT INTO t VALUES (1, 'a');           -- транзакция 750
UPDATE t SET v = 'b' WHERE id = 1;       -- транзакция 751

SELECT xmin, xmax, ctid, * FROM t;
--  xmin | xmax | ctid  | id | v
--   751 |    0 | (0,2) |  1 | b

SELECT lp, t_xmin, t_xmax, t_ctid, t_infomask
FROM heap_page_items(get_raw_page('t', 0));
--  lp | t_xmin | t_xmax | t_ctid
--   1 |    750 |    751 | (0,2)    -- старая версия, «удалена» 751
--   2 |    751 |      0 | (0,2)    -- новая версия
```

Обычный `SELECT` показывает только видимую версию. `pageinspect` показывает страницу целиком, включая мёртвую версию. Флаги удобно расшифровывать через `heap_tuple_infomask_flags(t_infomask, t_infomask2)`.

## 5. Статус транзакций: CLOG и hint bits

Сам `xmin` ничего не говорит о том, закоммичена ли транзакция. Статус хранится в CLOG (каталог `pg_xact`): по 2 бита на xid, четыре состояния: in progress, committed, aborted, sub-committed.

Ходить в CLOG на каждую строку дорого, поэтому есть hint bits в `t_infomask`:
- `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID`;
- `HEAP_XMAX_COMMITTED` / `HEAP_XMAX_INVALID`.

Первый, кто прочитал версию после завершения транзакции, проверяет CLOG и проставляет hint bit прямо в странице. Отсюда известный эффект: первый `SELECT` по только что загруженной таблице пишет на диск, потому что пачкает страницы hint-битами. Сами hint bits в WAL не пишутся, но при включённых checksums или `wal_log_hints = on` первое изменение страницы после чекпоинта порождает full page image, и тогда `SELECT` генерирует WAL.

Ещё нюанс: при `synchronous_commit = off` hint bit «committed» нельзя ставить, пока WAL не сброшен до LSN коммита этой транзакции. Иначе после сбоя на странице осталась бы отметка о коммите, которого по WAL не было.

Транзакция, которая упала вместе с сервером, в CLOG остаётся «in progress» навсегда. После рестарта её нет в ProcArray, поэтому она трактуется как aborted.

Источник истины для вопроса «работает ли транзакция сейчас» это ProcArray в shared memory, а не CLOG. При коммите запись в CLOG делается до удаления транзакции из ProcArray, поэтому код видимости сначала проверяет «в процессе ли транзакция» и только потом смотрит CLOG. Обратный порядок дал бы гонку.

## 6. Снапшот

Снапшот (`SnapshotData`) по сути состоит из трёх вещей:
- `xmin`: самый старый xid, который на момент снимка ещё был активен. Всё, что меньше, гарантированно завершено (закоммичено или откачено);
- `xmax`: первый ещё не выданный xid (`latestCompletedXid + 1`). Всё, что больше или равно, для снапшота «в будущем» и невидимо;
- `xip[]`: список xid, которые были активны в момент снимка и лежат в диапазоне `[xmin, xmax)`.

Плюс `subxip[]` для подтранзакций, флаг `suboverflowed` и `curcid` для своих команд.

```sql
SELECT pg_current_snapshot();
-- 100:105:100,102
```

Это означает: xid < 100 завершены; xid ≥ 105 невидимы; 100 и 102 были в процессе и невидимы, даже если закоммитятся через секунду; 101, 103, 104 завершены, и их видимость определяется по CLOG.

Ключевое свойство: снапшот фиксирует, какие транзакции считать завершёнными, а не какие данные видны. Транзакция из `xip` может закоммититься позже, CLOG будет говорить «committed», но для этого снапшота она навсегда останется «в процессе». Поэтому проверка «есть ли xid в снапшоте» идёт раньше проверки CLOG.

Снапшот строится функцией `GetSnapshotData`, которая проходит по ProcArray. На сотнях соединений это было узким местом; в PG 14 её заметно ускорили (в том числе кешируя снапшот, если с прошлого раза ни одна транзакция не завершилась).

## 7. Правила видимости

Упрощённая логика `HeapTupleSatisfiesMVCC`:

```
visible(tuple, snap):
    # Часть 1: видна ли вставка
    if xmin is frozen:
        pass
    elif xmin is my transaction (or my subtransaction):
        if cmin >= snap.curcid:            # вставлено моей же более поздней командой
            return false
    elif xmin >= snap.xmax or xmin in snap.xip:
        return false                       # для снапшота ещё в процессе
    elif not committed(xmin):
        return false                       # откатилась или упала

    # Часть 2: видно ли удаление
    if xmax is invalid or aborted or lock-only:
        return true
    if xmax is my transaction:
        return cmax >= snap.curcid         # удалено моей более поздней командой => ещё видна
    if xmax >= snap.xmax or xmax in snap.xip:
        return true                        # удалитель для снапшота ещё не завершён
    if committed(xmax):
        return false
    return true
```

Если `xmax` является мультитранзакцией (см. ниже), сначала из неё извлекается xid того участника, который именно обновлял, а не блокировал.

Следствия:
- одна и та же физическая версия одновременно видна одним снапшотам и невидима другим;
- закоммиченный `DELETE` ещё ничего не удаляет: пока жив хоть один снапшот, для которого удалитель «в процессе», версия ему нужна;
- индексы не хранят `xmin`/`xmax`, поэтому индексный поиск обязан идти в heap проверять видимость. Index-only scan обходит это через visibility map: если страница помечена all-visible, в heap можно не ходить.

## 8. Уровни изоляции и конкурентные изменения

**Read Committed** (по умолчанию): новый снапшот на каждый оператор. Внутри одного оператора данные согласованы, между операторами нет. Read Uncommitted в PostgreSQL ведёт себя так же: грязного чтения нет вообще.

**Repeatable Read**: снапшот берётся один раз на первый оператор транзакции, а не на `BEGIN`. Между `BEGIN` и первым `SELECT` мир ещё может измениться.

Самое интересное начинается, когда `UPDATE`/`DELETE` натыкается на версию, у которой `xmax` поставлен другой транзакцией:
1. Если та транзакция ещё работает, мы ждём её завершения (через блокировку на её xid).
2. Если она откатилась, работаем с этой версией.
3. Если закоммитилась:
   - в **Read Committed** идём по `ctid` к новой версии, заново проверяем на ней `WHERE` (механизм EvalPlanQual) и, если условие выполняется, обновляем её. Это видит данные, которых не было в снапшоте оператора, и даёт известные аномалии: например, `UPDATE ... WHERE balance > 100` может применить изменение к строке, которая подходила только в новой версии, при этом пропустив строки, ставшие подходящими после снапшота;
   - в **Repeatable Read** и **Serializable** получаем `ERROR: could not serialize access due to concurrent update`, и приложение должно повторить транзакцию.

**Serializable** построен поверх снапшотов (SSI, Serializable Snapshot Isolation). Добавляются предикатные «блокировки» `SIReadLock`, которые никого не блокируют, а только отслеживают зависимости чтение-запись. Если обнаруживается опасная структура из двух последовательных rw-зависимостей, одна из транзакций откатывается с ошибкой сериализации. Ошибки бывают ложноположительными, особенно при эскалации предикатных блокировок до уровня страницы или таблицы.

Снапшот можно экспортировать (`pg_export_snapshot()`) и импортировать в другой сессии (`SET TRANSACTION SNAPSHOT`). Так работает параллельный `pg_dump`.

## 9. Подтранзакции и мультитранзакции

**Подтранзакции** (`SAVEPOINT`, блоки `EXCEPTION` в PL/pgSQL) получают собственные xid при первой записи. Связь «подтранзакция → родитель» хранится в `pg_subtrans`. В ProcArray каждый бэкенд кеширует не больше 64 своих подтранзакций. Если их больше, снапшоты всех сессий получают `suboverflowed`, и проверка видимости начинает ходить в `pg_subtrans` через SLRU-кеш. Это классический обрыв производительности на нагруженных системах: долгая транзакция с сотней savepoint'ов (или PL/pgSQL-функция с `EXCEPTION` в цикле) замедляет всех. Каждая пишущая подтранзакция к тому же расходует xid.

**Мультитранзакции** появляются, когда строку одновременно блокируют несколько транзакций (`FOR SHARE`, `FOR KEY SHARE` от проверок FK) или одна блокирует, а другая обновляет. В `xmax` один xid не помещается, поэтому туда пишется MultiXactId (флаг `HEAP_XMAX_IS_MULTI`), а список участников с режимами лежит в `pg_multixact/offsets` и `pg_multixact/members`. MultiXactId тоже 32-битный и тоже подвержен wraparound, у него свои параметры заморозки (раздел 12). Нагрузка с массовыми FK-проверками по одним и тем же родительским строкам может разогнать мультитранзакции очень быстро.

## 10. Мёртвые версии, горизонт и HOT

Версия становится мёртвой, когда её `xmax` закоммичен и при этом удаление видно всем возможным снапшотам. Граница называется горизонтом (`OldestXmin`, в новых версиях `GlobalVisState`): минимум из `xmin` всех снапшотов и xid всех активных транзакций. Версия с закоммиченным `xmax` старше горизонта мертва (DEAD). Если `xmax` моложе горизонта, она «недавно мёртвая» (RECENTLY_DEAD) и удалять её нельзя.

Горизонт удерживают:
- долгие транзакции, включая `idle in transaction`;
- долгие запросы даже в Read Committed: одиночный оператор держит снапшот, пока выполняется;
- транзакции Repeatable Read/Serializable целиком;
- подготовленные транзакции (`PREPARE TRANSACTION`), про которые забыли;
- слоты репликации (`xmin`, а для логической `catalog_xmin` для системных каталогов);
- `hot_standby_feedback = on`: долгие запросы на реплике удерживают горизонт на мастере.

Пока горизонт стоит, никакой VACUUM мусор не удалит, сколько его ни запускай. Это самая частая причина «VACUUM работает, а таблица всё растёт».

**HOT (heap-only tuples).** Если `UPDATE` не меняет ни одной индексированной колонки и новая версия помещается на ту же страницу, индексы не трогаются вовсе. Индекс по-прежнему указывает на начало цепочки, а дальше по `ctid` внутри страницы находится актуальная версия. С PG 16 HOT разрешён и при изменении колонок, по которым есть только «суммирующие» индексы вроде BRIN. Чтобы HOT срабатывал, на страницах должно оставаться место: для часто обновляемых таблиц снижают `fillfactor` (например, до 70-90). Долю HOT видно в `pg_stat_user_tables.n_tup_hot_upd`.

**Pruning.** Обычное чтение страницы может её почистить: если на странице мало места, а мёртвые версии старше горизонта есть, бэкенд берёт cleanup lock и удаляет мёртвые HOT-версии, перестраивая цепочки через redirect line pointers. Это делается попутно, без VACUUM. Ограничение: pruning освобождает место под данными, но line pointer, на который ссылается индекс, превращается в `LP_DEAD` и остаётся (4 байта), пока индекс не почистит VACUUM. Освободить его раньше нельзя, иначе индексная запись указывала бы на переиспользованный слот с чужой строкой.

Индексы чистятся и сами: B-tree помечает записи как killed, если при сканировании выяснилось, что heap-версия мертва для всех, и удаляет их при заполнении страницы. С PG 14 есть bottom-up deletion, которая перед расщеплением страницы индекса пытается выкинуть дубликаты версий, порождённые не-HOT обновлениями.

## 11. Что делает VACUUM

Обычный `VACUUM` (без `FULL`) работает без эксклюзивной блокировки, параллельно с чтением и записью. Порядок такой:

1. **Сканирование heap.** Проходит страницы, пропуская помеченные all-visible в visibility map (если vacuum не агрессивный). На каждой странице делает pruning, замораживает старые версии (раздел 12) и собирает TID мёртвых line pointer'ов. Память под TID ограничена `maintenance_work_mem` / `autovacuum_work_mem`. До PG 17 это был плоский массив с потолком в 1 ГБ, и при нехватке приходилось делать несколько проходов по индексам. С PG 17 используется TidStore (radix tree), который гораздо компактнее и не ограничен 1 ГБ.
2. **Очистка индексов.** Для каждого индекса вызывается `ambulkdelete`, которая удаляет записи, указывающие на собранные TID. Обычно это самая дорогая часть, потому что B-tree сканируется целиком. Если мёртвых строк совсем мало (меньше ~2% страниц с ними), с PG 14 этот шаг может быть пропущен. Можно управлять и вручную: `VACUUM (INDEX_CLEANUP off)`.
3. **Второй проход по heap.** Line pointers из `LP_DEAD` становятся `LP_UNUSED`, их можно переиспользовать.
4. **Хвост.** Обновляются visibility map и free space map, пустые страницы в конце файла отрезаются (на это нужна кратковременная AccessExclusiveLock, и на реплике это может вызвать конфликты; отключается `vacuum_truncate`), обновляются `pg_class.relpages`, `reltuples`, `relfrozenxid`, `relminmxid`.

Visibility map хранит по два бита на страницу:
- **all-visible**: все версии на странице видны всем. Используется index-only scan и позволяет обычному vacuum пропускать страницу;
- **all-frozen**: все версии заморожены. Позволяет пропускать страницу даже агрессивному vacuum.

Любая запись в страницу сбрасывает оба бита.

Обычный VACUUM не возвращает место ОС, кроме отрезанного хвоста. Свободное место внутри файла переиспользуется новыми строками через FSM. Чтобы реально уменьшить файл, нужен `VACUUM FULL` (полная перезапись таблицы и индексов под AccessExclusiveLock, по сути недоступность таблицы) или `pg_repack` / `pg_squeeze`, которые делают это почти онлайн.

## 12. Autovacuum

Launcher периодически (`autovacuum_naptime`, 1 мин) выбирает базы, а воркеры (`autovacuum_max_workers`, по умолчанию 3) обрабатывают таблицы. Таблица считается кандидатом, если:

- мёртвых строк больше, чем `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples` (50 + 20%). В PG 18 добавлен `autovacuum_vacuum_max_threshold` (по умолчанию 100 млн), чтобы на огромных таблицах 20% не превращались в миллиарды;
- вставок больше, чем `autovacuum_vacuum_insert_threshold + autovacuum_vacuum_insert_scale_factor * reltuples` (с PG 13). Это нужно для insert-only таблиц: удалять там нечего, но страницы надо пометить all-visible и заморозить, иначе позже придёт тяжёлая агрессивная заморозка всего сразу;
- возраст `relfrozenxid` превысил `autovacuum_freeze_max_age` (раздел 13).

Скорость ограничивается cost-based delay: каждое чтение и запись страницы набирают «очки», и при достижении `autovacuum_vacuum_cost_limit` воркер спит `autovacuum_vacuum_cost_delay` (2 мс с PG 12). Лимит делится между всеми активными воркерами, поэтому увеличение `autovacuum_max_workers` без увеличения лимита работу не ускоряет. На больших и нагруженных таблицах масштабные факторы обычно задают на уровне таблицы: `ALTER TABLE t SET (autovacuum_vacuum_scale_factor = 0.01)`.

Обычный autovacuum уступает блокировкам: если кто-то ждёт конфликтующую блокировку (например, DDL), воркер отменяется. Anti-wraparound autovacuum не уступает, об этом дальше.

## 13. Wraparound и заморозка

### Проблема

Из-за кругового сравнения xid каждый номер через ~2,1 млрд транзакций переходит из «прошлого» в «будущее». Если у строки остался `xmin = 1000`, а счётчик ушёл на 2³¹ вперёд, все снапшоты начнут считать её вставленной в будущем, и строка исчезнет. Данные физически на месте, но невидимы. Это и есть transaction ID wraparound.

### Решение: заморозка

Версию, чей `xmin` закоммичен и гарантированно старше всех снапшотов, можно пометить как замороженную. Тогда она видна всем независимо от значения `xmin`. До PG 9.4 `xmin` физически заменялся на `FrozenTransactionId (2)`. С 9.4 просто ставятся оба бита `HEAP_XMIN_COMMITTED | HEAP_XMIN_INVALID` (вместе они значат `HEAP_XMIN_FROZEN`), а исходный `xmin` сохраняется для отладки.

Заморозка касается и `xmax`: старый `xmax` от откатившейся транзакции или от чистой блокировки обнуляется, старую мультитранзакцию раскрывают (иногда с созданием новой, поменьше) или убирают.

Учёт ведётся так:
- `pg_class.relfrozenxid`: все xid в таблице старше этого значения гарантированно заморожены;
- `pg_database.datfrozenxid`: минимум `relfrozenxid` по базе;
- самая старая `datfrozenxid` по кластеру определяет, насколько близко wraparound. Пространство xid общее на весь кластер, включая `template0`.

Когда `datfrozenxid` продвигается, старые сегменты `pg_xact` (и `pg_multixact`) можно отрезать, потому что для замороженных строк CLOG больше не нужен.

### Параметры

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | версии старше этого возраста vacuum замораживает, когда обрабатывает страницу |
| `vacuum_freeze_table_age` | 150 млн | если `age(relfrozenxid)` больше, vacuum становится агрессивным: сканирует все страницы, кроме all-frozen, а не только не-all-visible |
| `autovacuum_freeze_max_age` | 200 млн | принудительный anti-wraparound autovacuum, даже при `autovacuum = off` |
| `vacuum_failsafe_age` | 1,6 млрд | аварийный режим (PG 14+): vacuum отключает cost delay и пропускает очистку индексов, лишь бы успеть заморозить |
| `vacuum_multixact_freeze_min_age` | 5 млн | то же для мультитранзакций |
| `vacuum_multixact_freeze_table_age` | 150 млн | |
| `autovacuum_multixact_freeze_max_age` | 400 млн | |
| `vacuum_multixact_failsafe_age` | 1,6 млрд | |

`vacuum_freeze_table_age` фактически ограничен сверху значением `0.95 * autovacuum_freeze_max_age`.

Ограничение min_age и table_age: обычный vacuum пропускает all-visible страницы, а значит, не замораживает их. Они накапливаются, и агрессивный vacuum потом читает и переписывает огромную часть таблицы за один раз. Особенно больно это бьёт по большим insert-only таблицам: через 150-200 млн транзакций приходит «шторм заморозки» с массой записи и WAL. Последние версии смягчают это:
- PG 13: autovacuum по вставкам, страницы замораживаются раньше;
- PG 16: заморозка решается на уровне страницы. Если страницу всё равно пришлось переписать с full page image, её замораживают целиком, раз это почти бесплатно;
- PG 17: pruning и freezing страницы объединены в одну WAL-запись;
- PG 18: обычный vacuum может «жадно» сканировать часть all-visible, но не all-frozen страниц, чтобы заморозить их заранее и размазать агрессивную работу во времени (`vacuum_max_eager_freeze_failure_rate`).

### Что происходит у края

Anti-wraparound autovacuum отображается в `pg_stat_activity` как `autovacuum: VACUUM public.t (to prevent wraparound)`. Он не отменяется конфликтующими блокировками, поэтому `ALTER TABLE` может встать за ним в очередь, а за `ALTER TABLE` встанут все остальные запросы к таблице. Убивать такой воркер обычно бессмысленно: launcher запустит его снова.

Если и это не помогло:
- примерно за 40 млн xid до точки невозврата в лог и клиентам идут предупреждения `database "X" must be vacuumed within N transactions`;
- примерно за 3 млн xid сервер перестаёт выдавать новые xid: `database is not accepting commands that assign new transaction IDs to avoid wraparound data loss`. Чтение работает, любая запись нет.

Выход: найти и устранить то, что держит горизонт (иначе VACUUM ничего не заморозит), затем выполнить `VACUUM` на самых старых таблицах. В актуальной документации однопользовательский режим для этого больше не рекомендуется, достаточно обычного `VACUUM` в многопользовательском режиме. При этом `VACUUM FULL` в такой ситуации вреден: он медленнее и тоже расходует xid.

Самый частый сценарий катастрофы: autovacuum работает, но заморозить ничего не может, потому что горизонт держит забытый слот репликации или зависшая prepared-транзакция. Возраст растёт, и никто этого не замечает, пока не появятся предупреждения.

## 14. Диагностика

Насколько близко wraparound:

```sql
SELECT datname, age(datfrozenxid), mxid_age(datminmxid)
FROM pg_database ORDER BY 2 DESC;

SELECT c.oid::regclass, age(c.relfrozenxid), mxid_age(c.relminmxid),
       pg_size_pretty(pg_total_relation_size(c.oid))
FROM pg_class c
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY 2 DESC LIMIT 20;
```

Кто держит горизонт:

```sql
SELECT pid, state, backend_xid, backend_xmin,
       age(backend_xmin) AS xmin_age, xact_start, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

SELECT slot_name, active, xmin, catalog_xmin, age(xmin), age(catalog_xmin)
FROM pg_replication_slots;

SELECT gid, prepared, owner, age(transaction) FROM pg_prepared_xacts;
```

На репликах с `hot_standby_feedback` ищите долгие запросы там: их `xmin` приходит на мастер и виден в `pg_stat_replication.backend_xmin`.

Состояние таблиц и vacuum:

```sql
SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

SELECT * FROM pg_stat_progress_vacuum;
```

Для точной оценки bloat и состояния visibility map подходят расширения `pgstattuple` и `pg_visibility`. `log_autovacuum_min_duration = 0` (или небольшое значение) пишет в лог подробный отчёт по каждому прогону: сколько удалено, сколько осталось из-за горизонта (`tuples ... are dead but not yet removable`), какой `OldestXmin` использовался.

## 15. Нюансы, которые часто упускают

- **`TRUNCATE` и перезаписывающий DDL не MVCC-безопасны.** После `TRUNCATE` или `ALTER TABLE ... SET TYPE` (с перезаписью таблицы) транзакция Repeatable Read, начатая раньше, увидит таблицу пустой, потому что старый файл подменён новым.
- **Последовательности вне MVCC.** `nextval` не откатывается, отсюда дыры в id.
- **Системные каталоги** читаются через отдельный catalog snapshot, который обновляется чаще, чем снапшот транзакции. Поэтому DDL может быть виден раньше, чем данные.
- **`SELECT ... FOR UPDATE` пишет:** ставит `xmax` и расходует xid. Массовые блокировки строк создают WAL, грязные страницы и, при `FOR SHARE`/`FOR KEY SHARE`, мультитранзакции.
- **Конфликты на реплике.** Мастер удаляет версии, которые ещё нужны долгому запросу на реплике. Без `hot_standby_feedback` запрос будет отменён с `canceling statement due to conflict with recovery` после `max_standby_streaming_delay`. С фидбэком запрос доживёт, но держит горизонт мастера, со всеми последствиями выше.
- **`old_snapshot_threshold`** (ошибка «snapshot too old») удалён в PG 17, ограничивать долгие снапшоты теперь нужно через `idle_in_transaction_session_timeout`, `statement_timeout`, `transaction_timeout` (PG 17) и мониторинг.
- **Visibility map и index-only scan.** Если таблица часто обновляется и vacuum не успевает выставлять all-visible, index-only scan деградирует до обычного индексного (`Heap Fetches` в `EXPLAIN ANALYZE`).
- **Порядок видимости и порядок в WAL могут не совпадать.** Транзакция становится видимой, когда она удалена из ProcArray, а не в момент записи коммита в WAL. При синхронной репликации это даёт эффект, когда на мастере коммит виден другим сессиям чуть раньше, чем клиент получил подтверждение, или в ином порядке, чем на реплике. Для большинства приложений это незаметно, но для систем, рассчитывающих на строгий порядок коммитов, это нужно знать.

## 08-english

> What's the practical difference between git rebase and git merge, and when should I pick each?

### baseline (2284 chars)

## Суть

Обе команды переносят изменения из одной ветки в другую. Разница в том, как выглядит история после этого.

**`git merge`** создаёт merge-коммит с двумя родителями. История остаётся такой, какой была на самом деле: видно, что ветка жила отдельно и в какой-то момент слилась.

```
      A---B---C  feature
     /         \
D---E---F---G---M  main
```

**`git rebase`** переписывает коммиты ветки поверх новой базы. Получаются **новые коммиты с новыми хешами**, а история становится линейной, будто вы начали работу от свежего `main`.

```
D---E---F---G---A'--B'--C'  feature
```

## Практические последствия

| | merge | rebase |
|---|---|---|
| История | честная, ветвистая | линейная, чистая |
| Хеши коммитов | не меняются | меняются |
| Безопасно для общих веток | да | **нет** |
| Конфликты | решаются один раз | могут всплывать на каждом коммите |
| `git bisect`, `git log` | шумнее | удобнее |
| Откат фичи целиком | `git revert -m 1 <merge>` | нужно ревертить каждый коммит |

## Когда что брать

**Rebase:**
- Подтянуть свежий `main` в **свою локальную** ветку, которую ещё никто не забрал: `git pull --rebase` или `git rebase main`.
- Причесать коммиты перед PR: `git rebase -i` позволяет склеить «fix typo», переупорядочить коммиты и поправить сообщения.
- В проекте принята линейная история (rebase-and-merge или squash в PR).

**Merge:**
- Ветка уже запушена и с ней работают другие люди.
- Нужно сохранить факт интеграции, например долгоживущие ветки `release/*` или слияние `develop` в `main`.
- Хочется откатывать фичу одним действием.

## Золотое правило

**Не делайте rebase коммитов, которые уже кто-то забрал.** После rebase придётся делать `push --force`, а у коллег история разойдётся с вашей. Если всё же пришлось, используйте `git push --force-with-lease`: он не затрёт чужие коммиты, появившиеся на удалённой ветке после вашего последнего fetch.

## Типичный рабочий процесс

1. Работаете в своей фича-ветке и периодически делаете `git rebase main`, чтобы оставаться актуальным.
2. Перед PR вызываете `git rebase -i main` и чистите коммиты.
3. Сама интеграция в `main` проходит через merge или squash-merge в PR, смотря что принято в команде.

Если в команде уже есть договорённость, следуйте ей: единообразие важнее, чем выбор одного из двух подходов.

### both (2033 chars)

Rebase переписывает историю, чтобы она была линейной, merge сохраняет её как есть и добавляет коммит слияния. Rebase подходит для своей локальной ветки до публикации, merge для того, что уже лежит в общей ветке.

Что происходит в каждом случае:

`git merge main` в фиче-ветке создаёт merge-коммит с двумя родителями. Существующие коммиты не меняются, хеши остаются прежними. История честно показывает, что работа шла параллельно, но в графе появляются развилки и лишние коммиты вида «Merge branch 'main' into feature».

`git rebase main` берёт твои коммиты и заново применяет их поверх свежего `main`. Получаются новые коммиты с новыми хешами, история выглядит так, будто ты начал работу только что. Граф прямой, `git log` и `git bisect` читать проще.

Практические последствия:

| | merge | rebase |
|---|---|---|
| Хеши коммитов | не меняются | меняются |
| Конфликты | решаются один раз | могут всплывать на каждом переписываемом коммите |
| После публикации ветки | безопасно | нужен `push --force-with-lease`, ломает коллегам их копии |
| История | точная, но шумная | чистая, но «отредактированная» |
| Откат | `git revert -m 1` откатывает всю фичу разом | откатывать приходится по коммитам или через squash |

Когда что выбирать:

- Подтягиваешь свежий `main` в свою ещё не опубликованную или личную ветку: rebase (`git pull --rebase` или `git rebase main`).
- Хочешь причесать коммиты перед PR (склеить, переименовать, выкинуть «fix typo»): `git rebase -i`.
- Ветку уже кто-то забрал и работает поверх неё: только merge.
- Вливаешь готовую фичу в `main`: зависит от принятого в команде. Merge-коммит сохраняет границы фичи, squash-merge даёт один коммит на PR, rebase-merge даёт линейную историю без следа ветки.

Простое правило: не перебазируй то, что уже запушено в общую ветку и на чём могут стоять чужие коммиты. Всё остальное можно перебазировать.

При частых повторяющихся конфликтах во время rebase помогает `git config rerere.enabled true`: Git запоминает, как ты разрешил конфликт, и применяет это решение повторно.

### claudemd (1753 chars)

**Merge** сохраняет историю как есть и добавляет коммит слияния. **Rebase** переписывает твои коммиты поверх другой ветки и даёт линейную историю.

## Что меняется на практике

**Хэши.** Merge ничего не переписывает. Rebase создаёт новые коммиты с новыми хэшами. Если ветка уже запушена и кто-то на неё опирается, после rebase понадобится `git push --force-with-lease`, а у коллег история разъедется с удалённой.

**Конфликты.** При merge конфликты решаются один раз, в коммите слияния. Rebase применяет коммиты по одному, поэтому один и тот же конфликт может всплыть на нескольких коммитах подряд. Если такое повторяется, включи `git config rerere.enabled true`.

**История.** После merge видно, что работа шла параллельно, но `git log` обрастает коммитами вида «Merge branch 'main' into feature». Rebase даёт прямую линию: её проще читать, и с ней удобнее `git bisect` и `git revert` отдельных коммитов.

## Когда что выбирать

Rebase подходит, когда ветка твоя и ещё не стала общей:
- чтобы подтянуть свежий `main` в фичеветку: `git rebase main` или `git pull --rebase`;
- чтобы перед ревью почистить коммиты через `git rebase -i`: склеить «fix typo», переписать сообщения.

Merge подходит для общих веток:
- чтобы влить готовую фичу в `main` или `develop`;
- когда в ветке работают несколько человек;
- когда важно сохранить факт, что фича разрабатывалась отдельно (`--no-ff`).

Главное правило: не делай rebase коммитов, на которых другие уже построили свою работу.

Самый частый рабочий процесс совмещает оба подхода. Фичеветку ребейзишь на актуальный `main`, а в `main` вливаешь через merge или squash merge в PR. Чтобы `git pull` по умолчанию ребейзил локальные коммиты, а не плодил merge-коммиты, выставь `git config --global pull.rebase true`.

### current (2112 chars)

Оба способа сводят изменения из одной ветки в другую. Разница в том, что остаётся в истории.

**merge** берёт две ветки и создаёт merge-коммит с двумя родителями. Существующие коммиты не трогаются, SHA остаются прежними. История честная: видно, что была ветка и когда её влили. Минус в том, что при активной работе граф превращается в лапшу из `Merge branch 'main' into feature`.

**rebase** берёт твои коммиты и переигрывает их поверх новой базы. Получаются новые коммиты с новыми SHA, а история становится линейной, будто ты начал работу от свежего main. Читать её и гонять `git bisect` проще. Минус: это переписывание истории.

Практические последствия:

- Rebase ветки, которую уже кто-то стянул, ломает жизнь коллегам: у них старые SHA, у тебя новые. Отсюда главное правило: не ребейзить то, с чем работают другие. Свою личную ветку можно, после этого пушишь через `git push --force-with-lease`, не через голый `--force`.
- Конфликты. При merge решаешь их один раз. При rebase возможно на каждом коммите по очереди, если десять коммитов трогают одно место, будет больно. Тут помогает `git config rerere.enabled true`.
- Откат. Merge-коммит откатывается целиком через `git revert -m 1 <sha>`. После rebase фича размазана по отдельным коммитам, и откатывать придётся их.

Когда что брать:

- **rebase**: подтянуть свежий main в свою локальную ветку перед PR (`git rebase main`), почистить свои коммиты через `git rebase -i` (сквошнуть "fix typo", переписать сообщения), `git pull --rebase` вместо пула с лишним merge-коммитом.
- **merge**: влить готовую фичу в main или в общую ветку, интегрировать долгоживущие ветки (release, develop), любая ситуация, где важно сохранить, что изменения пришли пачкой из отдельной ветки.

Самый частый рабочий вариант: локально ребейзишь свою ветку на main и чистишь коммиты, а в main она попадает через merge или squash-merge в PR. Squash-merge сжимает всю фичу в один коммит в main. Это удобно, если промежуточные коммиты никому не нужны, но теряется детализация.

Если в команде уже принята конвенция, следуй ей. Смешивать подходы хаотично хуже, чем выбрать любой из них.

| | merge | rebase |

### baseline (981 chars)

`-f` и `-e` вернут **false** (код 1): они проверяют то, на что указывает ссылка, а цели нет. `-L` вернёт **true**, потому что смотрит на саму ссылку и не идёт по ней.

Можно проверить:

```bash
touch target && ln -s target link && rm target

[[ -e link ]]; echo $?   # 1
[[ -f link ]]; echo $?   # 1
[[ -L link ]]; echo $?   # 0
```

Так что первая проверка из моего ответа (`-f`) скажет «файла нет», хотя запись в каталоге есть. Это важно, например, перед `ln -s` или `touch`: путь занят, и создание упадёт или пойдёт не туда.

Что использовать в зависимости от задачи:

```bash
# есть ли что-нибудь по этому пути, включая битую ссылку
[[ -e "$f" || -L "$f" ]]

# именно битая ссылка
[[ -L "$f" && ! -e "$f" ]]

# живой обычный файл (битая ссылка не пройдёт)
[[ -f "$f" ]]
```

Ещё один нюанс: если ссылка указывает на каталог, к которому нет прав на поиск (`x`), `-e` тоже вернёт false. Цель при этом есть, но проверить её нельзя, и снаружи это выглядит так же, как битая ссылка.

### style (596 chars)

`-f` вернёт ложь: проверка идёт по цели ссылки, а цели нет. То же самое с `-e`, `-d`, `-s` и остальными, они все разыменовывают симлинк.

Саму ссылку видят только `-L` (или синоним `-h`), они ссылку не разыменовывают. Поэтому битый симлинк ловится так:

```bash
if [[ -L $path && ! -e $path ]]; then
  echo "битая ссылка"
fi
```

Отсюда практическое следствие: если нужно понять, занято ли имя в каталоге (например, перед созданием файла), одного `-e` мало, нужно `[[ -e $path || -L $path ]]`. Иначе битая ссылка покажется свободным местом, а запись по этому пути пойдёт туда, куда она указывает.
